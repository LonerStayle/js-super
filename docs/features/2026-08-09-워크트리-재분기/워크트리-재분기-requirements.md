> **다음 단계 안내**: 이 문서는 PRD (기획 단계 요구사항만) 입니다. 다음 단계로 `tech-design` skill (또는 `/tech-design` 슬래시) 을 호출해서 `워크트리-재분기-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요 — 그건 다음 두 산출물에 들어갑니다.

## 1. 배경/목적

`setting-up-worktrees` 스킬은 현재 호출 위치의 루트 아래 `.worktrees/` 에 워크트리를 만들고, 신규 브랜치는 현재 HEAD 에서 분기한다. 이미 만들어진 워크트리 안에서 스킬을 호출하면 두 가지 문제가 생긴다.

첫째, `.worktrees/` 가 기존 워크트리 **내부에 중첩** 생성된다. 중첩되면 git status 오염, git clean 사고, 에이전트 파일 탐색 시 컨텍스트 오염이 발생한다.

둘째, 기존 워크트리의 작업 상태를 확인하지 않고 분기한다. 커밋 안 된 변경이 있는 채로 분기하면 사용자가 의도한 시작점과 실제 분기 시작점이 어긋날 수 있다.

목적: 워크트리 안에서 호출해도 사용자가 위치를 신경 쓰지 않고, "현재 워크트리의 HEAD 를 시작점으로" 새 워크트리를 **메인 저장소 루트의 `.worktrees/`** 아래에 자동으로 안전하게 만들 수 있게 한다. 예시 (확정된 기대 동작):

```
# 세션 위치: .worktrees/나의에이전트 (브랜치: 나의에이전트, ecc533a)
/worktree 나의에이전트-툴콜링추가

git worktree list:
cogito                              131fae7 [dev]
.worktrees/나의에이전트              ecc533a [나의에이전트]
.worktrees/나의에이전트-툴콜링추가   ecc533a [나의에이전트-툴콜링추가]  ← 신규 (메인 루트 아래, 같은 커밋에서 분기)
```

## 3. 기능 요구사항 (FR)

- **FR-1 중첩 방지 배치**: 워크트리 내부에서 호출돼도 새 워크트리는 항상 **메인 저장소 루트**의 `.worktrees/<새브랜치>` 에 생성된다. 기존 워크트리 내부에 `.worktrees/` 를 중첩 생성하는 일이 없어야 한다. 사용자가 위치를 의식하거나 별도 지시할 필요 없이 자동 판정된다.
- **FR-2 분기 기준 자동 판정**: 신규 브랜치는 **호출 위치의 현재 HEAD** 에서 분기한다. 워크트리 A (feature-a) 안에서 호출하면 feature-a 의 현재 커밋이 시작점이 된다. 베이스 브랜치를 매번 묻지 않는다 (자동). 단, 사용자가 메시지에서 베이스를 명시하면 (예: "dev 기준으로") 그 브랜치를 시작점으로 쓴다.
- **FR-3 분기 전 dirty 확인**: 호출 위치 워크트리에 커밋 안 된 변경이 있으면 사용자에게 알리고, "WIP 커밋 후 분기" / "마지막 커밋 시점 기준으로만 분기" 중 선택받는다. stash 로 변경을 넘기는 방식은 쓰지 않는다.
- **FR-4 생성 후 보고 확장**: 요약 보고에 새 워크트리 경로 + 브랜치명 + **분기 기준 커밋 해시**를 포함한다. 분기 베이스가 메인 브랜치가 아닌 feature 브랜치면, 머지 경로가 스택 구조 (새브랜치 → 베이스브랜치 → 메인브랜치) 임을 명시하고, 베이스가 메인에 리베이스되면 새 브랜치도 리베이스가 필요하다는 주의사항을 함께 출력한다.
- **FR-5 기존 동작 보존 (최우선)**: 메인 루트에서 호출해 메인 브랜치 (dev 등) 의 HEAD 에서 분기·생성하는 기존 기능은 그대로 잘 동작해야 한다. 로컬 빌드 환경 파일 자동 복사, `.gitignore` 에 `.worktrees/` 추가, Claude 메모리 폴더 심링크 훅 등 기존 동작도 메인 루트 기준으로 그대로 수행된다.
- **FR-6 E2E 검증 (구현 완료 후 필수)**: 구현이 끝나면 Bash 로 실제 임시 git 저장소를 만들어 엄격한 E2E 테스트를 돌린다. 최소 시나리오: (a) 메인 루트에서 신규 브랜치 생성 (기존 동작), (b) 워크트리 안에서 재분기 (신규 동작 — 중첩 없음 + 베이스 HEAD 일치 확인), (c) dirty 워크트리에서 분기 시 선택 분기 동작, (d) 기존 브랜치/원격 브랜치 attach 케이스.
- **FR-7 기존 생성 경로 스크립트·훅 검토**: 워크트리 생성 흐름이 사용하는 기존 스크립트와 훅 (메모리 심링크 훅 등) 이 워크트리 안 호출 케이스에서도 문제없이 동작하는지 검토하고, 문제 발견 시 함께 수정한다.

## 5. 범위 밖 (Out of Scope)

- stash 로 변경을 새 워크트리로 넘기는 방식 (사용자 명시 제외)
- `worktree-merge-back` 의 스택 머지 지원 (새브랜치 → 베이스 feature 브랜치로 내려보내는 머지) — 현재는 nested 케이스 명시 차단이 유지되며, 필요 시 별도 피처로 분리
- 저장소 루트의 형제 디렉토리 (`<repo>-<브랜치>`) 배치 방식 — js-super 컨벤션인 메인 루트 `.worktrees/` 배치를 유지하는 것으로 확정

## 6. 수용 기준 (Acceptance Criteria)

워크트리 A 안에서 `/worktree <새브랜치>` 호출 시: (1) 새 워크트리가 메인루트/.worktrees/<새브랜치> 에 생기고, (2) 분기 커밋이 A 의 현재 HEAD 와 같고, (3) A 가 dirty 면 WIP 커밋 / 커밋 시점 분기 선택지가 뜨고, (4) 보고에 분기 기준 커밋 해시와 스택 구조 주의사항이 포함된다. (5) 메인 루트에서 호출하면 기존과 동일하게 동작한다 (dev 등 메인 브랜치 HEAD 분기). (6) Bash E2E 테스트 (FR-6 시나리오 a~d) 가 모두 통과하고, (7) 기존 스크립트·훅 검토 결과가 보고된다.
