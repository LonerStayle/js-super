# 개발방향: understand-anything-command

> **다음 단계 안내**: 이 문서는 기술 설계서입니다 (아키텍처 / 컴포넌트 / 데이터 / 인터페이스 / 결정 / 위험 / 테스트 전략). `understand-anything-command-requirements.md` 를 기반으로 작성됩니다. 다음 단계 `understand-anything-command-implementation-plan.md` (단계별 계획) 의 입력이 됩니다 (`writing-plans` skill 또는 `/write-plan` 슬래시). 단계별 구현 task 는 여기 박지 마세요 — 그건 다음 산출물 (plan) 에 들어갑니다.

## 1. 아키텍처 개요

세 층으로 나뉜다. js-super 저장소에는 **얇은 진입점만** 남기고, 무거운 것(분석 엔진, 병합 스크립트, 보조 에이전트 프롬프트, 언어별 스니펫)은 전부 **원저장소의 버전 고정 사본**에서 가져온다. 사본은 최초 실행 때 한 번 준비해 두고 이후 재사용한다.

```
┌─ 1층: js-super 저장소 (커밋 대상) ──────────────────────────┐
│  commands/understand.md          ← 부트스트랩 + 원본 절차 참조 │
│  commands/understand-chat.md     ← 본문 인라인 (조회형)        │
│  commands/understand-diff.md     ← 본문 인라인 (조회형)        │
│  commands/understand-explain.md  ← 본문 인라인 (조회형)        │
│  commands/understand-onboard.md  ← 본문 인라인 (조회형)        │
└──────────────────────────────────────────────────────────┘
                │ 최초 실행 시 1회 준비 (버전 고정 clone + 빌드)
                ▼
┌─ 2층: 엔진 사본 (사용자 홈, ~/.understand-anything-plugin) ──┐
│  원저장소 v2.9.4 전체 — 오케스트레이션 본문, 보조 에이전트     │
│  프롬프트 (전체 10종 중 이번 범위 사용 6종), Node/Python       │
│  스크립트, 언어·프레임워크·로케일 스니펫, core 빌드 산출물      │
└──────────────────────────────────────────────────────────┘
                │ 분석 실행 (7단계 파이프라인)
                ▼
┌─ 3층: 대상 프로젝트 산출물 (.ua/) ──────────────────────────┐
│  knowledge-graph.json / meta.json / config.json /           │
│  fingerprints.json / .understandignore                      │
└──────────────────────────────────────────────────────────┘
                │ 확인
                ▼
        원본 릴리즈의 완성 viewer (버전 고정, 로컬 서버)
```

`/understand` 의 실행 흐름: 먼저 엔진 사본이 준비돼 있는지 확인하고 없으면 만든다(부트스트랩). 그다음 사본 안의 원본 오케스트레이션 본문을 읽어 그대로 따르되, js-super 환경에 맞는 **덮어쓰기 조항**을 적용한다. 덮어쓰기 조항은 §5 의 D-3(경로 고정) · D-5(사용자 접점) · D-6(워크트리) · D-7(viewer) 에서 파생되며, 구현계획서가 이를 다섯 항목으로 펼쳐 표로 고정한다. 그래프가 완성되면 원본의 대시보드 자동 호출 대신 viewer 실행 방법을 안내한다.

조회형 4종은 엔진이 필요 없다 — 이미 만들어진 그래프 파일을 부분 검색으로 읽어 답하기만 하므로, 원본 본문(각 70~85줄)을 커맨드에 인라인으로 이식한다. 엔진 사본이 없는 머신에서도 그래프 파일만 있으면 동작한다.

## 3. 데이터 모델/스키마 변경

**새로 정의하는 스키마는 없다.** 산출물 형식은 원본 v2.9.4 의 그래프 스키마(노드 13종 / 엣지 26종 / 레이어 / 투어)를 그대로 쓴다 — viewer 호환(FR-5)이 걸려 있어 필드 하나도 바꾸지 않는다.

저장 위치와 구조 (모두 원본 규약 그대로):

| 위치 | 내용 | 수명 |
|---|---|---|
| `<대상 프로젝트>/.ua/` | `knowledge-graph.json`(최종 산출물), `meta.json`(분석 시점·커밋), `config.json`(언어 설정 등), `fingerprints.json`(증분용 지문), `.understandignore`(분석 제외 목록) | 커밋 권장 (제외 목록 포함) |
| `<대상 프로젝트>/.ua/intermediate/`, `.ua/tmp/` | 파이프라인 중간 파일 | 로컬 스크래치 (gitignore 안내) |
| `~/.understand-anything-plugin/` | 엔진 사본 (원저장소 v2.9.4 + 빌드 산출물) | 머신당 1회 설치, 재사용 |

워크트리에서 실행하면 `.ua/` 는 기본적으로 메인 저장소 루트에 만들어진다(FR-6, 원본 동작 유지). 현재 위치에 만들고 싶으면 `--here` 플래그를 쓴다.

## 4. 외부 인터페이스

이 피처가 **노출하는** 인터페이스는 없다 (API·이벤트·MCP 없음). **소비하는** 외부 자원은 셋이다:

| 자원 | 시점 | 실패 시 |
|---|---|---|
| 원저장소 clone: `https://github.com/Egonex-AI/Understand-Anything.git` (태그 `v2.9.4` 고정) | 엔진 사본 최초 준비 1회 | 안내 후 중단 — 그래프 생성 불가 |
| viewer 압축본: `https://github.com/Egonex-AI/Understand-Anything/releases/download/v2.9.4/understand-anything-viewer.tgz` (npx 실행) | 그래프 확인 시 | 안내만 — 그래프 생성은 이미 완료, 차선(HTML 리포트)은 별건 |
| 로컬 viewer 서버 (`127.0.0.1`, 토큰 포함 URL) | viewer 실행 중 | 기동 실패 시 안내 후 종료 — 그래프는 이미 생성돼 있어 손실 없음 |

viewer 서버가 정상 기동하면 출력에 나오는 **토큰 포함 URL 을 사용자에게 반드시 전달**한다 — 누락하면 접근이 차단된다 (정상 동작 요건, 실패 처리가 아님).

원본에 있던 Figma 연동(외부 API + 토큰)은 범위 밖이라 이 목록에 없다.

## 5. 핵심 결정 + 대안 비교

**D-1. `/understand` 본문 = 부트스트랩 + 원본 절차 참조 (전체 재작성 아님).**
원본 오케스트레이션 본문(858줄)을 js-super 커맨드에 통째로 옮겨 적지 않는다. 커맨드는 (1) 엔진 사본 확보, (2) 사본 안의 원본 본문을 읽고 따르라는 지시, (3) 덮어쓰기 조항 목록만 담는다.
- 대안 A(전체 인라인 재작성): 원본과의 drift 가 생기고, 원본 개정 때마다 858줄을 다시 맞춰야 한다. 버림.
- 채택 이유: 사본이 버전 고정이라 참조 대상이 불변 — drift 0, 커맨드 본문 약 150줄 수준 유지.
- 깨지는 조건: 사본이 없으면 실행 자체가 불가 → 부트스트랩을 본문 최상단 선행 단계로 강제해 해소.

**D-2. 조회형 4종 = 본문 인라인.**
- 대안(원본 참조 방식 통일): 엔진 사본이 없으면 조회도 못 하게 된다. 조회는 그래프 파일만 있으면 되는 가벼운 작업이라 사본 의존을 걸 이유가 없다. 버림.
- 채택 이유: 각 70~85줄로 작고, 인라인이면 그래프만 공유받은 머신(사본 없음)에서도 동작한다. 원본에 있던 최신성 검사 블록의 중복(4곳)은 원본 diff 추적을 쉽게 하려고 그대로 둔다.

**D-3. 엔진 사본 위치 = `~/.understand-anything-plugin` + 기준 경로 고정.**
원저장소는 저장소 루트 아래에 플러그인 폴더가 한 겹 더 있는 구조다. 저장소를 통째로 받으면 실제 플러그인은 그 한 겹 안쪽에 놓인다. 원본이 설치 경로를 스스로 찾는 로직은 플러그인이 최상위에 놓인 배치를 전제하므로, 이 배치에서는 맞지 않는다. 따라서 **탐색에 기대지 않고 기준 경로를 직접 고정한다**.
- 대안(원본 탐색 로직에 맡기기): 사본 배치가 원본 전제와 달라 못 찾는다. 배치를 원본 전제에 맞추려면 받은 뒤 폴더를 옮기거나 링크를 걸어야 하는데, 그 조작이 오히려 실패 지점을 늘린다. 버림.
- 채택 이유: 경로를 한 줄로 고정하면 탐색 결과에 흔들리지 않고, 덮어쓰기 조항도 그 한 줄로 끝난다. 이미 존재하면 버전을 확인하고, 고정 버전과 다르면 사용자 확인 후 재설치한다. **재설치를 거부하면 중단한다** — 불일치 사본으로 진행하지 않는다 (R-2 의 스키마 어긋남 위험을 안고 갈 이유가 없음).
- 빌드 절차는 새로 정의하지 않는다 — 원본 본문의 사전 준비 단계가 정의한 명령(`pnpm install` + core 패키지 빌드)을 그대로 쓴다. 정확한 호출 줄은 구현계획서에서 원본 본문을 인용해 확정한다.

**D-4. 보조 에이전트 = 사본의 프롬프트 파일을 읽어 범용 보조 에이전트로 호출.**
원본에는 보조 에이전트 정의가 전체 10종 있고, 이번 이식 범위(메인 파이프라인)가 쓰는 것은 그중 6종(스캔 / 파일 분석 / 병합 복구 / 아키텍처 / 투어 / 검토)이다.
- 대안(js-super `agents/` 에 원본 정의 등록): 등록형 에이전트 목록은 매 세션 컨텍스트에 상주한다 — "무거워서 커맨드로" 라는 이식 취지 정면 위배. 버림.
- 채택 이유: 원본 프롬프트를 사본에서 그대로 읽어 쓰므로 내용 복제도 없다. 병렬 상한(동시 5개) 등 원본 규약은 프롬프트에 이미 들어 있다.

**D-5. 사용자 접점 = js-super 규약 덮어쓰기 (FR-7, FR-9).**
원본의 확인 대기 지점(분석 제외 목록 확인, 대규모 프로젝트 범위 조정, 출력 언어 확인)은 원본에선 산문 질문이다. js-super 규약(알람 발화)에 맞춰 AskUserQuestion 도구 호출로 바꾸는 덮어쓰기 조항을 둔다. 확인 지점의 **개수와 위치는 원본 그대로** — 새 게이트를 만들지 않는다.
같은 조항에 **안내문 톤**도 포함한다: 진행 보고·확인 질문·종료 요약 등 사용자에게 보이는 문장은 한국어 친화 톤(짧은 문장, 영어 식별자 최소)으로 낸다. 조회형 4종의 인라인 본문에도 같은 톤 지침을 한 줄씩 박는다. 그래프 **내용**(요약·레이어명)의 언어는 원본의 자동 감지·설정 저장 동작을 그대로 둔다 — 안내문 톤과 산출물 언어는 별개 축이다.

**D-6. 워크트리 = 원본 리다이렉트 유지 + `--here` 플래그 (FR-6).**
원본은 환경변수로 리다이렉트를 끈다. 사용자 접점을 플래그로 통일하고, 내부적으로 그 환경변수를 세팅하는 방식으로 원본 절차를 건드리지 않는다.

**D-7. 그래프 확인 = viewer 안내로 대체 (FR-5).**
원본은 파이프라인 끝에서 자체 대시보드 명령을 자동 호출한다. 그 명령은 이식하지 않으므로, 종료 보고에서 버전 고정 viewer 실행 한 줄(npx + 릴리즈 URL + 대상 경로)을 안내하는 것으로 대체한다. 자동 실행이 아니라 안내인 이유: 로컬 서버 기동은 사용자가 원할 때만.

**D-8. 훅 없음 (요구사항 범위 밖 확정 반영).**
원본의 커밋 감지 자동 갱신 훅은 가져오지 않는다. 증분 갱신은 `/understand` 재실행으로만.

| R-4 | 병렬 분석 결과 파일 이름 규약 위반 시 병합에서 조용히 유실 | race | 원본 프롬프트의 이름 규약을 무수정으로 따름 (규약 자체가 완화책) — 덮어쓰기 조항에서 이 부분은 건드리지 않는다고 명시 |

| R-6 | 커맨드 이름이 원본 플러그인과 동일 — 동시 설치 시 충돌 | breaking | 요구사항 범위 밖에 명시 (동시 설치 비전제) + README 에 한 줄 안내 |

## 7. 테스트 전략

코드 로직이 아니라 커맨드 본문(instruction)이 산출물이므로, js-super 관례대로 **정적 회귀 검사 + 시나리오 fixture + 실전 dogfood** 3단으로 간다.

**(1) 정적 회귀 catch grep** — CLAUDE.md 결합 메모에 박아 릴리즈 전 실행:

```bash
# 5 커맨드 존재 + 명시 호출 전용 플래그
grep -lF "disable-model-invocation: true" \
  commands/understand.md commands/understand-chat.md commands/understand-diff.md \
  commands/understand-explain.md commands/understand-onboard.md
# expected: 5 lines

# 커맨드 ↔ 스킬 이름 충돌 없음
ls -d skills/understand* 2>/dev/null
# expected: (없음)

# 버전 고정 문자열 존재 (엔진 clone 태그 + viewer URL)
grep -c "v2.9.4" commands/understand.md
# expected: 2 이상

# 훅 미도입 (범위 밖 유지)
grep -rn "understand" hooks/ | grep -v Binary
# expected: 0
```

**(2) 시나리오 fixture** — `commands/understand-tests/H-e2e/README.md` 에 사람이 돌리는 검증 시나리오를 적는다: 소형 샘플 저장소 준비 → `/understand` 실행 → 부트스트랩·규모 보고·그래프 생성 확인 → 조회형 4종 각 1회 → viewer 안내 확인 → 재실행(증분 경로) 확인.

**(3) 실전 dogfood** — js-super 저장소 자신을 대상으로 `/understand` 1회 완주 + 워크트리 안에서 실행해 메인 루트 저장(FR-6)과 `--here` 를 각각 확인.

엔진·병합 스크립트 자체의 단위 테스트는 만들지 않는다 — 원본 사본을 무수정으로 쓰므로 원본의 품질을 그대로 신뢰하고, 우리 검증 대상은 "이식 층"(커맨드 본문과 덮어쓰기 조항)에 한정한다.
