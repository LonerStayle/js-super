# 기술설계: 에픽 단위 브레인스토밍

> **다음 단계 안내**: 이 문서는 기술 설계서입니다. 다음 단계로 `writing-plans` skill (또는 `/write-plan` 슬래시) 을 호출해서 `<slug>-implementation-plan.md` 를 만드세요.

## 1. 아키텍처 개요

큰 작업 하나를 여러 번의 브레인스토밍으로 나눠 진행할 때, 그 사이를 잇는 것은 대화가 아니라 파일이다. 이 설계는 세 겹으로 나뉜다. 사용자가 부르는 진입점, 브레인스토밍 흐름 안에 끼어드는 두 단계, 그리고 진행 상태를 세는 계산 부분이다.

```
┌─ ① 사용자 진입 ──────────────────────────────────────┐
│   /epic          큰 작업 만들기 · 상태 조회 · 종료 표시 │
│   /brainstorm    피처 대화 (기존 커맨드, 변경 없음)     │
└──────────────────────┬───────────────────────────────┘
                       │
┌─ ② 브레인스토밍 흐름 ─▼───────────────────────────────┐
│   시작 단계    큰 그림과 미해소 이월 항목을 읽어 보여줌  │
│   (기존 대화 절차 — 변경 없음)                         │
│   마무리 단계  갱신 판정 · 이월 기록 · 예상 빗나감 판정  │
└──────────────────────┬───────────────────────────────┘
                       │ 진행 상태가 필요할 때
┌─ ③ 상태 계산 ────────▼───────────────────────────────┐
│   소속 표식으로 피처 폴더를 모으고 산출물로 단계 판정    │
└──────────────────────┬───────────────────────────────┘
                       │
┌─ ④ 저장소 ───────────▼───────────────────────────────┐
│   docs/epics/<날짜>-<slug>/                           │
│      overview.md      큰 그림                         │
│      carry-over.md    이월 노트                        │
│      forecast.md      예상도                          │
│                                                       │
│   docs/features/<날짜>-<slug>/                        │
│      <slug>-requirements.md   머리에 소속 한 줄        │
│      <slug>-tech-design.md                            │
│      <slug>-implementation-plan.md                    │
└───────────────────────────────────────────────────────┘
```

| 번호 | 하는 일 |
|---|---|
| ① | 사용자가 직접 부르는 자리. 큰 작업을 만들고, 상태를 보고, 끝났다고 표시한다 |
| ② | 기존 브레인스토밍 절차의 앞뒤에 붙는다. 가운데 대화 절차는 손대지 않는다 |
| ③ | 저장된 진행 표시를 읽지 않고 매번 센다 |
| ④ | 큰 작업 폴더는 피처 폴더와 나란히 놓인다. 어느 쪽도 다른 쪽 안에 들어가지 않는다 |

②의 두 단계는 큰 작업 폴더가 없으면 통째로 건너뛴다. 큰 작업 없이 피처 하나만 만드는 기존 사용법이 지금과 똑같이 동작해야 하기 때문이다 (요구 16).

## 5. 핵심 결정 + 대안 비교

### 큰 작업 폴더를 피처 폴더와 나란히 둔다

| 안 | 무엇이 달라지나 | 무엇을 포기하나 |
|---|---|---|
| 채택 — `docs/epics/` | 피처 폴더와 대칭이고 사용자가 찾기 쉽다. git 이력에 남는다 | 새 최상위 폴더가 하나 늘어난다 |
| 피처 폴더 안에 넣기 | 폴더가 안 늘어난다 | 피처 폴더를 순회하는 기존 로직들이 예외 처리를 해야 한다 |
| git 밖에 두기 | 워크트리 사이 공유가 쉬워진다 | 이력이 안 남고 다른 컴퓨터에서 사라진다 |

세 번째 안은 워크트리 문제를 풀려던 것인데, 자식 워크트리가 부모에서 갈라지며 파일을 물려받는 구조로 정해지면서 풀 문제 자체가 없어졌다.

### 소속은 요구사항 문서 머리의 인용 한 줄로 표시한다

| 안 | 무엇이 달라지나 | 무엇을 포기하나 |
|---|---|---|
| 채택 — 인용 한 줄 | 요구사항 문서 머리에 이미 다음 단계 안내 인용이 있어 자리가 있다. 소속이 바뀌면 한 줄만 고친다 | 정확한 문자열 형식을 지켜야 읽힌다 |
| 문서 머리 설정 블록 | 기계가 읽기 가장 정확하다 | 요구사항 문서에는 그 블록을 쓰지 않는 관례가 있다. 기술설계서만 쓴다 |
| 폴더 이름에 접두어 | 폴더 목록만 봐도 소속이 보인다 | 소속이나 큰 작업 이름이 바뀌면 폴더와 그 안 파일을 전부 다시 이름 붙여야 한다 |

### 진행 상태는 스크립트가 세고 큰 그림 갱신은 사람 판단이 한다

두 가지 판정의 성격이 다르다.

| 판정 | 누가 | 왜 |
|---|---|---|
| 피처가 어느 단계까지 왔나 | 스크립트 | 파일이 있는지 없는지라 흔들릴 여지가 없다 |
| 큰 그림을 고쳐야 하나 | 대화 중 판단 | 항목이 없어졌는지 새로 생겼는지는 내용을 읽어야 안다 |

진행 표시를 파일에 적어두고 갱신하는 방식을 버린 이유는 갱신을 규칙으로 정해두면 언젠가 빠지고, 그때부터 적힌 것과 실제가 어긋나기 때문이다. 이 저장소는 계획서에 코드를 싣는 규칙을 사람 준수에 맡겼다가 같은 방식으로 무너진 적이 있다.

### 브레인스토밍 흐름의 앞뒤에만 붙인다

가운데 대화 절차는 한 줄도 건드리지 않는다. 붙는 자리는 둘이다.

```
Entry Router
     ↓
[시작 단계]  ← 여기            큰 그림과 이월 항목을 읽는다
     ↓
컨텍스트 탐색 → 이름 확인 → 대화 → 문서 작성 → 자체 점검 → 승인
     ↓
변경이력 기록
     ↓
[마무리 단계]  ← 여기          갱신 판정 · 이월 기록 · 예상 판정
     ↓
기술설계 단계로
```

시작 단계를 컨텍스트 탐색보다 앞에 두는 이유는 큰 그림을 먼저 읽어야 그 위에서 대화가 시작되기 때문이다. 뒤에 두면 이미 잡힌 방향에 나중에 맥락을 끼워 넣게 된다.

시작 단계가 읽는 파일은 큰 그림과 이월 노트 둘뿐이다. 예상도는 읽지 않는다 (요구 11). 읽어서 대화에 들어오면 다음 주제가 결국 그 예상을 따라가고, 예상도를 따로 떼어낸 이유가 사라진다. 예상도는 마무리 단계에서 빗나감을 적을 때와 사용자가 직접 열어볼 때만 쓰인다.

마무리 단계를 변경이력 기록 뒤에 두는 이유는 이월 항목을 적을 때 방금 만든 피처 문서를 가리켜야 하는데, 그러려면 문서가 확정돼 있어야 하기 때문이다.

### 진행 중인 큰 작업이 여럿일 때는 가장 최근에 손댄 것을 쓴다

한 워크트리에 큰 작업은 보통 하나지만, 끝난 큰 작업의 폴더가 계속 쌓인다. 끝났는지는 사람이 정하므로 (요구 12) 큰 그림 문서에 상태를 적는다.

| 상황 | 동작 |
|---|---|
| 진행 중인 것이 없음 | 시작 단계와 마무리 단계를 건너뛴다 |
| 진행 중인 것이 하나 | 그것을 쓴다 |
| 진행 중인 것이 여럿 | 가장 최근에 갱신된 것을 쓰고 그 사실을 한 줄 알린다 |

여럿일 때 사용자에게 묻는 방식은 버렸다. 대부분의 경우 하나뿐인데 질문이 상시로 끼어들면 큰 작업을 안 쓰는 사용자까지 마찰을 겪는다.

### 워크트리는 제안만 하고 만들지 않는다

피처 브레인스토밍을 그 피처 전용 워크트리에서 진행한다는 것 (요구 13) 은 사용자의 작업 방식이지 이 기능이 강제하는 절차가 아니다. 마무리 단계에서 다음 주제를 고를 때 어느 워크트리를 부모로 삼을지 알려주는 데까지가 범위다.

| 다음 피처가 | 부모로 삼을 곳 |
|---|---|
| 방금 끝낸 피처의 결과에 기댐 | 방금 끝낸 피처의 워크트리 |
| 방금 끝낸 것과 무관하고 더 앞선 무언가에 기댐 | 그 앞선 피처의 워크트리 |
| 아무것에도 안 기댐 | 큰 작업 워크트리 |

실제 생성은 사용자가 기존 워크트리 커맨드로 한다. 부모 기록도 그 커맨드가 남긴다. 이 기능이 워크트리를 직접 만들면 만들기와 되돌리기를 모두 떠안게 되고, 이미 잘 도는 기능과 절차가 둘로 갈린다.

세 파일이 부모에서 자식으로 물려오는 것 (요구 18) 은 새로 만들 동작이 아니다. 자식 워크트리는 부모의 마지막 커밋에서 갈라지므로 그 시점의 파일을 그대로 갖는다. 설계에서 할 일은 이 성질이 깨지지 않게 하는 것뿐이다 — 세 파일을 git 밖에 두거나 워크트리마다 따로 만들면 상속이 성립하지 않는다.

### 병렬 제안은 대화 내용만 근거로 한다

착수 가능한 피처가 둘 이상일 때 서로 건드리는 곳이 겹치는지는 대화에서 나온 내용으로 판단한다. 코드를 뒤져 실제 파일 충돌을 계산하지 않는다.

제안은 말로 하는 데까지이고 워크트리를 실제로 만들지는 않는다. 만드는 일은 기존 워크트리 커맨드가 한다.

### 이월 노트와 예상도는 뒤에 붙이기만 한다

형제 워크트리로 갈라져 양쪽에서 같은 파일에 적으면 되돌려 합칠 때 만난다. 뒤에 붙이기만 하는 파일은 서로 다른 줄에 쌓이므로 대체로 자동으로 합쳐진다. 중간을 고쳐 쓰는 파일은 같은 자리를 양쪽이 건드려 충돌이 난다.

큰 그림은 고쳐 쓰는 파일이라 이 보호를 못 받는다. 다만 갱신은 브레인스토밍이 끝나는 시점에만 일어나고, 형제로 동시에 진행하는 경우는 드물다. 충돌이 나면 사용자가 합친다.

## 6. 위험/사이드이펙트

| 위험 | 어떤 일이 벌어지나 | 대응 |
|---|---|---|
| 브레인스토밍 스킬이 커짐 | 이 스킬은 매 세션 컨텍스트에 상주한다. 지금도 488줄인데 더 늘면 상주 비용이 커진다 | 두 단계를 짧게 쓰고 자세한 규칙은 커맨드 본문에 둔다 |
| 큰 작업을 안 쓰는 사용자에게 마찰 | 시작 단계가 매번 돌면서 아무것도 없는 폴더를 뒤진다 | 폴더 존재 확인 한 번으로 빠져나간다. 안내 문구도 출력하지 않는다 |
| 소속 표식 형식이 어긋남 | 표식을 못 읽으면 그 피처가 목록에서 빠진다. 조용히 빠져서 눈치채기 어렵다 | 스캔 결과에 표식 없는 피처 수를 함께 보고한다 |
| 형제 워크트리에서 큰 그림 충돌 | 되돌려 합칠 때 같은 자리를 양쪽이 고쳐 충돌 | 이월 노트와 예상도는 붙이기만 해서 영향이 없다. 큰 그림만 사람이 합친다 |
| 새 최상위 폴더 강요 | 사용자 프로젝트에 안 쓰던 폴더가 생긴다 | 큰 작업을 실제로 시작할 때만 만든다. 안 쓰면 안 생긴다 |
| 갱신 판정이 느슨해짐 | 바뀐 게 없는데 문구만 다듬어 매번 파일이 변한다 | 새로 붙이는 항목에 근거를 함께 적게 하고, 근거를 못 적으면 적지 않는다 |

## 7. 테스트 전략

| 대상 | 방법 |
|---|---|
| 소속 피처 수집과 단계 판정 | 임시 폴더에 여러 모양의 피처 폴더를 만들어 놓고 함수를 직접 부르는 단위 테스트 |
| 표식이 없거나 형식이 어긋난 피처 | 같은 단위 테스트에서 별도 항목으로 세는지 확인 |
| 큰 작업이 없을 때 브레인스토밍 | 사람이 돌리는 시나리오. 시작 단계 안내가 전혀 안 나오는지 본다 |
| 큰 그림 갱신 판정 | 사람이 돌리는 시나리오. 바뀐 게 없는 경우에 파일이 안 변하는지 본다 |
| 커맨드 본문 규약 | 이 저장소의 결합 규칙 검사에 확인 명령을 추가한다 |

단계 판정은 파일 존재 여부라 결정적이므로 단위 테스트로 덮인다. 갱신 판정과 병렬 제안은 대화 판단이라 자동 검사가 불가능하고, 사람이 돌리는 시나리오 문서로 남긴다.
