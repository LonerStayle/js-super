# 요구사항: 에픽 단위 브레인스토밍

> **다음 단계 안내**: 이 문서는 요구사항 (기획 단계) 입니다. 다음 단계로 `tech-design` skill (또는 `/design-tech` 슬래시) 을 호출해서 `<slug>-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요 — 그건 다음 산출물 (tech-design, 3개 트랙이면 plan 까지) 에 들어갑니다.

## 배경

한 번의 브레인스토밍으로 감당이 안 되는 규모의 일이 있다. 이런 일은 서너 번으로 나눠 진행하는데, 그때마다 큰 그림을 담은 문서를 즉석에서 만들고 진행 상황을 표시하게 지시해야 했다. 매번 사람이 직접 시켜야 했고, 무엇을 만들지도 그때그때 달랐다.

이 문서에서는 그렇게 나눠 진행하는 일 하나를 **큰 작업** 이라 부른다. 큰 작업 하나가 여러 번의 브레인스토밍으로 쪼개지고, 브레인스토밍 하나가 피처 폴더 하나를 만든다.

지금 구조로는 두 가지가 막힌다.

첫째, 계층이 없다. `docs/features/` 아래에는 피처 폴더만 평평하게 쌓인다. 같은 날 폴더가 다섯 개 생겨도 그중 셋이 한 작업이었는지 다섯이 다 별개였는지 폴더만 봐서는 알 수 없다.

둘째, 대화가 압축된다. 피처 하나를 끝내고 다음으로 넘어갈 때 `/compact` 로 대화를 요약하는데, 앞에서 정한 것과 미룬 것과 주의사항이 요약에 안 남거나 뭉개진다. 압축을 견디는 것은 파일뿐이다.

## 핵심 결정

### 큰 그림은 계획서가 아니라 현재 상태 기록

시작 시점에 할 일 목록과 순서를 확정하고 그 목록을 소진하는 방식을 버렸다. 실제로 서너 번 도는 동안 목록은 계속 바뀌었다. 무엇을 할지는 앞 브레인스토밍이 끝나봐야 알 수 있다.

대신 매 시점의 상태를 적는다. 무엇을 이루려는지, 지금까지 무엇이 정해졌는지, 지금 착수할 수 있는 것은 무엇이고 무엇을 기다리는지, 아직 모르는 것은 무엇인지.

### 파일을 셋으로 나눔

| 파일 | 담는 것 | 쓰는 방식 |
|---|---|---|
| 큰 그림 | 목표, 정해진 것, 착수 가능, 기다림, 모르는 것 | 고쳐 씀 |
| 이월 노트 | 미룬 것, 주의사항, 기각한 안, 유보한 것 | 뒤에 붙이기만 |
| 예상도 | 시점별 예상과 빗나간 기록 | 뒤에 붙이기만 |

하나의 문서에 다 담는 방식을 버렸다. 서너 번 쌓이면 문서가 커지고, 커진 문서에서 내용이 생략되는 문제가 이 저장소에서 이미 관찰됐다.

이월 노트와 예상도를 뒤에 붙이기만 하는 방식으로 두는 이유는 읽고 고치는 갱신이 언젠가 빠뜨리기 때문이다. 해소된 항목도 지우지 않고 해소 표시만 덧붙인다.

### 피처마다 워크트리를 만들고 의존에 따라 잇는다

큰 작업 워크트리를 부모로 삼아 피처마다 워크트리를 만든다. 앞 피처의 결과가 있어야 다음이 가능하면 그 피처의 워크트리를 부모로 삼아 이어 붙이고, 서로 독립이면 같은 부모에서 나란히 갈라낸다.

```
큰 작업 워크트리
  └─ 피처1
       ├─ 피처2      피처1 이 있어야 가능
       └─ 피처3      피처1 이 있어야 가능. 피처2 와는 독립이라 나란히
```

자식 워크트리는 부모의 마지막 커밋에서 갈라지므로 세 파일이 그대로 물려온다. 피처1 에서 큰 그림을 갱신해 커밋하면 피처2 워크트리를 만들 때 갱신된 내용을 받는다. 형제로 갈라낸 경우에만 각자 갱신한 내용이 갈리고, 이때는 되돌아 합칠 때 만난다.

한 워크트리에서 대화를 압축하며 순차로 진행하는 방식을 버렸다. 압축 요약이 앞 내용을 왜곡하고, 여러 피처가 한 브랜치에 섞여 되돌리기 어려우며, 병렬이 아예 불가능하다. 지금 만드는 세 파일이 맥락을 나르므로 대화를 끊어도 앞 내용이 사라지지 않는다.

서로 무관한 큰 작업 둘은 각각 별도의 큰 작업 워크트리에서 돈다. 어느 피처 워크트리에서든 부모를 거슬러 올라가면 큰 작업이 하나로 정해지므로, 브레인스토밍을 시작할 때 소속을 고를 일이 없다.

### 진행 상태는 저장하지 않고 계산

큰 그림에 진행 표시를 적어두는 방식을 버렸다. 표시를 갱신하라고 정해두면 몇 번은 지키다가 언젠가 빠지고, 그때부터 문서와 실제가 어긋난다.

대신 피처 폴더에 어떤 산출물이 있는지 세어 단계를 판정한다.

| 폴더에 있는 것 | 판정 |
|---|---|
| 요구사항서만 | 기획 완료 |
| 기술설계서까지 | 설계 완료 |
| 구현계획서까지 | 계획 완료 |
| 변경이력에 코드 수정 기록 | 실행 완료 |

### 이월 노트는 대기열이 아니라 보관함

미뤄둔 항목을 순서대로 꺼내 쓰는 것이 아니다. 다음 브레인스토밍에서 지금 처리하는 편이 낫다고 판단되면 언제든 앞당겨 꺼낼 수 있다.

### 예상이 빗나가는 것은 정상

예상도를 갱신할 때 옛 예상을 덮어쓰지 않고, 무엇이 어떻게 빗나갔는지를 근거와 함께 아래에 덧붙인다. 빗나간 기록이 쌓이면 예상도가 따라가야 할 계획이 아니라 지나온 기록이 된다.

예상도는 다음 주제를 고를 때 참조하지 않는다. 참조하면 결국 그 순서를 따라가게 된다.

### 기존 브레인스토밍 흐름에 얹음

큰 작업 전용 대화 절차를 따로 만드는 방식을 버렸다. 같은 대화를 두 벌 유지해야 하고, 매번 어느 쪽을 쓸지 판단해야 한다.

큰 작업을 시작하는 진입점 하나만 새로 두고, 나머지는 기존 브레인스토밍 흐름에 시작 단계와 마무리 단계를 더한다.

## 파일 배치

```
저장소
│
├─ 큰 작업 폴더
│   ├─ 큰 그림       목표 · 정해진 것 · 착수 가능 · 기다림 · 모르는 것
│   ├─ 이월 노트     미룬 것 · 주의사항 · 기각한 안 · 유보
│   └─ 예상도        시점별 예상과 빗나감
│
└─ docs/features/
    ├─ 날짜-피처1/    요구사항 · 기술설계 · 구현계획
    ├─ 날짜-피처2/
    └─ 날짜-피처3/
```

피처 폴더는 지금 위치에 그대로 둔다. 큰 작업 폴더 안으로 옮기지 않는다.

이 배치는 큰 작업 워크트리와 그 아래 모든 피처 워크트리에 똑같이 나타난다. 자식이 부모에서 갈라져 나오기 때문이다.

## 진행 흐름

```
큰 작업 시작 → 큰 그림 초안 (아는 만큼만)
       │
       ▼
 ┌──→ 브레인스토밍 시작
 │        ① 큰 그림과 이월 노트 미해소 항목을 읽어 보여줌
 │        ▼
 │     대화 → 요구사항 → 기술설계 → 구현계획 → 실행
 │        │
 │        ▼
 │     브레인스토밍 마무리
 │        ② 큰 그림 갱신 판정
 │        ③ 이월 항목 기록
 │        ④ 예상 빗나감 판정
 │        │
 └────────┘  다음 주제는 갱신된 상태를 보고 그때 고름
```

| 번호 | 하는 일 |
|---|---|
| ① | 압축된 대화 대신 파일에서 읽어온다. 이월 항목은 지금 앞당길지 판단하는 데 쓴다 |
| ② | 바뀐 게 없으면 파일을 고치지 않는다 |
| ③ | 대화 중 나온 항목을 모아 보여주고 남길 것만 기록한다 |
| ④ | 예상이 빗나갔을 때만 근거와 함께 덧붙인다 |

## 요구 항목

**요구 1**: 큰 작업을 시작하는 진입점이 있어야 한다. 대화를 거쳐 큰 그림 문서를 만든다.

**요구 2**: 큰 작업을 시작하는 대화는 목표와 경계까지만 묻고 끝낸다. 각 피처의 세부 요구사항, 기술 선택, 전체 순서 확정은 묻지 않는다.

**요구 3**: 큰 그림에는 목표, 지금까지 정해진 것, 지금 착수할 수 있는 것, 무엇을 기다리는 것, 아직 모르는 것을 담는다. 확정된 할 일 목록과 순서는 담지 않는다. 착수 가능과 기다림의 구분은 알게 된 시점에 채우며, 시작 시점에는 비어 있어도 된다.

**요구 4**: 브레인스토밍을 시작하면 그 워크트리의 큰 그림과 이월 노트의 미해소 항목을 읽어 사용자에게 먼저 보여준다.

**요구 5**: 브레인스토밍이 끝나면 큰 그림을 갱신할지 판정한다. 항목이 없어지거나 생기거나 순서가 뒤집힌 경우에만 고쳐 쓰고, 표현만 다듬는 수정은 하지 않는다. 바뀐 것이 없으면 파일을 고치지 않고 대화로만 알린다.

**요구 6**: 이월 노트는 미룬 것, 주의사항, 기각한 안, 유보한 것을 담는다. 항목마다 어느 브레인스토밍에서 나왔는지를 함께 적는다.

**요구 7**: 이월 노트는 뒤에 붙이기만 한다. 해소된 항목도 지우지 않고 해소 표시와 처리된 곳을 덧붙인다.

**요구 8**: 이월 항목은 순서대로 소진하는 대기열이 아니다. 타당하다고 판단되면 언제든 앞당겨 처리할 수 있다.

**요구 9**: 이월 항목은 브레인스토밍이 끝나는 시점에 파일에 기록한다. 대화 중에는 파일을 건드리지 않는다.

**요구 10**: 예상도는 시점별로 아래에 쌓는다. 옛 예상을 덮어쓰지 않고, 빗나간 내용과 그렇게 판단한 근거를 함께 적는다. 근거를 적을 수 없으면 기록하지 않는다.

**요구 11**: 예상도는 다음 주제를 고를 때 참조하지 않는다. 사용자가 직접 열어볼 때만 본다.

**요구 12**: 큰 작업이 끝났는지는 예상 항목이 다 소진됐는지로 판정하지 않는다. 사용자가 끝났다고 할 때 끝난다.

**요구 13**: 피처 브레인스토밍은 그 피처 전용 워크트리에서 진행한다. 앞 피처의 결과가 있어야 가능한 피처는 그 피처의 워크트리를 부모로 삼고, 독립인 피처는 같은 부모에서 나란히 갈라낸다.

**요구 14**: 큰 작업에 속한 피처의 진행 상태는 저장하지 않는다. 피처 폴더의 산출물 파일 존재로 판정한다.

**요구 15**: 큰 작업에 속한 피처 목록과 각 단계를 한 번에 조회할 수 있어야 한다.

**요구 16**: 큰 작업이 없는 상태에서도 기존 브레인스토밍은 지금과 똑같이 동작한다. 큰 작업 관련 질문이나 단계가 끼어들지 않는다.

**요구 17**: 착수할 수 있는 피처가 둘 이상이고 서로 건드리는 곳이 겹치지 않으면, 나란히 갈라내 동시에 진행하도록 제안한다.

**요구 18**: 큰 그림과 이월 노트와 예상도는 부모 워크트리에서 자식 워크트리로 물려온다. 자식에서 갱신한 내용은 부모로 되돌려 합칠 때 올라간다.

## 범위 밖

- 큰 작업 전용 커맨드 계열을 따로 만들지 않는다. 기존 브레인스토밍 흐름에 시작 단계와 마무리 단계를 더한다.
- 피처 폴더를 큰 작업 폴더 안으로 옮기지 않는다. 지금 경로 규약을 그대로 둔다.
- 이 저장소가 쓰는 `docs/backlog/` 관습을 플러그인 규약으로 가져오지 않는다. 다른 프로젝트에는 그 폴더가 없다.
- 이미 만들어진 피처 폴더에 소급 적용하지 않는다.
- 자동 진행 경로 (`auto-brainstorming` 계열) 에는 적용하지 않는다. 자동 경로는 사람 개입 없이 끝까지 도는 흐름이라 큰 작업 단위로 나눠 진행하는 상황과 맞지 않는다.
