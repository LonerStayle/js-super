# 요구사항: 무맥락 검증자 병렬

> **다음 단계 안내**: 이 문서는 PRD (기획 단계 요구사항만) 입니다. 다음 단계로 `tech-design` skill (또는 `/tech-design` 슬래시) 을 호출해서 `무맥락-검증자-병렬-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요 — 그건 다음 산출물 (tech-design, 3개 트랙이면 plan 까지) 에 들어갑니다.

## 1. 배경/목적

`verifying-spec` 은 `<slug>-tech-design.md` 와 `<slug>-implementation-plan.md` 가 만들어진 직후 도는 검증 게이트다. 그런데 이 검증을 수행하는 주체가 **방금 그 문서를 쓴 메인 에이전트 자신**이다. 브레인스토밍 대화 전체, 각 결정을 왜 그렇게 내렸는지, 어떤 대안을 왜 버렸는지를 전부 들고 있는 상태에서 자기 문서를 읽는다.

`skills/verifying-spec/SKILL.md:11` 의 보조 에이전트 금지 규칙은 이게 **의도된 설계**임을 명시한다 — "the user explicitly requires main-agent verification for context preservation". 맥락을 들고 있어야 정확하고 투명하다는 판단이었고, 그 판단 자체는 지금도 유효하다.

문제는 맥락이 정확도를 올리는 동시에 특정 실패를 가린다는 점이다. 이번 v2.9.0 E2E 검증에서 실행자의 보고서를 별도 검증자에게 넘겨 반박시켰을 때, 검증자가 실행자의 근거 인용 오류와 누락된 탐지 범위를 잡아냈다. 다만 그때도 검증자는 보고서를 받은 상태였다. 보고서를 아예 안 받은 검증자는 또 다른 각도를 볼 가능성이 크다.

이 피처는 메인의 맥락 보유 검증을 그대로 둔 채, **대화 이력이 전혀 없는 보조 에이전트 하나를 병렬로 더 세운다**. 두 결과를 메인이 합쳐 하나의 보고서로 낸다.

잡으려는 실패는 세 가지다.

- **해석 동조** — 작성자가 내린 요구사항 해석을 검증자가 그대로 수용한다. 무맥락 검증자는 그 해석을 모르니 상위 문서 원문만 보고 다시 판단한다.
- **검증 범위 축소** — 작성자가 의식한 부분만 검증 대상이 된다. 언급되지 않은 구멍은 애초에 시야 밖이다.
- **결과물 자체의 이상** — 상위 문서 대비 정합성과 무관하게 문서 자체가 이상한 경우. 모호한 지시, 미결정 사항, 내부 모순, 검증 불가능한 서술. 요구사항 대조만 하면 통과하지만 사람이 읽으면 이상한 것들이다.

## 2. 사용자 스토리 / 시나리오

해당 없음 — js-super 내부 워크플로우 확장이라 외부 사용자 스토리가 성립하지 않는다.

## 3. 기능 요구사항 (FR)

### FR-1: 무맥락 검증자 병렬 실행

`verifying-spec` 실행 시, 메인이 자체 검증(A 정합성 + C 코드 영향)을 수행하는 것과 **동시에** 맥락 없는 보조 에이전트를 백그라운드로 띄운다. 메인이 자기 검증을 끝낸 뒤에 순차로 부르는 것이 아니라 진짜 병렬이어야 한다.

보조 에이전트를 몇 개로 나눌지는 개발방향 단계에서 정한다. FR-3 의 읽기 순서를 어떤 방식으로 강제하느냐에 따라 갈리며, 어느 쪽이든 메인 자체 검증과 병렬이라는 점은 동일하다.

적용 시점은 `verifying-spec` 이 원래 도는 두 지점 모두다.

| 시점 | 대상 문서 | 상위 문서 |
|---|---|---|
| `tech-design` 종료 시 | `<slug>-tech-design.md` | `<slug>-requirements.md` |
| `writing-plans` 종료 시 | `<slug>-implementation-plan.md` | `<slug>-requirements.md`, `<slug>-tech-design.md` |

산출물 2개 트랙(tech-design frontmatter `depth: 2`)에서는 `verifying-spec` 자체가 첫 행만 실행되므로, 무맥락 검증자도 자연히 tech-design 시점에만 돈다. 별도 분기 불필요.

### FR-2: 무맥락의 경계 — 무엇을 주지 않는가

무맥락 검증자에게 다음을 **전달하지 않는다**.

- 브레인스토밍 / tech-design / writing-plans 대화 이력
- 메인 에이전트의 `verifying-spec` 자체 검증 보고서 (중간 결과 포함)
- 각 결정의 배경 서술, 버린 대안, "왜 이렇게 했는지" 설명
- 대상 문서의 `## 변경이력` footer 내용

전달하는 것은 **파일 경로와 판정 기준뿐**이다. 새 보조 에이전트는 대화 이력이 애초에 없으므로 무맥락은 기본값이고, 이 요구사항은 "편의상 맥락을 끼워넣는 것"을 금지하는 규칙이다.

### FR-3: 2단계 읽기 순서 강제

무맥락 검증자는 읽는 순서를 고정한다. 순서를 바꾸면 3번째 실패 유형(결과물 자체의 이상)을 못 잡는다.

- **1단계** — 대상 문서만 단독으로 읽는다. 상위 문서를 아직 열지 않은 상태에서 이 문서 자체의 문제를 먼저 적는다. 모호한 지시, 미결정으로 남은 부분, 내부 모순, 검증 불가능한 서술, 이 문서만으로 구현이 안 되는 지점.
- **2단계** — 그 다음에 상위 문서를 열어 정합을 판정한다. 누락과 모순.

1단계 결과는 2단계 진입 전에 확정한다. 2단계에서 상위 문서를 읽고 나서 1단계 지적을 철회하거나 수정하지 않는다.

### FR-4: 판정 축

무맥락 검증자는 메인이 보는 축을 **독립적으로 다시 판정하고**, 거기에 메인이 안 보는 축을 더한다.

- **재검 축** — 누락(상위 항목이 대상에 안 나타남), 모순(상위 제약을 대상이 뒤집음). 메인도 보는 축이지만 독립 판정이 대조의 근거가 된다.
- **새 축** — 문서 자체의 문제(FR-3 의 1단계 결과). 메인이 보지 않는 축.

두 축의 지적은 보고 시 구분되어야 한다. 뒤섞으면 FR-5 의 성격 분리가 불가능해진다.

### FR-5: 결과 통합과 중재

메인이 두 결과를 합쳐 **하나의 보고서**로 낸다. 사용자에게 두 개의 보고서를 따로 보여주지 않는다. 최종 `진행 / 수정` 게이트도 하나다.

판정이 엇갈릴 때 메인이 중재하되, 지적의 **성격에 따라 처리를 나눈다**.

| 지적 성격 | 처리 |
|---|---|
| 상위 문서 대비 누락 또는 모순 | 문서 수정 사유. 보고서에 수정 권고로 올린다 |
| 상위 문서와 무관한 문서 자체의 문제 | 수정 사유가 아니다. 보고서에 별도 항목으로 남기고 진행한다 |

메인이 무맥락 검증자의 지적을 기각할 경우, **기각 사유를 보고서에 남긴다**. 조용히 버리지 않는다. 기각 사유가 안 보이면 무맥락 검증자를 돌린 의미가 사라진다.

엇갈릴 때마다 사용자에게 묻지 않는다. 기존 위임 룰(보조 에이전트 모드 선택 = 진행 위임)과 일관되게, 메인이 판정하고 결과를 보고서에 반영한다.

### FR-6: 실행 게이팅

기본은 **켜짐**이다. 끄는 플래그를 제공한다.

- 플래그를 안 주면 무맥락 검증자가 돈다
- 끄는 플래그를 명시하면 메인 자체 검증만 돈다 (v2.9.0 이전 동작과 동일)
- 플래그 이름과 전달 경로(`/tech-design` / `/write-plan` 슬래시 인자)는 개발방향 단계에서 확정한다. 기존 `--no-ask` 플래그 패턴을 따르는 것이 자연스럽다

변경 규모나 복잡도로 메인이 알아서 켜고 끄는 조건부 자동 판정은 채택하지 않는다. 판정 기준이 틀리면 조용히 건너뛰는데, 건너뛴 사실이 사용자에게 안 보인다.

### FR-7: 모델

무맥락 검증자는 **메인 세션 모델을 그대로 상속**한다. 고정 모델 상수를 두지 않는다.

- 별도 모델 값을 명시하지 않는 방식으로 구현한다 (보조 에이전트 호출 시 모델 미지정 = 부모 상속)
- 세션 모델을 바꾸면 검증자도 따라 바뀐다
- 판정이 갈렸을 때 "모델 등급이 달라서"를 변명으로 쓸 수 없다

### FR-8: 기존 보조 에이전트 금지 규칙에 예외 명시

`skills/verifying-spec/SKILL.md` 의 HARD-GATE 는 현재 보조 에이전트 dispatch 를 금지한다. 이 규칙 본문에 이번 예외를 **명시적으로 새겨넣는다**.

규칙의 원래 의도(메인 검증을 보조 에이전트로 **대체하지 마라**)는 유지된다. 이번 건은 대체가 아니라 병렬 추가다. 이 구분을 규칙 본문에 적지 않으면, 나중 세션이 HARD-GATE 만 읽고 무맥락 검증자 dispatch 를 규칙 위반으로 판단해 삭제한다.

## 4. 비기능 요구사항 (NFR)

- **비용** — 문서 단계에 보조 에이전트 호출이 새로 붙는다. 정확한 개수는 FR-3 을 어떤 방식으로 강제하느냐에 달렸고 개발방향 단계에서 확정한다. 문서 단계는 실행 단계보다 원래 가벼우므로 피처 전체 비용에서 차지하는 비중은 제한적이지만, 끄는 수단(FR-6)이 반드시 있어야 한다.
- **지연** — 병렬 실행(FR-1)이라 무맥락 검증자가 끝나기를 메인이 놀면서 기다리지 않는다. 사용자 체감 지연은 두 검증 중 느린 쪽에 수렴한다.

## 5. 범위 밖 (Out of Scope)

- **코드 실행 단계 검증자** — `js-super-sub-driven` 의 wave 별 spec reviewer(`spec-reviewer-prompt.md`)에 무맥락 검증자를 붙이는 것. 이번엔 문서 단계로 한정한다. 따라서 wave 실패 격리 룰과의 정합도 이번 범위에 해당 없음.
- **`requesting-code-review`** — 같은 이유로 제외.
- **무맥락 검증자의 문서 직접 수정** — 읽고 보고만 한다. 문서 수정은 메인이 사용자 승인 후 수행한다.
- **버전 올리기** — 워크트리 세션에서는 6 manifest 버전을 건드리지 않는다.
- **조건부 자동 게이팅** — FR-6 에서 배제 결정.

## 6. 수용 기준 (Acceptance Criteria)

1. `verifying-spec` 실행 시 무맥락 검증자가 병렬로 뜨고, 최종 보고서에 재검 축과 새 축의 지적이 구분되어 나타난다.
2. 끄는 플래그를 주면 무맥락 검증자가 뜨지 않고 기존 동작 그대로 돈다.
3. 메인이 무맥락 검증자 지적을 기각한 경우 기각 사유가 보고서에 남는다.
4. `CLAUDE.md` 에 결합 메모와 회귀 탐지 grep 이 추가되고, 그 grep 이 통과한다.
5. fixture 가 추가된다 (위치는 기존 fixture 관례를 따른다).
6. 실제 피처 하나를 `/tech-design` 까지 끝까지 돌려, 메인 보고서와 무맥락 검증자 보고가 **서로 다른 항목을 최소 1건 이상** 지적하는 것을 확인한다. 두 보고가 완전히 같으면 이 피처는 목적을 못 달성한 것이다. 양쪽 다 지적 0건으로 나오면 판정 불가로 보고, 결함을 의도적으로 심은 문서로 다시 확인한다.
