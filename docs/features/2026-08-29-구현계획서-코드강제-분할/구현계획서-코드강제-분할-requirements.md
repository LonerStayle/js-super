# 요구사항: 구현계획서 코드 강제 + 위키형 분할

> **다음 단계 안내**: 이 문서는 요구사항 (기획 단계) 입니다. 다음 단계로 `tech-design` skill (또는 `/design-tech` 슬래시) 을 호출해서 `<slug>-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요 — 그건 다음 산출물 (tech-design, 3개 트랙이면 plan 까지) 에 들어갑니다.

## 배경

구현계획서가 길어지면 작성 시점에 구현 코드 블록을 생략하고 자연어 설명만 남기는 drift 가 발생한다. 실제 사례: 사용자가 계획서의 코드를 보고 문제점을 사전에 파악하려 했는데, 계획서에 코드가 아예 실려 있지 않아 검토 자체가 불가능했다.

현행 룰 (v2.9+) 은 구현 코드를 `**원본**`/`**수정 후**` 블록으로 싣도록 요구하지만, 이는 LLM 자율 준수에 맡겨져 있다. 기존 결정적 검사 (`plan_byte_check`) 는 **존재하는** `**원본**` 블록의 byte-equal 만 검사하므로, 코드 블록이 아예 없는 task 는 검사 대상 밖이다. 즉 "코드를 안 실은 계획서" 를 잡는 장치가 없다.

## 핵심 결정 (Socratic 대화 결과)

1. **분할 단위 = task 기반 하위 문서 (묶음 허용)** — 메인 계획서는 개요 + DAG/wave 구조 + task 요약과 링크를 담은 인덱스, task 상세 (코드 블록 포함) 는 하위 문서로. 하위 문서 하나에 연관 task 를 2~3개까지 묶을 수 있되 **최대 3 task 상한**은 결정적 규칙으로 고정.
   - 버린 안 A (Phase별 분할): Phase 하나에 task 가 6~8개만 돼도 문서가 다시 커져 같은 drift 재발 위험 → 기각.
   - 버린 안 B (AI 가 분할 단위 자체를 그때그때 판단): 판단 룰에 맡기는 방식이 이번에 drift 로 무너진 지점 → 기각.
2. **발동 기준 = task 10개 이상** — 임계값 초과 시에만 분할 구조. 미만이면 지금처럼 단일 문서 유지. 단, 임계 미만이어도 코드량이 많다고 판단되면 분할할 수 있다 (분할 방향 재량만 허용 — 안전한 방향).
   - 버린 안 (항상 분할): 작은 피처까지 인덱스 + 하위 문서로 쪼개면 오버헤드만 늘어남 → 기각.
3. **강제화 수준 = 결정적 검사로 게이트 차단** — 코드 블록 부재·축약 마커를 결정적 검사로 탐지하고, 위반 시 계획서가 저장·승인 게이트를 통과하지 못한다. LLM 자율 준수 (Self-Review 항목 추가만) 로는 긴 문서에서 다시 무너진다는 것이 이번 사고의 교훈.

## 요구 항목

**FR-1**: 파일을 생성·수정하는 모든 task 는 구현 코드 블록 (`**원본**`/`**수정 후**` 페어, 신규 파일은 `**수정 후**` 만) 을 계획서 (분할 시 하위 문서 포함) 에 실어야 한다. 자연어 설명만으로 코드 변경을 서술하는 task 는 허용되지 않는다.

**FR-2**: 코드 블록 안의 축약 마커 (`... 생략`, `// 기존 코드 유지`, "동일 패턴 반복" 류의 생략 표현) 를 결정적 검사로 탐지한다.

**FR-3**: FR-1/FR-2 위반이 하나라도 있으면 계획서는 저장·승인 게이트를 통과하지 못한다 (결정적 검사 — LLM 자율 준수에 맡기지 않는다).

**FR-4**: task 가 10개 이상인 계획서는 분할 구조로 작성한다 — 메인 계획서는 개요·DAG(wave)·task 요약·하위 문서 링크를 담은 인덱스, task 상세 (코드 블록 포함) 는 하위 문서에 담는다.

**FR-5**: 하위 문서 하나는 연관 task 최대 3개까지 담는다. 어떤 task 를 묶을지는 AI 가 연관성 (같은 파일 / 의존 사슬) 으로 판단하되, 3개 상한은 결정적 규칙이다.

**FR-6**: task 10개 미만이어도 코드량이 많다고 판단되면 분할 구조를 쓸 수 있다. 재량은 분할 방향으로만 허용된다 — 10개 이상인데 단일 문서로 합치는 반대 방향 재량은 없다.

**FR-7**: 적용 범위는 정식 흐름 (`writing-plans`) 과 auto-flow (`auto-writing-plans`) 둘 다이다.

**FR-8**: 실행·검증 단계 (executing-plans / js-super-sub-driven / verifying-spec / plan_byte_check / code-pretty / glossary) 는 단일 문서 계획서와 분할 구조 계획서 **양쪽 모두** 읽고 처리할 수 있어야 한다 (하위 호환).

## 범위 밖

- 이미 작성된 기존 계획서의 소급 분할·재작성은 하지 않는다.
- 테스트 코드는 지금처럼 자연어 `**검증**:` 필드를 유지한다 (v2.9+ 룰 보존) — 이번 코드 강제화는 **구현 코드**에만 해당한다.
- 요구사항 문서·기술설계 문서의 분할은 다루지 않는다 (구현계획서 전용).

## 수용 기준

- task 10개 이상인 계획서를 작성하면 인덱스 + 하위 문서 구조가 생성된다.
- 파일 변경 task 에 코드 블록이 없거나 축약 마커가 있는 계획서는 게이트에서 결정적으로 차단된다.
- 기존 단일 문서 계획서의 실행 흐름 (executing-plans / js-super-sub-driven) 에 회귀가 없다.
