# 요구사항: 변수명 노출 줄이기

> **모드**: Socratic (자유 형식). 다음 단계의 `tech-design` 가 본 문서를 자유 형식 산문으로 읽습니다 (PRD 6 섹션 ID 강제 X).

## 배경

기술설계 문서를 쓸 때 프로젝트의 아주 작은 이름까지 본문에 자주 등장한다. 내부 변수, 아직 만들지도 않은 함수 이름, 중간 계산값 같은 것들이 설명 문장 안에 그대로 박힌다.

이런 이름은 설계를 읽는 사람에게 도움이 되지 않는다. 구현 단계에서 얼마든지 바뀔 이름이라 문서만 먼저 낡고, 정작 알아야 할 구조와 결정은 이름 사이에 묻힌다.

저장소의 기존 문서를 세어 보면 실태가 드러난다. 기술설계 문서 한 편에 이런 이름이 적게는 없고 많게는 열아홉 개까지 나온다. 최근 문서도 배경 설명 문단에 함수 이름과 경로가 섞여 있다.

현재 스킬에는 이를 막는 장치가 사실상 없다. 요구사항 작성 스킬에는 "기술 결정을 넣지 말라"는 룰이 세 군데 있지만 전부 아키텍처 선택 수준을 말하는 것이고, 개별 이름의 노출은 겨냥하지 않는다. 기술설계 작성 스킬에는 서술 수준에 관한 룰이 아예 없다.

## 이번에 다루는 범위

기술설계 문서를 만드는 두 경로에만 손댄다. 사용자가 직접 부르는 경로와 자동 흐름 경로가 같은 종류의 문서를 만들기 때문에, 한쪽만 고치면 두 경로의 문체가 갈린다.

다음은 이번 범위에서 뺀다.

- **요구사항 문서** — 앞으로 이 산출물 자체를 없앨 가능성이 있어 지금 룰을 정해두면 헛수고가 된다. 필요해지면 그때 같은 원칙을 옮겨 적으면 된다.
- **구현계획서** — 실제로 코드를 다루는 문서라 이름이 나오는 게 정상이다.
- **문서를 검증하는 스킬** — 작성 스킬 안에서 스스로 점검하는 것으로 충분하다고 판단했다. 검증 보고가 길어지는 대가에 비해 얻는 게 적다.

## 핵심 결정

### 1. 기본은 풀어쓰기, 예외는 계약

이름을 쓰려는 자리마다 먼저 그 역할을 말로 풀어쓴다. 이것이 기본 동작이다.

예외는 하나다. **그 이름이 바뀌면 문서 밖의 무언가가 깨지는 경우**에만 실제 이름을 쓴다.

기본값을 풀어쓰기로 둔 이유가 있다. 판정을 매번 통과시키는 방식으로 가면 판정 문장을 아무리 잘 써도 결국 지금과 비슷해진다. 반대로 기본 동작을 풀어쓰기로 잡으면 방향 자체가 바뀌고, 예외 문장이 꼭 필요한 이름을 지켜준다.

### 2. 판단을 돕는 예시

기준 문장 하나만으로는 경계 사례에서 흔들린다. 짧은 예시를 함께 둔다.

| 실제 이름을 쓰는 경우 | 말로 풀어쓰는 경우 |
|---|---|
| 사용자가 입력하는 명령어 | 내부 변수, 지역 변수 |
| 설정 파일의 키 이름 | 아직 없는 새 함수나 클래스 이름 |
| 다른 팀이나 외부가 호출하는 공개 함수 | 직접 지은 중간 계산값 |
| 저장소에 이미 있는 파일 경로 | 반복문 변수, 임시로 붙인 이름 |

왼쪽은 이름 자체가 약속이라 바꾸면 문서 밖이 깨진다. 오른쪽은 구현하면서 얼마든지 달라질 수 있어 지금 적어봐야 의미가 없다.

### 3. 서술 문단에만 적용

이 룰은 줄글로 설명하는 부분에만 적용한다. 코드 블록, 표, 도식은 그대로 둔다.

코드 블록은 이름을 보여주는 것 자체가 목적이고, 영향 범위를 정리한 표는 파일 경로가 있어야 쓸모가 있다. 여기까지 손대면 설계 근거가 사라진다.

### 4. 쓰고 나서 한 번 되돌아보기

문서를 다 쓴 뒤 스스로 확인하는 항목을 둔다. 서술 문단에 남은 이름을 훑고, 각각이 위 예외에 해당하는지 보고, 아니면 말로 바꾼다.

작성 지침만 두면 한 번 놓쳤을 때 걸러지지 않는다. 별도 검증 스킬까지 동원하는 건 과하다고 봤고, 같은 스킬 안에서 끝내는 선을 골랐다.

## 우려와 대응

**너무 빡빡해서 설계가 뜬구름이 되지 않을까.** 서술 문단에만 적용하고 코드 블록과 표는 온전히 남기기로 해서 설계 근거는 그대로 유지된다. 계약에 해당하는 이름도 예외로 살아남는다.

**너무 느슨해서 지금과 같아지지 않을까.** 기본 동작이 풀어쓰기라 방향이 반대다. 이름을 쓰려면 예외에 해당한다는 판단을 거쳐야 한다.

**두 경로의 문체가 갈리지 않을까.** 수동 경로와 자동 경로에 같은 룰을 함께 넣는다.

**룰이 지켜지는지 어떻게 확인할까.** 문체에 관한 룰이라 단순 검색으로는 잡히지 않는다. 확인 방법을 어떻게 마련할지는 다음 단계에서 정한다.

## 수용 기준

- 새로 쓴 기술설계 문서의 서술 문단에 내부 이름이 남지 않는다
- 명령어, 설정 키, 공개 함수, 기존 파일 경로는 그대로 남아 있다
- 코드 블록과 표의 내용은 이번 변경 전과 달라지지 않는다
- 수동 경로와 자동 경로가 같은 룰을 따른다
- 문서를 다 쓴 뒤 스스로 확인하는 항목이 작성 스킬 안에 있다

## 다음 단계에서 정할 것

- 룰과 예시를 스킬 본문의 어느 위치에 어떤 문장으로 넣을지. 지침으로 쓸지, 금지 사례 표로 쓸지, 예시로 보여줄지에 따라 실제 행동이 달라진다
- 룰이 지켜지는지 확인하는 방법. 문체 룰이라 단순 검색이 어렵다
- 두 경로를 함께 고쳐야 한다는 결합 메모를 어디에 남길지
