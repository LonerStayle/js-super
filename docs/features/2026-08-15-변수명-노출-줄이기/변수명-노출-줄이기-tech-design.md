## 1. 아키텍처 개요 (diagram + prose)

이번 변경은 기술설계 문서를 만드는 두 스킬의 **본문에 서술 수준 룰을 심는 것**이 전부다. 실행되는 코드도, 새로 도는 검사도 없다. 문서를 쓰는 순간 읽히는 지침과, 다 쓰고 난 뒤 스스로 훑는 점검 항목 두 자리에 룰을 배치한다.

룰이 실제로 행동을 바꾸려면 문서를 쓰기 직전과 쓴 직후 양쪽에 있어야 한다. 지침만 두면 한 번 놓쳤을 때 걸러지지 않고, 점검만 두면 이미 다 쓴 문서를 고쳐야 해서 부담이 커진다.

```
[문서 쓰기 전]        [문서 쓰는 중]         [문서 쓴 뒤]
전용 지침 섹션   ──→   서술은 풀어쓰기    ──→   자체 점검 항목
판별 문장 + 예시 표     표·코드 블록은 그대로     남은 이름 훑고 교정
                                              ↑
                                     금지 사례 표가 경계 사례 보강
```

같은 배치를 수동 경로와 자동 경로 양쪽에 넣는다. 자동 경로는 사용자 개입 없이 문서를 쓰기 때문에 룰이 본문에 없으면 아예 적용되지 않는다.

## 5. 핵심 결정 + 대안 비교 (why this path)

- **D-1 룰 배치 = 전용 섹션 신설** (채택). 룰이 판별 문장 하나와 예시 표, 적용 부위 세 덩어리로 이뤄져 있어 기존 섹션 어디에도 자연스럽게 안 붙는다. 전용 섹션이면 자동 경로 쪽에 옮겨 적기도 쉽다. 대안 1은 문서 템플릿 안내문에 한 문장만 넣는 것 — 짧아서 읽히긴 하나 예시 표가 들어갈 자리가 없어 경계 사례에서 흔들려 기각. 대안 2는 질의응답 절차 안에 섞는 것 — 절차는 무엇을 물을지를 정하는 자리라 문체 룰이 묻혀 기각.

- **D-2 자체 점검 = 기존 점검 목록에 항목 하나 추가** (채택). 수동 경로에는 문서를 다 쓴 뒤 돌아보는 자리가 이미 있고 네 항목이 들어 있다. 다섯 번째로 붙이면 별도 절차 없이 자연스럽게 돌아간다. 대안은 점검 절차를 새로 만드는 것 — 문체 하나 때문에 절차를 늘리는 건 과해서 기각.

- **D-2b 자동 경로의 점검 = 문서 작성 단계 안에 포함** (채택). 자동 경로에는 되돌아보는 자리가 아예 없다. 새 절차를 만드는 대신 문서를 쓰는 단계 자체를 "쓰고 나서 서술 문단을 한 번 훑는다"까지로 넓히고, 진행 목록에 보이는 그 단계의 문구도 같이 넓힌다. 대안 1은 진행 목록에 점검 단계를 따로 추가하는 것 — 자동 흐름은 사용자 개입 없이 달리는데 문체 점검만을 위해 단계를 늘리면 진행 표시가 산만해져 기각. 대안 2는 자동 경로에 점검을 넣지 않는 것 — 두 경로가 같은 룰을 따라야 한다는 요구사항에 어긋나 기각.

- **D-3 금지 사례 표에 한 행 추가** (채택). 이 저장소의 다른 룰들이 전부 "지침 + 점검 + 금지 사례" 세 겹으로 되어 있고, 금지 사례 표가 경계 사례에서 가장 강하게 작동한다. 요구사항이 고른 "작성 지침 + 자체 점검" 범위 안에 드는 보강이다. 대안은 표를 건드리지 않는 것 — 한 행이라 부담이 없고 효과가 커서 기각.

- **D-4 자동 경로 반영 = 핵심 룰과 예시 표를 옮겨 적고 상세는 참조** (채택). 자동 경로 본문은 백 줄이 안 되게 짧게 유지되어 왔다. 판별 문장과 예시 표만 옮기면 실제 판단에 필요한 건 다 들어가고, 배경 설명은 참조로 남긴다. 같은 스킬이 이미 다른 룰을 이 방식으로 처리한 선례가 있다. 대안 1은 전문을 그대로 복사하는 것 — 본문이 길어지고 고칠 때마다 두 배로 손이 가서 기각. 대안 2는 참조 한 줄만 두는 것 — 자동 경로는 사람이 중간에 개입하지 않아 본문에 없는 룰은 적용이 불확실해서 기각.

- **D-5 룰 준수 확인 = 룰 문구가 박혔는지 확인 + 시나리오 사례 문서** (채택). 문체 룰이라 문서를 기계로 판정하기 어렵다. 그래서 확인을 둘로 나눈다. 하나는 룰 문구가 두 스킬 본문에 살아 있는지 검색으로 확인하는 것이고 (룰이 지워지거나 한쪽만 남는 회귀를 잡는다), 다른 하나는 통과 사례와 위반 사례를 나란히 적은 시나리오 문서다 (사람이나 검토 에이전트가 판단 기준을 맞춰볼 수 있다). 대안은 서술 문단의 이름 개수를 세는 스크립트를 만드는 것 — 몇 개부터 위반인지 정할 근거가 없고 새 스크립트는 이번 범위를 넘어서 기각. 다만 나중에 필요해지면 붙일 수 있는 자리로 남겨둔다.

- **D-6 결합 메모 = 두 파일을 함께 고치는 룰로 기록** (채택). 한쪽만 고치면 두 경로의 문서 문체가 갈리는데, 이건 검색으로도 잘 안 잡히는 종류의 어긋남이다. 저장소의 다른 짝지어진 스킬들과 같은 방식으로 메모를 남긴다.

- **D-7 버전은 올리지 않음** (채택). 여러 워크트리가 동시에 진행 중이라 각자 버전을 올리면 합칠 때 충돌한다. 이 작업은 문서와 스킬 본문만 커밋하고, 버전 결정은 메인 워크트리로 합친 뒤에 한다.

## 6. 위험/사이드이펙트 (preliminary)

- **side-effect**: 룰이 의도보다 넓게 읽혀 표나 코드 블록의 이름까지 지워질 수 있다. 요구사항이 "서술 문단만"으로 못 박았으므로 룰 본문에도 적용 부위를 명시하고, 금지 사례 표에 "표와 코드 블록까지 손대는 것"을 위반 사례로 넣어 완화한다.

- **side-effect**: 반대로 룰이 너무 약하게 읽혀 지금과 달라지지 않을 수 있다. 기본 동작을 풀어쓰기로 잡은 것이 이 위험에 대한 대응이고, 예시 표의 오른쪽 열이 실제로 자주 나오는 사례를 담아야 효과가 난다.

- **breaking**: 없음. 두 스킬의 절차·게이트·다음 단계 연결은 건드리지 않는다. 추가되는 건 문체 지침과 점검 항목뿐이라 기존 흐름이 끊길 자리가 없다.

- **race**: 없음. 실행되는 코드 변경이 없다.

- **side-effect (문서 쪽)**: 이미 쓰인 기존 기술설계 문서들은 그대로 둔다. 소급해서 고치면 변경이력이 부풀고 얻는 게 없다. 새로 쓰는 문서부터 적용된다.

## 7. 테스트 전략

실행되는 코드가 없어 자동 테스트로 검증할 대상이 없다. 확인은 세 가지로 한다.

- **룰 존재 확인**: 두 스킬 본문에 판별 문장과 예시 표, 점검 항목, 금지 사례 행이 모두 남아 있는지 검색으로 확인한다. 한쪽만 남는 회귀를 잡는 것이 목적이다.
- **범위 보존 확인**: 두 스킬의 기존 절차·게이트·다음 단계 연결이 그대로인지 확인한다. 변경 전후를 비교해 추가된 부분만 있고 기존 줄이 사라지지 않았는지 본다.
- **시나리오 사례 문서**: 통과 사례와 위반 사례를 나란히 적은 문서를 테스트 폴더에 추가한다. 같은 설계 내용을 이름 그대로 쓴 문장과 풀어쓴 문장으로 각각 보여주고, 어느 쪽이 룰에 맞는지 표시한다. 문체 판정은 기계가 못 하므로 판단 기준을 맞춰보는 용도다.

실사용 확인은 이번 변경 다음에 쓰이는 기술설계 문서가 자연스럽게 맡는다. 참고로 이 문서 자체가 새 룰을 따라 쓰였다 — 서술 문단에는 저장소에 이미 있는 파일 경로만 남기고 나머지는 말로 풀었다.
