# 요구사항: plan-test-자연어축약

> **모드**: Socratic (자유 형식, auto-flow). 다음 단계의 `tech-design` 가 본 문서를 자유 형식 산문으로 읽습니다 (PRD 6 섹션 ID 강제 X).

## 배경

writing-plans / auto-writing-plans 가 만드는 구현계획서는 TDD bite-sized task 구조라서, 각 task 에 실패 테스트 코드 블록이 그대로 들어간다. 그래서 계획서를 리뷰할 때 구현 코드와 테스트 코드가 섞여 분량이 커지고, 정작 자세히 봐야 할 구현 코드에 집중하기 어렵다.

이번 변경의 목적은 하나다 — **계획서 리뷰 때 구현 코드만 자세히 보게 만드는 것**. 테스트 코드는 계획서에서 자연어 검증 설명으로 축약하고, 실제 테스트 코드 작성과 실행은 실행 단계로 옮긴다. TDD 자체 (테스트 먼저 작성 → 실패 확인 → 구현 → 통과) 는 실행 단계에서 그대로 유지한다.

## 핵심 결정

### 결정 1 — 계획서의 테스트 표현: 자연어 검증 설명 1~2줄 (사용자 결정)

구현계획서의 각 task 에는 테스트 코드 블록을 넣지 않는다. 대신 그 task 의 테스트가 "무엇을 검증하는지 + 어떤 기준으로 성공인지" 를 자연어 1~2줄로 적는다.

### 결정 2 — TDD 는 실행 단계에서 유지 (사용자 결정)

실제 테스트 코드 작성 → 실패 확인 → 구현 → 통과 확인 순서는 실행 단계 (executing-plans inline / js-super-sub-driven subagent) 가 담당한다. 계획서에서 코드가 빠질 뿐, 테스트 먼저 원칙은 변하지 않는다.

### 결정 3 — 실행 단계 하위 호환 유지 (사용자 결정)

실행 단계는 두 형식 모두 처리한다:

- 계획서에 테스트 코드 블록이 있으면 (기존 형식) → 그대로 사용
- 테스트 코드 블록이 없고 자연어 검증 설명만 있으면 (새 형식) → 실행 단계에서 설명 기반으로 테스트를 직접 작성

기존 docs/features/ 아래 계획서들의 소급 변환은 하지 않는다.

### 결정 4 — 접근 방식: 스키마 + 실행 절차 동시 개정 (자동 선택)

세 가지 접근을 비교해 B안을 선택했다.

- **A안 — 계획서 스키마만 변경**: 실행 단계 룰은 그대로 둠. 실행 쪽이 "계획서에 테스트 코드가 있다" 는 전제를 유지한 채 공백이 생겨 실행 시 혼선. 탈락.
- **B안 (선택) — 스키마 + 실행 절차 동시 개정**: 계획서 스키마 변경과 함께 실행 단계 (inline / subagent 양쪽) 에 자연어 설명 기반 테스트 작성 절차를 명시. 리뷰 슬림 목적을 직접 달성하고 TDD 실행 흐름에 공백이 없다.
- **C안 — 테스트 코드 부록 파일 분리**: 계획서 본문만 슬림화하고 테스트 코드는 별도 파일로. 리뷰 목적은 달성하지만 관리 파일이 늘고 byte-copy 검증 대상이 유지돼 복잡도가 커진다. 탈락.

선택 근거: 목적 (리뷰 슬림) 을 가장 단순한 구조로 달성하면서 실행 단계에 공백을 만들지 않는 안은 B 뿐.

## 요구 항목

1. writing-plans 와 auto-writing-plans 가 생성하는 구현계획서의 task 에는 테스트 코드 블록이 없어야 한다. 각 task 에 자연어 검증 설명 1~2줄 (무엇을 검증하는지 + 성공 기준) 이 있어야 한다.
2. 두 skill 의 관련 룰 본문 (task 템플릿, placeholder 금지 룰, same-file 묶음 step 구조) 이 새 표현과 모순 없이 갱신돼야 한다. 두 skill 은 페어 동기 (atomic 수정).
3. 실행 단계 (executing-plans inline + js-super-sub-driven subagent) 에 "자연어 검증 설명 → 테스트 작성·실행" 절차가 명시돼야 한다. 하위 호환 (결정 3) 포함.
4. 구현 코드의 byte-copy 룰 (drift 방지) 은 그대로 유지된다. 테스트 코드만 byte-copy 대상에서 빠진다.
5. subagent 모드의 테스트 작성 주체와 모델 (haiku 유지 여부 / sonnet 승격 여부) 은 tech-design 에서 결정한다. 계획서에서 테스트 코드가 빠져도 테스트 품질이 유지되는 방안이어야 한다.
6. writing-plans 의 `**Model**:` 필드 ↔ js-super-sub-driven dispatch 결합은 유지된다.

- 기존 계획서 문서들의 소급 변환

| task 의 Files: Test 경로 줄까지 사라지면 wave 병렬의 파일 충돌 감지에서 테스트 파일이 빠짐 | Test: 경로 줄은 계획서에 유지 — 코드 블록만 제거 |
| 계획서 검증 도구 영향 | plan_byte_check.py 는 `**원본**` 라벨 블록만 검사 (테스트 블록은 원래 라벨 없음 → 영향 없음), code-pretty 는 `**수정 후**` 라벨만 대상 (영향 없음), verifying-spec 은 저장소의 실제 테스트 파일을 검사 (영향 없음) — 탐색으로 확인 |
