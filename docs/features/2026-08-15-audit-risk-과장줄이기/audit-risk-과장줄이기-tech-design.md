## 1. 아키텍처 개요

### 현재 흐름

```
사용자 → /audit-risk
  Step 1  mkdir docs/audit/
  Step 2  보조 에이전트 5개 병렬 (A 비용 / B 개인정보 / C 민감로직 / D 에이전트 / E 거버넌스)
  Step 3  결과 취합 (부분 실패 허용)
  Step 4  보조 에이전트 F → HTML 1개 생성
  Step 4.5 F 결과 검증 (파일 존재 / 크기 0~120KB) → 실패 시 파일 삭제 + 메인이 다시 작성
  Step 5  한 줄 요약 출력
```

### 개편 후 흐름

```
사용자 → /audit-risk
  Step 1  mkdir docs/audit/ + 코드 규모 측정 → 모드 결정 (축소 / 전체)
  Step 2  [축소 모드] 보조 에이전트 1개가 5개 영역 순회
          [전체 모드] 보조 에이전트 5개 병렬 (기존과 동일)
  Step 3  결과 취합 (부분 실패 허용)
  Step 4  메인이 직접 마크다운 보고서 작성 (단일 Write)
  Step 5  한 줄 요약 출력
```

보조 에이전트 F 와 Step 4.5 검증·복구 절차가 사라집니다. HTML 생성이 없어지면서 크기 제한, 단일 Write 강제, 부분 파일 정리 같은 장치가 필요 없어집니다.

에이전트 수는 축소 모드에서 1개, 전체 모드에서 5개입니다 (기존 6개 → 최대 5개).

## 4. 외부 인터페이스 (산출물 계약)

### 4-1. 산출물 경로

- 변경 전: `docs/audit/<YYYY-MM-DD-HHMMSS>-audit-risk.html`
- 변경 후: `docs/audit/<YYYY-MM-DD-HHMMSS>-audit-risk.md`

기존에 생성된 `.html` 파일은 삭제하지 않습니다. 두 형식이 같은 폴더에 공존하며, 둘 다 git 추적 대상이 아닙니다.

### 4-2. 보조 에이전트 반환 형식

영역별 반환 JSON 에서 `score` 필드를 없애고 `status` 를 필수로 만듭니다.

```
{
  "status": "clean | findings | skipped | failed",
  "checked": ["<무엇을 어떤 기준으로 봤는지 — 1~3 항목>"],
  "findings": [ ... ],
  "unverified": [ ... ],
  "summary": "<한 줄>"
}
```

- `clean` — 점검했고 해당 항목이 없음
- `findings` — 발견 항목 있음
- `skipped` — 해당 영역이 이 프로젝트에 적용되지 않음 (예: LLM 에이전트 코드 자체가 없음)
- `failed` — 에이전트 실행 실패

`checked` 는 `clean` 일 때 필수입니다. 무엇을 봤는지 남겨야 "점검했지만 없음" 과 "점검하지 않음" 이 구분됩니다.

### 4-3. 발견 항목 형식

```
{
  "file": "<경로>",
  "line_range": "<시작-끝>",
  "severity": "심각 | 높음 | 보통",
  "category": "<영역별 하위 분류>",
  "title": "<제목>",
  "evidence": "<코드에서 확인한 사실>",
  "impact": "<이 상태에서 무엇이 일어나는지>",
  "recommendation": "<권장 조치>"
}
```

`unverified` 항목은 심각도 없이 별도 배열에 담습니다.

```
{
  "file": "<경로>",
  "line_range": "<시작-끝>",
  "title": "<제목>",
  "why_unverified": "<코드만으로 판단할 수 없는 이유>",
  "how_to_check": "<사용자가 확인하는 방법>"
}
```

## 5. 핵심 결정 + 대안 비교

### 결정 1 — 규모 판정은 소스 파일 수와 총 줄 수 두 조건을 모두 만족할 때만 축소

Step 1 에서 셈합니다. git 저장소면 `git ls-files`, 아니면 `find` 로 소스 확장자만 추립니다.

축소 모드 조건: **소스 파일 40개 미만 그리고 총 줄 수 8,000 미만**. 둘 중 하나라도 넘으면 전체 모드입니다.

- 대안 A: 파일 수만 → 파일 수는 적은데 파일 하나가 거대한 경우를 놓칩니다.
- 대안 B: 줄 수만 → 짧은 파일이 흩어져 있는 구조를 반영하지 못합니다.
- 대안 C (선택): 두 조건 AND → 어느 한쪽이라도 크면 전체 모드로 가므로, 요구사항의 "애매하면 5개" 가 규칙 자체로 지켜집니다.

판정 결과는 사용자에게 한 줄 알립니다. 예: `점검 대상 27개 파일 / 4,100줄 — 간단 모드로 진행합니다.`

### 결정 2 — 심각도는 3단계, 실행 경로를 확인한 항목에만 부여

- **심각** — 실행 경로 확인됨. 발생 시 데이터 유출·손실 또는 금전 손실로 직결
- **높음** — 실행 경로 확인됨. 영향이 조건부이거나 범위가 제한적
- **보통** — 실행 경로 확인됨. 즉각적인 피해는 없고 관행·유지보수 문제

실행 경로를 확인하지 못한 항목은 심각도를 붙이지 않고 "확인 필요" 목록으로 보냅니다. 왜 확인하지 못했는지와 사용자가 확인하는 방법을 함께 적습니다.

- 대안 A: 기존 4단계(Critical/High/Medium/Low) 유지 → Low 가 "확인 못 했지만 일단 낮음" 을 흡수하면서 건수만 부풀립니다.
- 대안 B (선택): 3단계 + 확인 필요 분리 → 심각도가 붙은 항목은 모두 근거가 있는 상태가 됩니다. 요구사항 결정 6과 직결됩니다.

### 결정 3 — 보고서는 메인이 마크다운으로 직접 작성

메인은 영역별 결과를 이미 갖고 있어 다시 전달할 필요가 없고, 마크다운은 디자인 판단이 필요 없습니다.

보고서 구조:

```markdown
# 감사 결과 — <프로젝트명>

생성: <YYYY-MM-DD HH:MM> / 모드: 간단(1) | 전체(5) / 대상: <N>개 파일, <M>줄

이 결과는 코드를 읽어 판단한 것으로, 외부 보안 도구를 대신하지 않습니다.

## 요약

| 심각도 | 건수 |
|---|---|
| 심각 | N |
| 높음 | N |
| 보통 | N |
| 확인 필요 | N |

| 영역 | 상태 |
|---|---|
| 외부 API 비용 | 발견 N건 |
| 개인정보 | 점검함, 해당 항목 없음 |
| 사용량·결제 로직 | 점검함, 해당 항목 없음 |
| LLM 에이전트 | 해당 없음 (관련 코드 없음) |
| 거버넌스 | 발견 N건 |

## 영역별 결과
### <영역명>
<발견 항목이 있으면 항목별로 파일:줄 / 확인한 사실 / 영향 / 권장 조치>
<없으면: 점검함, 해당 항목 없음. 확인한 범위: ...>

## 확인 필요
<심각도 미부여 항목 — 왜 판단 못 했는지 + 확인 방법>

## 조치 순서
<심각 → 높음 → 보통 순 목록>
```

- 대안 A: 보고서 전용 에이전트 유지 + 마크다운 작성 → 결과를 다시 넘기는 비용이 들고, 형식이 단순해 위임할 이유가 없습니다.
- 대안 B (선택): 메인 직접 작성 → 에이전트 1개와 재전달 비용이 사라지고, 실패 시 복구 절차도 필요 없습니다.

### 결정 4 — 축소 모드는 영역을 빼지 않고 한 에이전트가 순회

축소 모드에서도 다섯 영역을 모두 점검합니다. 영역을 생략하는 게 아니라 한 에이전트가 차례로 훑고 하나의 결과를 반환합니다.

- 대안 A: 영역을 줄인다 (예: 비용과 거버넌스만) → 놓치는 영역이 생기고, 무엇을 안 봤는지 사용자가 알기 어렵습니다.
- 대안 B (선택): 영역 유지, 에이전트만 통합 → 작은 코드베이스는 한 번에 훑을 수 있어 품질 손실이 크지 않습니다.

### 결정 5 — 표현 규칙을 프롬프트에 명시적으로 박는다

다섯 영역 프롬프트와 보고서 작성 지침 양쪽에 같은 규칙을 넣습니다.

- 코드에서 확인한 사실(`evidence`)과 그로 인한 영향(`impact`)을 분리해서 적는다
- 비용 추정은 단가 출처와 호출 빈도 근거를 함께 댈 수 있을 때만 적고, 그렇지 않으면 적지 않는다
- "치명적", "심각한", "위험천만", "즉시" 같은 형용사·부사를 쓰지 않는다
- 발견 항목이 없으면 만들어내지 말고 `status: "clean"` 과 확인 범위를 반환한다

### 결정 6 — 기존 HTML 산출물은 건드리지 않는다

폴더에 남아 있는 `.html` 파일을 삭제하거나 변환하지 않습니다. 두 형식이 공존해도 문제가 없고, 이미 만들어진 파일을 지우면 되돌릴 수 없습니다.
