# 요구사항: audit-risk 과장 줄이기

> **모드**: Socratic (자유 형식). 다음 단계의 `tech-design` 가 본 문서를 자유 형식 산문으로 읽습니다 (PRD 6 섹션 ID 강제 X).

## 배경

`/audit-risk` 는 프로젝트의 보안 / 개인정보 / 비용 / 거버넌스를 1회 훑고 보고서를 내는 커맨드입니다 (v2.3.0 도입). 현재 구성은 보조 에이전트 5개가 영역별로 병렬 점검하고, 6번째 에이전트가 그 결과를 HTML 1개로 만듭니다.

실사용에서 다음 네 가지가 걸렸습니다.

**1. HTML 산출물이 목적에 비해 과합니다.** `commands/audit-report-prompt.md` 는 보고서에 "wow first", 글래스모피즘, aurora 배경, 애니메이션, 필터 / 정렬 / 검색 UI, 다크모드 토글을 요구합니다. 감사 결과를 읽는 데 필요한 요소가 아닙니다. 결과물이 30~80KB 로 커지면서 단일 Write 실패에 대비한 검증 + 되돌리기 + 메인 인계 절차까지 커맨드에 붙어 있습니다 (Step 4.5, v2.3.1 에서 추가).

**2. 표현이 실제보다 부풀려집니다.** 영역별 0~100 점수는 근거 없이 매겨집니다. 월 비용은 best / worst 범위로 나오지만 실제 호출 빈도를 알 수 없는 상태의 추정입니다. 심각도 라벨(Critical / High)도 실행 경로 확인 없이 붙습니다.

**3. 문제가 없을 때 없다고 말하지 않습니다.** 조기 종료 경로는 에이전트 D(LLM 에이전트 위험)에만 있습니다. 나머지 네 영역은 finding 배열을 채워야 하는 구조라, 실제로 위험이 없어도 낮은 심각도 항목을 만들어내는 압력이 생깁니다.

**4. 프로젝트 규모와 무관하게 항상 6개 에이전트가 돕니다.** 파일 몇 개짜리 프로젝트에도 동일한 비용이 듭니다.

## 핵심 결정

### 결정 1 — 산출물은 마크다운 1개, HTML 폐지

`docs/audit/<timestamp>-audit-risk.md` 하나만 만듭니다. HTML 생성 경로와 `commands/audit-report-prompt.md` 는 제거합니다.

- 대안 A: HTML 유지 + 디자인 룰만 담백하게 → 크기 문제와 Write 실패 대비 절차가 그대로 남습니다.
- 대안 B (선택): 마크다운만 → 커맨드에서 Step 4.5 검증 / 되돌리기 / 인계 절차 전체가 사라집니다. 터미널과 편집기에서 바로 읽히고, diff 로 이전 감사와 비교할 수 있습니다.

기존에 만들어진 `docs/audit/*.html` 파일은 그대로 둡니다 (해당 경로는 git 추적 대상이 아닙니다).

### 결정 2 — 영역별 점수 폐지, 세어서 확인 가능한 값만

0~100 점수를 없애고 심각도별 건수만 남깁니다. 보고서 상단 요약은 "심각 0건 / 높음 2건 / 보통 5건 / 낮음 3건" 형태입니다.

- 대안 A: 점수 유지 + 근거 한 줄 첨부 → 근거를 붙여도 점수 자체가 임의값인 문제는 남습니다.
- 대안 B (선택): 건수만 → 보고서를 읽는 사람이 직접 세어 확인할 수 있습니다.

### 결정 3 — 프로젝트 규모에 따라 점검 에이전트 수를 조절

작은 프로젝트에서는 에이전트 1개가 전 영역을 훑고, 그렇지 않으면 기존대로 5개가 영역별로 나눠 봅니다. 규모 판정은 커맨드 시작 시 코드 규모를 세서 결정하고, 어느 쪽인지 애매하면 5개 쪽을 택합니다. 사용자에게는 판정 결과를 한 줄 알립니다.

- 대안 A: 항상 5개 → 작은 프로젝트에서 비용 낭비.
- 대안 B: 사용자가 매번 선택 → 매 호출마다 질문이 생깁니다.
- 대안 C (선택): 자동 판정 + 결과 통지 → 질문 없이 진행하면서 사용자가 판정을 확인할 수 있습니다.

### 결정 4 — 문제가 없으면 없다고 명시

다섯 영역 각각이 "문제 없음" 을 정식 결과로 낼 수 있어야 합니다. 지금은 에이전트 D 에만 있는 조기 종료 경로를 전 영역으로 넓힙니다. 보고서에도 영역별로 "점검함, 해당 항목 없음" 이 한 줄씩 남습니다 — 점검을 건너뛴 것과 점검했지만 문제가 없는 것이 구분되어야 합니다.

### 결정 5 — 보고서는 메인이 직접 작성

보고서 생성 전용 에이전트(F)를 없앱니다. 메인은 다섯 영역 결과를 이미 갖고 있어 재전달 비용이 들지 않고, 마크다운은 디자인 판단이 필요 없습니다.

### 결정 6 — 확인된 사실과 추정을 분리해서 쓴다

- 코드에서 직접 확인한 것과 추정한 것을 보고서에서 구분합니다.
- 실행 경로를 확인하지 못한 항목은 심각도를 붙이지 않고 "확인 필요" 로 분류합니다.
- 비용 추정은 근거(단가 출처 + 호출 빈도 근거)를 댈 수 있을 때만 적고, 그렇지 않으면 적지 않습니다.
- "치명적", "위험천만", "심각한" 같은 형용사를 쓰지 않고 무엇이 어떻게 되는지로 적습니다.

## 우려 / 해결

**점수를 없애면 영역 간 비교가 어려워집니다.** 심각도별 건수 표로 대신합니다. 영역 간 우열보다 어디에 몇 건이 있는지가 실제로 필요한 정보입니다.

**작은 프로젝트에서 1개 에이전트가 놓치는 것이 있을 수 있습니다.** 규모 기준을 넉넉하게 잡아 애매하면 5개 쪽으로 보냅니다. 구체적인 경계값은 다음 단계에서 정합니다.

**"문제 없음" 을 허용하면 대충 훑고 넘어갈 수 있습니다.** 문제 없음을 보고할 때도 무엇을 어떤 기준으로 봤는지 함께 적게 합니다. 빈 결과와 점검하지 않은 상태를 보고서에서 구분합니다.

**기존 검증용 시나리오 문서가 HTML 을 전제로 씌어 있습니다.** `commands/audit-risk-tests/H23-e2e/` 의 6개 시나리오와 확인 명령을 마크다운 기준으로 고쳐야 합니다.

**README 안내가 HTML 보고서를 소개하고 있습니다.** 428행 부근 설명과 흐름도, 516행 표를 함께 고칩니다.
