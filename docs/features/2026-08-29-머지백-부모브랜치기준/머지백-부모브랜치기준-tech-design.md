# 기술설계: 머지백 부모브랜치 기준

> 입력: `머지백-부모브랜치기준-requirements.md` (FR-1..5) · 다음 단계: `/write-plan` (구현계획서)

## 1. 아키텍처 개요

두 스킬이 하나의 기록을 사이에 두고 연동한다.

- **생성 쪽** (`setting-up-worktrees`): 새 브랜치로 워크트리를 만들 때, 분기 기준이 된 브랜치 이름을 저장소가 공유하는 git 설정에 남긴다. 이미 캡처하고 있는 분기 기준 값을 보고만 하고 버리던 것을, 한 줄 명령으로 영속화하는 것이 전부다.
- **머지백 쪽** (`worktree-merge-back`): 머지 대상 추론 단계가 "워크트리 목록의 첫 entry = 최상위" 방식을 버리고, 위 기록을 읽어 직계 부모를 확정한다. 기록이 없거나 검증에 실패하면 자동 진행을 멈추고 사용자에게 머지 대상을 확인받는다 (FR-3). 이후 단계 — 부모 변경 흡수, 부모로 머지, 환경 파일 동기화, 사후 안내 — 는 모두 이렇게 확정된 부모 하나를 기준으로 동작한다 (FR-4).

최상위에서 바로 분기한 워크트리는 기록값이 최상위 브랜치이므로 기존 동작과 동일하다 (FR-1).

**변경하지 않는 것 (안전성 룰 보존)**: 기존 안전장치 세 가지 — feature 워크트리 안에서만 실행되는 진입 차단 (HARD-GATE worktree-only), 충돌 자동 해결 금지 (`--strategy ours|theirs` 자동 적용 X), push·워크트리 제거 등 사후 처리 자동 실행 금지 — 는 본문 그대로 유지한다. 이번 변경은 "머지 대상이 누구인가" 만 바꾼다 (요구사항 제약).

## 3. 데이터 모델 — 부모 기록

- **키 2개**: `branch.<브랜치명>.js-super-parent` (분기 기준이 된 브랜치 이름) + `branch.<브랜치명>.js-super-parent-base` (분기 시점 커밋 SHA). 분기 SHA 는 생성 절차가 이미 캡처하는 값이라 추가 비용이 없고, 아래 검증 4번 (분기점 조상 검사) 의 근거가 된다.
- **위치**: 저장소 공유 git config. 워크트리별 config 가 아니라 공유 config 라서 어느 워크트리에서 읽어도 같은 값이 나오고, 워크트리 디렉토리를 지워도 기록은 남는다.
- **생성**: `setting-up-worktrees` 가 새 브랜치(`-b`)로 워크트리를 만들 때. 같은 이름 브랜치를 스킬로 다시 만들면 덮어쓴다.
- **미생성 케이스**: 기존 로컬 브랜치 attach / remote-only 브랜치 attach (분기 이력을 알 수 없음) · 분기 시점에 브랜치 이름을 얻을 수 없는 상태 (detached HEAD). 이 경우 기록 없음 → 머지백 시 FR-3 게이트.
- **삭제**: 하지 않는다 (정리는 범위 밖). 단 잔존 키는 무해하지 않다 — 브랜치 삭제 후 같은 이름 브랜치를 스킬 밖에서 재생성하면 옛 기록을 그대로 물려받는다. 이 상속 오판은 검증 4번이 대부분 걸러내고, 남는 엣지는 §6 R5 로 수용.
- **소급**: 기존 워크트리에 심지 않는다 (요구사항 범위 밖 명시).

### 머지백 쪽 판별 절차 (Step 2 교체)

```bash
FEATURE_BRANCH=$(git rev-parse --abbrev-ref HEAD)
PARENT_BRANCH=$(git config "branch.$FEATURE_BRANCH.js-super-parent" || true)
PARENT_BASE=$(git config "branch.$FEATURE_BRANCH.js-super-parent-base" || true)

# 검증 4건 — 하나라도 실패 시 판별 실패 → 사용자 확인 게이트 (FR-3)
# 1) 기록 존재 + 자기 자신 아님
[ -n "$PARENT_BRANCH" ] && [ "$PARENT_BRANCH" != "$FEATURE_BRANCH" ]
# 2) 부모 브랜치가 로컬에 실존
git show-ref --verify --quiet "refs/heads/$PARENT_BRANCH"
# 3) 부모 브랜치가 어떤 워크트리에 체크아웃되어 있음 (머지를 실행할 경로 확보)
PARENT_PATH=$(git worktree list --porcelain \
  | awk -v b="refs/heads/$PARENT_BRANCH" '/^worktree /{p=$2} $0=="branch "b{print p; exit}')
[ -n "$PARENT_PATH" ]
# 4) 기록된 분기점이 현재 히스토리의 조상 — 스킬 밖 동명 재생성으로 물려받은 stale 기록 차단
[ -n "$PARENT_BASE" ] && git merge-base --is-ancestor "$PARENT_BASE" HEAD
```

판별 성공 시 이후 단계의 머지 대상 브랜치·경로 변수로 그대로 사용. 최상위 브랜치 이름은 기존 진입 차단 검사와 같은 방식 (`git worktree list --porcelain` 첫 entry 의 브랜치) 으로 얻되, 용도는 스택 여부 판정 (FR-5) 과 게이트 후보 나열뿐이다 — 머지 대상 결정에는 쓰지 않는다.

### 판별 실패 게이트 (FR-3)

`AskUserQuestion` 으로 머지 대상 브랜치를 확인받는다 (전역 v2.3.5+ 룰). 선택지는 후보를 실제로 나열한다 — 최상위 브랜치 + 다른 워크트리에 체크아웃된 브랜치들 (자기 자신 제외, 최대 4개 초과분은 Other 로). 실패 사유 (기록 없음 / 부모 브랜치 삭제됨 / 부모 미체크아웃 / 분기점 조상 아님) 를 질문 본문에 1줄 명시. 조용한 최상위 fallback · 히스토리 추정 자동 진행은 금지 (요구사항 핵심 결정).

사용자가 게이트에서 고른 대상 (Other 자유 입력 포함) 에도 위 검증 2·3번 (브랜치 실존 + 워크트리 체크아웃) 을 동일하게 적용한다 — 체크아웃 없는 브랜치엔 머지를 실행할 수 없으므로. 통과하지 못하면 실패 사유를 1줄 안내하고 게이트를 다시 연다 (검증 1·4번은 기록에 대한 검사라 사용자 명시 선택에는 적용하지 않음).

이 게이트 신설로 skill body 의 "AskUserQuestion 게이트 0건" 서술과 "Other / 모호 응답 룰 비활성" 서술은 함께 갱신한다 (게이트 1건 부활 — Other 룰 재활성).

## 5. 핵심 결정 + 대안 비교

### D1. 부모 기록 매체 — git config 커스텀 키 (채택)

- **(a) 공유 git config 의 커스텀 키** (채택): 달라지는 것 — 생성·머지백 각 한 줄. 포기하는 것 — git 표준 UI 에는 안 보이는 자체 규약. 되돌리는 비용 — 낮음 (키를 안 읽으면 그만).
- **(b) 워크트리 안 마커 파일** (기각): gitignore 안 하면 머지백 Step 1 의 자동 커밋에 섞여 저장소를 오염시키고, gitignore 하려면 사용자 프로젝트마다 gitignore 수정이 필요. 두 방향 모두 부작용이 채택안보다 크다.
- **(c) git 네이티브 upstream 설정** (기각): `git status` 의 ahead/behind 표시와 pull 동작이 바뀐다. ahead/behind 를 판정에 쓰는 기존 도구 (`/goodmorning` 뒤처진 워크트리 제외 등) 에 부작용 전파 위험.

채택안이 깨지는 조건: 사용자가 config 를 수동 편집해 기록이 사라지는 경우 — FR-3 게이트가 안전망이라 사고로는 이어지지 않는다.

### D2. 판별 실패 판정 — 검증 4건 전부 통과해야 자동 진행

기록 존재 여부만 보지 않고, 부모 브랜치 실존 + 워크트리 체크아웃 + 기록된 분기점의 조상 여부까지 확인한다. 하나라도 깨지면 자동 머지가 불가능하거나 (체크아웃 없는 브랜치엔 머지 실행 불가) 위험하므로 (삭제된 부모 / 물려받은 stale 기록) 게이트로 떨어뜨린다. "조금이라도 불확실하면 묻는다" 는 요구사항 안전망의 구체화.

### D3. 기록 시점 — 신규 분기(`-b`) 직후에만

기존 브랜치 attach 는 분기 이력을 모르므로 기록하지 않는다. 추정해서 심으면 D1-(b)/(c) 를 기각한 이유와 같은 오판 위험이 생긴다. 기록 없는 브랜치는 FR-3 이 흡수.

기록 명령은 `git worktree add` 와 **별도의 후속 Bash 호출**로 실행한다 — 생성 명령은 `git worktree add ` 로 시작할 때만 메모리 심링크 훅이 발화하는 기존 결합이 있어, 명령을 한 호출로 묶어 접두사가 바뀌면 훅이 죽는다.

### D4. 스택 안내 (FR-5) — 부모 ≠ 최상위일 때만

머지 완료 메시지에 "이 머지는 직계 부모까지 — 최상위 반영은 부모 워크트리에서 `/merge-back-worktree` 재실행" 안내를 추가. 부모 = 최상위면 출력하지 않는다 (기존 메시지 유지).

## 6. 사전 리스크

- **R1 기록-히스토리 불일치**: 사용자가 부모 브랜치를 리베이스·재작성한 경우. 기존 Step 4 의 머지 전 조상 검증(merge-base pre-check)이 그대로 잡는다 — 추가 장치 불필요.
- **R2 부모 워크트리 부재**: 부모 브랜치는 있는데 워크트리가 제거된 경우. 검증 3번에서 게이트로 — 사용자가 부모 워크트리 재생성 후 재호출하거나 다른 대상을 선택.
- **R3 게이트 부활로 인한 문서 불일치**: skill body 곳곳의 "게이트 0건" 서술 · CLAUDE.md 의 기존 결합 메모와 어긋날 수 있음 → §2 의 서술 갱신 + 결합 메모 신규 섹션으로 흡수.
- **R4 반영 시점**: 플러그인은 캐시에서 로드되므로 워크트리 수정만으로는 사용자 세션에 반영되지 않음 — 머지 + 릴리즈 후 `/reload-plugins` (기존 관례 답습, 이번 설계의 추가 작업 아님).
- **R5 동명 재생성 상속 엣지 (수용)**: 부모 브랜치의 작업이 이미 최상위에 흡수된 뒤, 같은 이름 브랜치를 스킬 밖에서 최상위 기준으로 재생성하면 옛 분기점이 새 히스토리의 조상이 되어 검증 4번도 통과할 수 있다 — 이때 옛 부모로 자동 머지된다. 발생 조건이 겹겹이고 (스킬 밖 재생성 + 동명 + 부모 흡수 완료 + 부모 워크트리 잔존) 머지 자체는 되돌릴 수 있어 수용 리스크로 두고, fixture 로 문서화만 한다.
