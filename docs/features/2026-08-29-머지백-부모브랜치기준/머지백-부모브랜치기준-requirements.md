# 요구사항: 머지백 부모브랜치 기준

> **다음 단계 안내**: 이 문서는 요구사항 (기획 단계) 입니다. 다음 단계로 `tech-design` skill (또는 `/design-tech` 슬래시) 을 호출해서 `머지백-부모브랜치기준-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요 — 그건 다음 산출물 (tech-design, 3개 트랙이면 plan 까지) 에 들어갑니다.

## 배경

`/worktree` (setting-up-worktrees) 는 워크트리 안에서 호출하면 호출 위치의 HEAD 를 기준으로 재분기한다 (2026-08-09 워크트리-재분기 피처). 즉 워크트리 A 에서 워크트리 B 를 만들면 B 의 직계 부모는 A 다.

그런데 `/merge-back-worktree` (worktree-merge-back) 는 머지 대상을 `git worktree list` 의 첫 번째 entry — 항상 최상위(main) 워크트리 — 로 추론한다. 재분기 워크트리에서 머지백을 실행하면 직계 부모(A)가 아니라 최상위(main)로 머지하려 들고, 지금까지는 모델이 상황을 보고 운 좋게 막아준 덕에 사고가 안 났을 뿐이다.

근본 원인: 워크트리 생성 시 분기 기준(BASE_BRANCH)을 **보고만 하고 어디에도 기록하지 않아서**, 머지백 시점에는 직계 부모를 알 방법이 없다.

## 핵심 결정

머지 대상 판별 방식으로 세 가지를 비교했다.

**A. 생성 시점에 부모를 기록하고, 머지백이 그 기록을 읽는다** (채택)
- 달라지는 것: 워크트리 생성 흐름과 머지백 흐름이 각각 한 군데씩 수정된다. 판별이 결정적(deterministic)이 된다.
- 포기하는 것: 이 개선 이전에 만든 워크트리에는 기록이 없다 — 이 경우를 위한 별도 처리(FR-3)가 필요하다.
- 되돌리는 비용: 낮음 — 기록을 안 읽으면 기존 동작 그대로다.

**B. 머지백 시점에 커밋 히스토리로 부모를 추정한다** (기각)
- 형제 브랜치가 같은 지점에서 갈라진 경우 등 애매한 케이스에서 오판 위험이 있고, 오판은 잘못된 브랜치로의 자동 머지로 이어진다. 안전성 핵심과 충돌.

**C. 머지백 때마다 사용자에게 머지 대상을 물어본다** (기각)
- 매번 질문이 발생해 자동화 의도와 충돌. 판별 불가 케이스의 fallback 으로만 쓴다 (FR-3).

A 안이 깨지는 조건: 기록 방식이 워크트리 밖(다른 세션·수동 git 조작)에서 훼손될 수 있다면 B 수준의 애매함이 되살아난다 — 그래서 판별이 조금이라도 불확실하면 FR-3 (사용자 확인) 으로 떨어지는 안전망을 함께 둔다.

## 요구 항목

**FR-1**: `/merge-back-worktree` 의 머지 대상은 항상 **직계 부모 브랜치** (이 워크트리를 분기시킨 브랜치) 다. 최상위(main) 워크트리에서 바로 분기한 워크트리는 지금과 동일하게 main 이 대상이 된다 — 동작 변화 없음.

**FR-2**: 워크트리 생성 시 (`setting-up-worktrees`) 분기 부모를 머지백이 나중에 판별할 수 있는 형태로 남긴다. 사용자가 베이스를 명시한 경우 그 브랜치가 부모다.

**FR-3**: 직계 부모를 확실히 판별할 수 없는 경우 — 기록이 없는 기존 워크트리, 부모 브랜치가 이미 삭제된 경우 등 — 자동 진행하지 않고 **머지를 멈추고 사용자에게 머지 대상 브랜치를 확인**받는다 (사용자 결정). 최상위로의 조용한 fallback 이나 히스토리 추정 자동 진행은 하지 않는다.

**FR-4**: 머지백 흐름에서 "parent" 를 참조하는 모든 단계 — 부모 변경사항 흡수(Step 3), 부모로 머지(Step 4), 환경 파일 동기화(Step 4.5), 사후 처리 안내(Step 5) — 가 같은 직계 부모를 기준으로 일관되게 동작한다.

**FR-5**: 부모가 최상위가 아닌 경우(스택 구조), 머지 완료 안내에 "이 머지는 직계 부모까지만이며 최상위 반영은 부모 워크트리에서 다시 머지백해야 한다"는 취지의 경로 안내를 포함한다.

## 우려와 해결

- **기존 워크트리 호환**: 이 개선 이전에 만든 워크트리(현재 20여 개)는 부모 기록이 없다 → FR-3 으로 흡수. 기록이 없으면 묻는다. 소급 기록 작업은 하지 않는다.
- **기존 안전성 룰과의 충돌 여부**: HARD-GATE (worktree-only) / 충돌 자동 해결 금지 (`--strategy ours|theirs` X) / push·삭제 자동 실행 금지 — 모두 그대로 유지. 이번 변경은 "머지 대상이 누구인가" 만 바꾼다.
- **판별 애매 시 자동 머지 사고**: 판별 로직에 조금이라도 불확실성이 있으면 FR-3 경로로 — 잘못된 대상 자동 머지가 최악의 결과라는 전제.

## 범위 밖

- `worktree-remove` 동작 변경 — 이번 범위 아님.
- remote(origin) 동기화 동작 변경 — 현행 유지 (로컬 브랜치 기준).
- 기존 워크트리에 부모 기록을 소급해서 심는 마이그레이션 — 하지 않음 (FR-3 이 흡수).
- 최상위 직계 워크트리의 머지백 동작 변경 — 없음 (FR-1 명시).
