# 기술설계: 워크트리 재분기 네이밍

> **다음 단계 안내**: 이 문서는 기술 설계서입니다. 다음 단계로 `writing-plans` skill (또는 `/write-plan` 슬래시) 을 호출해서 `워크트리-재분기-네이밍-implementation-plan.md` (구현계획서) 를 만드세요.

상위 문서: `워크트리-재분기-네이밍-requirements.md` (FR-1..6)

## 1. 아키텍처 개요

변경은 워크트리 생성 스킬 (`skills/setting-up-worktrees/SKILL.md`) 의 **브랜치 이름 결정 단계** 하나에 집중된다. 새 스크립트, 새 훅, 새 스킬은 만들지 않는다. 이름 생성은 결정적 코드로 만들 수 있는 성격이 아니라 (작업 설명을 읽고 짧은 이름을 짓는 일), 메인 에이전트의 판단으로 수행한다.

현재 스킬의 이름 처리 단계는 사용자 메시지에서 브랜치 이름 목록을 추출하는 일만 한다. 이 단계를 "이름 해석" 단계로 확장한다.

1. **사용자가 브랜치 이름을 명시한 경우** — 그 이름을 그대로 쓴다 (FR-4, 기존 동작 보존). 네이밍 규칙을 덮어씌우지 않는다.
2. **작업 설명만 있고 이름이 없는 경우** — 메인 에이전트가 이름을 생성한다 (FR-1).
   - 분기 기준 브랜치 (호출 위치의 현재 브랜치) 가 메인 브랜치와 **다르면** (= 재분기): `<분기 기준 브랜치>__<자식이름>` 형식 (FR-2). 부모 이름에 이미 `__` 가 있으면 자연스럽게 누적된다 (FR-3). 판별 기준은 D-2 참조.
   - 분기 기준 브랜치가 메인 브랜치와 **같으면**: 접두어 없이, 저장소의 기존 브랜치 관례 (언어·스타일·접두어 유무) 를 참고해 짓는다 (FR-6).
3. **확정** — 기본은 제안 이름을 선택지로 보여주고 확인받는다. 사용자가 "알아서 만들어" 류의 속행 신호를 준 상황이면 확인 없이 생성하고 결과 이름을 알린다 (FR-5).

부모 브랜치 이름은 스킬이 이미 캡처하는 "호출 위치의 현재 브랜치" 값을 그대로 쓴다 (v2.9.0 재분기 기능이 분기 기준 보고에 쓰는 값과 동일 소스). 새로 알아낼 것이 없다.

## 5. 핵심 결정 + 대안 비교

**D-1 이름 생성 위치 = 스킬 본문 (LLM 판단)**
- 대안 A (채택): 스킬 본문의 이름 해석 단계에서 메인 에이전트가 생성. 작업 설명 이해가 필요한 일이라 LLM 몫이 맞고, 파일 추가가 없다.
- 대안 B (버림): 결정적 helper script 로 이름 생성. 슬러그 변환은 코드로 되지만 "설명 → 좋은 이름" 은 코드로 안 된다. 스크립트는 어차피 LLM 출력을 받아야 해서 층만 는다.
- 되돌리는 비용: 낮음 — 스킬 본문 한 단계만 되돌리면 된다.

**D-2 재분기 판별 = 브랜치 기준 (분기 기준 브랜치 ≠ 메인 브랜치), 부모 이름 소스 = 호출 위치의 현재 브랜치**
- 대안 A (채택): 스킬이 v2.9.0 부터 캡처하는 두 값 — "호출 위치의 현재 브랜치" 와 "메인 워크트리의 현재 브랜치" — 를 비교해, **다르면 재분기로 판정**하고 호출 위치 브랜치를 접두어로 쓴다. 스택 구조 주의 출력이 이미 쓰는 판정과 동일해 기준이 하나로 통일된다. 부수 효과로, 메인 워크트리에서 feature 브랜치를 체크아웃한 채 분기해도 접두어가 붙는데 — 이 경우도 실제로 그 브랜치의 하위 작업이므로 의미가 맞다 (FR-2 는 워크트리 안 케이스를 강제할 뿐 이 확장을 금지하지 않는다).
- 대안 B (버림): 호출 위치 경로가 워크트리 안인지로 판정 (경로 기준). 메인 워크트리에서 feature 브랜치에 서서 분기하는 케이스에서 부모 관계가 이름에 안 남고, 판정 기준이 스택 안내 (브랜치 기준) 와 둘로 갈라진다.
- 대안 C (버림): 워크트리 폴더 경로에서 부모 이름을 역산. 폴더와 브랜치 이름이 어긋난 경우 깨진다.
- 깨지는 조건: detached HEAD 로 호출하면 현재 브랜치가 비어 있다 → D-6 fallback.

**D-3 워크트리 폴더 이름 = 브랜치 이름 그대로 (기존 동작 무변경)**
- 대안 A (채택): 폴더는 지금처럼 브랜치 이름을 그대로 쓴다. `feat/x__y` 처럼 `/` 가 든 이름은 `.worktrees/feat/x__y` 로 중첩 폴더가 되지만, git 이 중간 디렉토리를 만들어 주고 기존 스킬 동작과 동일해 변경이 0 이다.
- 대안 B (버림): `/` 를 `-` 로 치환한 평평한 폴더명. 브랜치 ↔ 폴더 대응이 어긋나 정리·머지 스킬의 경로 추론이 복잡해진다.
- 참고: 이 저장소의 브랜치 관례는 `/` 없는 평평한 이름이라 (FR-6 이 관례를 따르므로) AI 제안 이름에서 `/` 중첩이 실제로 발생할 확률은 낮다.

**D-4 자식 이름 생성 규칙**
- 자식 부분은 작업 설명에서 뽑은 짧은 이름 (공백 → 하이픈). 저장소 브랜치 관례의 언어·스타일을 따른다.
- 자식 부분에는 `__` 와 `/` 를 넣지 않는다 — `__` 는 부모·자식 구분자로 예약되고 (요구사항 "우려와 해결" 의 모호성 항목), `/` 는 폴더 중첩을 새로 만들기 때문. 사용자가 명시한 이름에는 이 제약을 적용하지 않는다 (FR-4).

**D-5 확정 휴리스틱 (FR-5 의 재량을 스킬 본문에 명문화)**
- 기본: AI 가 이름을 생성한 경우 제안 이름 (필요 시 후보 2~3개) 을 선택지로 확인받고 생성.
- 즉시 생성: 사용자가 이름 없이 "바로/알아서 만들어" 류 속행 신호를 준 경우 — 확인 없이 생성 + 결과 이름 알림.
- 명시 이름: 질문 없이 그대로 생성 (기존 동작).
- 대안 (버림): 항상 확인 게이트. 속행 신호까지 게이트에 걸리면 마찰이 늘어 FR-5 의 "상황 재량" 취지에 어긋난다.

**D-6 부모 브랜치명이 없을 때 (detached HEAD)**
- 접두어를 생략하고 단독 이름으로 제안하되, 한 줄 안내를 붙인다 (부모 브랜치를 알 수 없어 접두어 생략). 실패로 처리하지 않는다.

## 6. 예비 위험

- **이름 길이 누적** — 다단계 재분기에서 이름이 길어진다. 사용자가 누적 유지를 명시 선택 (FR-3) 했으므로 수용. 축약 도입 없음.
- **skill ↔ commands 미동기 회귀** — 한쪽만 고치면 안내와 실제 동작이 어긋난다. 기존 v2.0.2+/v2.9.0+ 결합 룰과 같은 방식으로 CLAUDE.md 결합 메모 + grep 으로 잡는다.
- **훅 프리픽스 결합 보존** — 이름 결정은 워크트리 생성 명령 **앞** 단계에서 끝난다. `git worktree add ` 로 시작하는 개별 Bash 호출 규칙 (v2.9.0) 은 그대로다. 이름 해석이 생성 호출과 한 명령으로 합쳐지면 훅이 침묵하는 회귀가 난다.
- **제안 남발** — 사용자가 이름을 명시했는데도 AI 가 "더 좋은 이름" 을 제안하는 행동은 금지 (FR-4). Anti-Patterns 표에 명시한다.

## 7. 테스트 전략

fixture README 1건 (시나리오 대조 사례) + 결합 메모의 회귀 catch grep.

시나리오:
1. **재분기 + 설명만** — `feat/scheduled-tasks` 워크트리 안에서 "알림 기능 워크트리" 요청 → `feat/scheduled-tasks__<자식이름>` 형식 제안이 나와야 한다.
2. **명시 이름** — 사용자가 `hotfix-x` 라고 이름을 주면 접두어 없이 그대로 생성 (제안·개명 없음).
3. **다단계 누적** — `a__b` 워크트리 안에서 설명만 주면 `a__b__<자식이름>` 제안.
4. **메인에서 설명만** — 판정 가능한 기준: 제안 이름에 `__` 와 `/` 가 없다 (접두어 미부착). 저장소 관례 부합 여부는 사람 눈 판정 보조 항목으로만 둔다 (fixture 는 사람이 돌리는 시나리오 문서).
5. **detached HEAD** — 접두어 생략 + 안내 한 줄.

회귀 catch grep: 마커 문구를 리터럴 `부모브랜치__자식이름` 으로 고정하고, skill 본문과 commands 양쪽에 존재를 검사한다 (`grep -cF "부모브랜치__자식이름" skills/setting-up-worktrees/SKILL.md commands/worktree.md` — 각 1 이상). 문서 속 다른 `__` 등장 (예시 브랜치명 등) 과 섞이지 않도록 느슨한 `grep -c "__"` 는 쓰지 않는다. Step 4 의 개별 `git worktree add` 호출 규칙 불변 확인은 기존 v2.9.0 grep 을 재사용한다. fixture 는 `skills/js-super-sub-driven/tests/H20-worktree-naming/` 로 예약한다 (H19 까지 사용 중).
