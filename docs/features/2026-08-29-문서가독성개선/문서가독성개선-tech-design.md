# 개발방향: 문서 가독성 개선

> **다음 단계 안내**: 이 문서는 기술 설계서입니다 (아키텍처 / 컴포넌트 / 데이터 / 인터페이스 / 결정 / 위험 / 테스트 전략). `문서가독성개선-requirements.md` 를 기반으로 작성됩니다. 다음 단계 `문서가독성개선-implementation-plan.md` (단계별 계획) 의 입력이 됩니다 (`writing-plans` skill 또는 `/write-plan` 슬래시). 단계별 구현 task 는 여기 박지 마세요 — 그건 다음 산출물 (plan) 에 들어갑니다.

## 1. 아키텍처 개요

이 작업은 코드를 실행하는 시스템이 아니라, 문서를 만드는 스킬 4개의 본문 (작성 규칙) 과 그 문서의 요구 항목 번호를 읽는 스킬들을 고치는 작업이다. 전체 구조는 아래 도면과 같다. 도면의 번호는 아래 표에서 설명한다.

```
┌────────────────────────────────────────────────────────────────┐
│  문서를 만드는 쪽 — 스타일 규칙과 번호 형식이 여기서 정해진다        │
│                                                                │
│   정식 경로                      자동 경로                       │
│  ┌────────────────────┐        ┌────────────────────┐          │
│  │ brainstorming      │        │ auto-brainstorming │          │
│  │  스타일 규칙 ①      │        │  압축 규칙 ①         │          │
│  └─────────┬──────────┘        └─────────┬──────────┘          │
│            ▼                             ▼                     │
│        요구사항서 (요구 항목 번호: 요구 1, 요구 2, …) ②            │
│                                                                │
│  ┌────────────────────┐        ┌────────────────────┐          │
│  │ tech-design        │        │ auto-tech-design   │          │
│  │  스타일 규칙 ①      │        │  압축 규칙 ①         │          │
│  │  도면 형식 기준 ③    │        │  도면 형식 기준 ③    │          │
│  └─────────┬──────────┘        └─────────┬──────────┘          │
│            ▼                             ▼                     │
│        기술설계서 (다이어그램: 도면 방식) ③                        │
└───────────────────────────┬────────────────────────────────────┘
                            │  요구 항목 번호를 읽는다
                            ▼
┌────────────────────────────────────────────────────────────────┐
│  번호를 읽는 쪽 — 새 형식 인식 + 옛 형식 하위 호환 ④                │

│   tech-design (요구사항서 읽기)   verifying-spec (검증 대조)      │

└────────────────────────────────────────────────────────────────┘
```

| 번호 | 내용 |
|---|---|
| ① | 문서를 만드는 스킬 4개에 "산출물 문서 스타일" 규칙 섹션을 넣는다. 정식 경로는 전체 규칙, 자동 경로는 압축본 (기존 미러 패턴 그대로) |
| ② | 요구 항목 번호를 `FR-1` 에서 `요구 1` 로 바꾼다. 템플릿과 작성 규칙이 바뀌는 지점 |
| ③ | 기술설계서의 다이어그램을 도면 방식으로 그리는 판단 기준을 넣는다 |
| ④ | 번호를 읽는 스킬들이 `요구 N` 을 인식하게 고치고, 이미 작성된 옛 문서의 `FR-N` 도 계속 읽도록 하위 호환 문구를 유지한다 |

## 5. 핵심 결정 + 대안 비교

### 결정 1 — 요구 항목 번호는 `**요구 N**:` 형식으로 쓴다

요구사항서에서 채택된 사용자 결정이다. 문서에는 `**요구 1**: <한 문장>` 형태로 쓴다. 굵게 표시까지 포함한 형태를 템플릿에 고정해야 읽는 쪽이 같은 패턴을 찾을 수 있다.

| 대안 | 판단 |
|---|---|
| `요구 1.` (마침표) | 굵게 없는 번호는 본문 속 "요구 1가지" 같은 일반 표현과 헷갈린다 |
| `[요구 1]` (대괄호) | 대괄호는 이 저장소에서 변경이력 태그 (`[요구사항-수정]`) 가 이미 쓰고 있어 의미가 겹친다 |
| `**요구 1**:` (채택) | 기존 `**FR-1**:` 과 구조가 같아서 읽는 쪽 수정이 표기 치환으로 끝난다 |

### 결정 2 — 하위 호환은 읽는 쪽에서 처리한다

이미 작성된 문서를 고치지 않고, 읽는 쪽이 세 세대의 형식을 모두 인식한다. 기술설계서 작성 스킬에는 이미 두 세대를 읽는 문구가 있어서, 거기에 새 형식을 한 세대 더 얹는 방식이다.

| 세대 | 형식 | 위치 |
|---|---|---|
| 최신 | `요구 N` | `## 요구 항목` 섹션 |
| 직전 | `FR-N` | `## 요구 항목` 섹션 |
| 초기 | `FR-N` | `## 3. 기능 요구사항 (FR)` 섹션 |

대안은 옛 문서를 일괄 수정하는 것인데, 요구사항서에서 이미 범위 밖으로 확정됐다 (변경이력이 있는 문서를 소급 수정하면 이력 의미가 깨진다).

### 결정 3 — 스타일 규칙은 스킬 본문에 직접 넣고, 섹션 이름을 네 스킬에서 통일한다

요구사항서의 채택안 (스킬 본문 직접 삽입) 을 그대로 따른다. 여기에 하나를 더한다: 규칙 섹션의 이름을 네 스킬 모두 "산출물 문서 스타일" 로 통일한다. 이름이 같아야 회귀 검사가 한 줄 검색으로 네 파일을 한 번에 확인할 수 있다.

규칙 본문은 네 가지다.

| 규칙 | 내용 |
|---|---|
| 위에서 아래로 | 용어는 처음 등장하는 자리에서 설명한다. 아래 섹션을 먼저 읽어야 이해되는 문장을 쓰지 않는다 |
| 간결한 자연어 | 문장은 짧게. 비유법 금지. 핵심과 무관한 서술 금지 |
| 표·도면 우선 | 나열·비교·구조 설명은 산문 대신 표나 도면으로. 산문은 배경과 판단 근거에만 |
| 항목 코드 금지 | 본문에 알파벳-숫자 코드를 만들지 않는다. 이름이 필요하면 짧은 한국어 제목을 쓴다. 유일한 예외는 `요구 N` |

정식 경로 두 스킬은 전체 규칙 + Self-Review 점검 항목을, 자동 경로 두 스킬은 압축본 + 작성 직후 점검 한 줄을 갖는다. 앞서 "서술 수준 — 이름보다 역할" 규칙이 정식/자동에 각각 전체본/압축본으로 들어간 것과 같은 배치다.

### 결정 4 — 도면 형식은 세 가지, 기본은 아스키 박스 도면

기술설계서의 다이어그램은 구역과 배치가 보이는 도면 방식이 기본이다. 금지하는 것은 절차 단계를 노드와 화살표로 나열한 흐름도로 구조 설명을 대신하는 것이다. 관계·조건 분기가 본질인 자리는 아래 표대로 mermaid 를 쓸 수 있다 — 이때도 절차 나열이 아니라 관계를 보여주는 그림이어야 한다. 스킬 본문 안의 dot 흐름도는 에이전트 실행용이라 대상이 아니다.

| 상황 | 형식 |
|---|---|
| 기본 — 구역·레이어·배치를 보여줄 때 | 아스키 박스 도면 |
| 구성 요소가 많거나 (대략 6개 이상) 요소마다 세부 설명이 필요할 때 | 아스키 도면에 번호를 달고 표에서 설명 |
| 관계·조건 분기가 본질이고 렌더링 환경 (GitHub, VS Code 미리보기) 을 전제할 수 있을 때 | mermaid |

도면 안 번호 (①②③) 는 알파벳-숫자 코드가 아니라 표에서 설명하는 도면 표기법이다. 항목 코드 금지 규칙의 대상 자체가 아니므로 `요구 N` 이 유일한 예외라는 문구와 충돌하지 않는다 — 규칙 문구에는 "도면 번호는 금지 대상이 아니다" 라는 적용 범위 명확화로 넣는다.

### 결정 5 — 코드 주석 금지 목록에 `요구 N` 을 추가한다

코드 주석에 문서 식별자를 못 쓰게 하는 기존 규칙이 있다 (주석은 자기 완결이어야 한다는 취지). `FR-1` 이 `요구 1` 로 바뀌어도 문서 참조라는 본질은 같으므로, 금지 예시와 패턴에 `요구 N` 을 추가한다. 대안은 한국어 표기라 덜 암호 같으니 허용하는 것인데, 문서가 바뀌면 주석이 낡는 문제는 표기 언어와 무관해서 기각한다.

## 6. 위험/사이드이펙트

| 위험 | 분류 | 대응 |
|---|---|---|
| 정식/자동 한쪽 경로만 수정되면 두 경로 문서의 문체가 갈린다 | side-effect | 네 스킬을 한 묶음으로 수정하고, 통일된 섹션 이름 검색으로 회귀 검사 |
| 번호를 읽는 스킬 중 한 곳이 누락되면 그 스킬이 요구 항목을 못 찾는다 | breaking | 2번 섹션의 파일 목록이 전수 조사 결과 — 목록 밖 파일에는 실제 번호 참조가 없음을 구현 단계에서 재확인 |
| 하위 호환 문구가 빠지면 옛 피처 문서를 다시 열 때 요구 항목을 못 읽는다 | breaking | 세 세대 인식 문구를 기술설계서 읽기 규칙에 명시하고, 검증·전파 스킬에도 옛 표기 병기 + 회귀 검사 |
| 결합 메모의 검사 명령 형식이 어긋나면 스킬 검증 러너가 규칙을 놓친다 | side-effect | 기존 결합 메모의 명령 형식 (bash 코드 블록 + 기대값 주석) 을 그대로 따른다 |

## 7. 테스트 전략

이 저장소의 스킬 본문 검증 방식 그대로, 결합 메모의 회귀 검사 명령과 대조 사례 fixture 로 검증한다.

| 검증 대상 | 방법 |
|---|---|
| 스타일 규칙 섹션이 네 스킬에 모두 있는가 | 통일 섹션 이름 검색 → 4개 파일 매치 |
| 요구사항서 템플릿이 새 번호 형식인가 | 템플릿의 `**요구 1**:` 존재 + `**FR-1**:` 부재 검색 |
| 하위 호환 문구가 살아 있는가 | 기술설계서 읽기 규칙의 `FR-N` 언급 존재 검색 (완전 소멸이 오히려 회귀) |
| 번호를 읽는 쪽이 새 형식을 아는가 | 검증·전파 스킬의 `요구 N` 표기 존재 검색 |
| 도면 형식 기준이 있는가 | 기술설계서 작성 스킬 두 곳의 기준 표 존재 검색 |
| 새 스타일의 통과/위반 판별 | 대조 사례 fixture (통과 예 + 위반 예) — 앞선 "서술 수준" 규칙의 fixture 와 같은 구성 |

구체적 검사 명령과 기대값은 구현 단계에서 결합 메모에 확정한다.
