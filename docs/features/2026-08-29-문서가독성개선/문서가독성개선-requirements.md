# 요구사항: 문서 가독성 개선

> **다음 단계 안내**: 이 문서는 요구사항 (기획 단계) 입니다. 다음 단계로 `tech-design` skill (또는 `/design-tech` 슬래시) 을 호출해서 `문서가독성개선-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요.

## 배경

js-super 가 만드는 두 문서 — 요구사항서와 기술설계서 — 가 읽기 어렵다는 문제 제기에서 출발한 작업이다.

| 문제 | 실제 증상 |
|---|---|
| 아래를 읽어야 위가 이해됨 | 용어 설명이 문서 뒷부분에 있어서, 앞부분을 읽다가 뒤로 갔다 와야 함 |
| 항목 코드 남발 | 본문 곳곳에 알파벳-숫자 코드 (예: 결정 코드, 룰 코드) 가 등장해서 독자가 코드표를 머리에 들고 읽어야 함 |
| 장황한 산문 | 표 하나면 끝날 내용을 문단 여러 개로 풀어 씀. 비유적 표현이 섞임 |
| 다이어그램이 워크플로우 일변도 | 노드와 화살표 나열 방식이라 시스템 구조가 한눈에 안 들어옴 |

이 작업은 두 문서를 만드는 스킬의 작성 규칙을 바꿔서, 앞으로 생성되는 문서가 위에서 아래로 한 번에 읽히게 만든다.

## 바꾸는 대상

문서를 만드는 스킬 4개와, 요구 항목 번호를 읽는 스킬들이 대상이다.

| 구분 | 대상 | 바뀌는 것 |
|---|---|---|
| 요구사항서 작성 | `brainstorming`, `auto-brainstorming` | 작성 스타일 규칙 + 요구 항목 번호 형식 |
| 기술설계서 작성 | `tech-design`, `auto-tech-design` | 작성 스타일 규칙 + 다이어그램 그리는 방식 |
| 번호를 읽는 쪽 | `tech-design`, `verifying-spec` (무맥락 검증 프롬프트 포함), `change-propagation` | 새 번호 형식 인식 + 옛 형식 하위 호환 |

정식 경로와 자동 경로 (auto) 를 함께 고친다. 한쪽만 고치면 두 경로가 만드는 문서의 문체가 갈리기 때문이다. 이 저장소는 앞서 "서술 수준 — 이름보다 역할" 규칙을 도입할 때도 같은 이유로 두 경로를 함께 고쳤다.

## 핵심 결정

### 요구 항목 번호를 "요구 N" 으로 바꾼다

지금 요구사항서의 요구 항목은 `FR-1`, `FR-2` 형식이다. 이 번호는 단순 표기가 아니라 뒷단계 스킬들이 "요구 몇 번이 설계 어디에 반영됐나" 를 찾아가는 연결 고리다. 세 가지 안을 비교했다.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| 유지 | `FR-1` 그대로 두고 나머지 코드만 금지 | 뒷단계 스킬 무변경 | 영문 약어가 본문에 남음 |
| 제거 | 번호 자체를 없앰 | 코드 완전 소멸 | 뒷단계 연결 고리가 사라져 전면 재설계 필요 |
| 교체 (채택) | `요구 1` 한국어 번호로 바꿈 | 읽기 좋고 연결 고리 유지 | 번호를 읽는 스킬들 동시 수정 필요 |

교체안을 채택한다 (사용자 결정). 번호를 읽는 스킬들은 이번에 함께 수정하고, 이미 작성된 옛 문서의 `FR-N` 번호도 계속 읽을 수 있게 하위 호환을 유지한다.

### 기술설계서 다이어그램은 도면 방식으로 그린다

노드와 화살표를 나열하는 워크플로우 그림 대신, 구역과 배치가 보이는 도면 방식을 기본으로 한다. 문서가 마크다운이므로 쓸 수 있는 형식은 세 가지이고, 상황에 맞게 골라 쓴다 (사용자 결정).

| 형식 | 쓰는 상황 |
|---|---|
| 아스키 박스 도면 | 구역·레이어 배치를 보여줄 때. 터미널·GitHub·에디터 어디서든 보임 |
| mermaid 다이어그램 | 렌더링 환경 (GitHub, VS Code 미리보기) 이 전제되고 관계가 복잡할 때 |
| 아스키 도면 + 표 조합 | 큰 그림은 도면으로, 세부는 도면에 번호를 달고 표에서 설명할 때 |

어떤 상황에 어떤 형식을 쓰는지 판단 기준을 스킬 본문에 박는다. 기준이 없으면 매번 형식이 흔들린다.

### 규칙은 스킬 본문에 직접 넣는다

스타일 규칙을 어디에 둘지 세 가지 안을 비교했다.

| 안 | 내용 | 판단 |
|---|---|---|
| 스킬 본문에 직접 (채택) | 문서를 만드는 스킬 4개의 본문에 작성 규칙 섹션 추가 | 이 저장소 스킬은 자기 완결이 원칙. 앞선 문체 규칙도 같은 방식으로 넣었음 |
| 공용 스타일 파일 분리 | 별도 파일 하나를 네 스킬이 참조 | 이 저장소에 없는 참조 패턴을 새로 만들게 됨 |
| 검사 스크립트 추가 | 금지 패턴을 기계로 검사 | 한국어 문체를 기계로 판정하기 어려움. 코드 패턴 검사 정도만 보조로 검토 가능 |

## 요구 항목

**요구 1**: 요구사항서와 기술설계서는 위에서 아래로 한 번에 읽혀야 한다. 용어는 처음 등장하는 자리에서 설명하고, 아래 내용을 먼저 읽어야 이해되는 표현을 쓰지 않는다.

**요구 2**: 두 문서의 본문은 간결한 자연어로 쓴다. 비유법을 쓰지 않는다. 핵심과 무관한 서술을 넣지 않는다.

**요구 3**: 나열·비교·구조 설명은 산문 대신 표나 다이어그램으로 표현한다.

**요구 4**: 두 문서의 본문에 알파벳-숫자 항목 코드를 쓰지 않는다. 요구 항목 번호는 `요구 N` 형식을 쓴다.

**요구 5**: 요구 항목 번호를 읽는 뒷단계 스킬들은 `요구 N` 형식을 인식하고, 이미 작성된 옛 문서의 `FR-N` 형식도 계속 읽는다.

**요구 6**: 기술설계서의 다이어그램은 도면 방식을 기본으로 한다. 아스키 박스 도면 / mermaid / 아스키 도면 + 표 조합 세 형식 중 상황에 맞게 고르는 판단 기준을 스킬 본문에 둔다.

**요구 7**: 정식 경로 (`brainstorming`, `tech-design`) 와 자동 경로 (`auto-brainstorming`, `auto-tech-design`) 에 같은 규칙을 함께 적용한다.

## 범위 밖

| 제외 항목 | 이유 |
|---|---|
| 구현계획서 스타일 | 이번 요청은 요구사항서·기술설계서 두 문서에 한정 |
| 가벼운 원본 흐름 (og) 의 산출물 스타일 | 원본 흐름은 손대지 않는 것이 원칙. 형식을 설명하는 비교 문구 한 줄만 사실에 맞게 갱신 |
| 이미 작성된 문서의 소급 수정 | 새로 쓰는 문서부터 적용. 옛 문서는 하위 호환으로 계속 읽힘 |
| 스킬 본문 자체의 영어 식별자·내부 코드 | 스킬 본문은 에이전트가 읽는 코드에 해당. 바꾸는 것은 산출물의 스타일 |

## 우려와 해결

| 우려 | 해결 |
|---|---|
| 옛 문서의 `FR-N` 이 안 읽히게 됨 | 번호를 읽는 스킬에 옛 형식 하위 호환을 명시 (요구 5) |
| 정식·자동 두 경로의 문체가 갈림 | 두 경로 동시 수정 (요구 7) |
| 도면 형식이 매번 흔들림 | 형식 선택 판단 기준을 스킬 본문에 고정 (요구 6) |
| 코드 주석 금지 규칙과의 충돌 | 코드 주석에 문서 식별자를 못 쓰게 하는 기존 규칙이 새 번호 형식 (`요구 N`) 도 막아야 하는지는 기술설계에서 판단 |
