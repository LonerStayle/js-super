# 개발방향: PRD 제거 + 소크라테스 고도화

> **다음 단계 안내**: 이 문서는 기술 설계서입니다 (아키텍처 / 컴포넌트 / 데이터 / 인터페이스 / 결정 / 위험 / 테스트 전략). `prd제거-소크라테스고도화-requirements.md` 를 기반으로 작성됩니다. 3개 트랙이면 다음 단계 `<slug>-implementation-plan.md` (단계별 계획) 의 입력이 됩니다 (`writing-plans` skill 또는 `/write-plan` 슬래시). 2개 확정 트랙 (frontmatter `depth: 2`) 이면 이 문서가 마지막 산출물입니다. 단계별 구현 task 는 여기 박지 마세요 — 그건 다음 산출물 (plan) 에 들어갑니다.

## 1. 아키텍처 개요

### 1-1. 현재 구조

`skills/brainstorming/SKILL.md` 는 진입 후 갈래가 둘로 나뉘고, 그 뒤로도 분기가 계속 따라다닙니다.

```
진입
 └─ Entry Router (og 안내 / js-super 풀 트랙)
     └─ 컨텍스트 탐색 → 슬러그 확정
         └─ 모드 선택 게이트  ← 사용자 질문
             ├─ PRD 경로
             │   ├─ 카테고리 미니질문
             │   ├─ Visual Companion (엄격 트리거)
             │   ├─ 질문 계획 동의 게이트
             │   └─ 적응형 질문 (루브릭 표 기반)
             └─ 소크라테스 경로
                 ├─ Visual Companion (느슨 트리거)
                 └─ 자유 대화 (지시 5줄)
                     ↓
              자체 점검 (모드별로 항목이 다름)
                     ↓
              승인 게이트 → 변경이력 → tech-design
```

분기는 갈림길 하나에서 끝나지 않습니다. 자체 점검이 모드별로 갈리고, 흐름도 노드에 `[PRD]` / `[Socratic]` 접두가 붙고, 안티 패턴 표와 경고 표에도 PRD 전제 행이 섞여 있습니다. 문장 하나하나가 "다른 모드와의 대비"로 쓰여 있는 상태입니다.

### 1-2. 이후 구조

갈래를 없애고 한 줄기로 만듭니다.

```
진입
 └─ Entry Router (og 안내 / js-super 풀 트랙)   ← 그대로 유지
     └─ 컨텍스트 탐색 → 슬러그 확정
         └─ 소크라테스 절차 (단일 경로)
             ├─ 블록 1  질문
             ├─ 블록 2  대안
             ├─ 블록 3  문서 작성
             └─ 블록 4  승인
                 ↓
          자체 점검 (단일 목록)
                 ↓
          승인 게이트 → 변경이력 → tech-design
```

Entry Router 는 건드리지 않습니다. 이것은 "가벼운 흐름이냐 풀 트랙이냐"를 가르는 갈림길이라 이번에 없애는 "문서를 어떤 틀로 쓰느냐"와 층이 다릅니다.

### 1-3. 소크라테스 절차 4블록

현재 5줄짜리 절차를 네 블록으로 다시 씁니다. 블록 경계는 "무엇이 끝나야 다음으로 가는가"로 나눴습니다.

**블록 1 — 질문.** 한 번에 하나씩 묻습니다. 개수 상한은 두지 않고, 대신 무엇이 채워지면 멈추는지를 적습니다. 사용자가 "모르겠다"고 답할 때의 대처를 포함합니다.

**블록 2 — 대안.** 2~3안을 고정 비교축으로 제시하고 추천을 먼저 말합니다. 고른 이유와 버린 이유를 문서에 남깁니다.

**블록 3 — 문서 작성.** 자유 산문을 유지하되 요구 항목 섹션 하나만 필수입니다. 대화 중 나온 제외 항목을 모아 되돌려주는 절차가 여기 들어갑니다.

**블록 4 — 승인.** 초안 전체를 한 번에 보여주고 승인받습니다. 섹션마다 끊지 않습니다.

### 1-4. 문서 형식 계약

산출물에서 고정되는 것은 넷입니다.

| 요소 | 규정 |
|---|---|
| H1 제목 | `# 요구사항: <피처명>` |
| 요구 항목 섹션 | `## 요구 항목` — 이름 고정, 항목마다 `FR-N` |

| 나머지 섹션 | 자유. 대화에서 나온 대로 |

모드 표기 줄은 사라집니다 (D1 참조).

## 5. 핵심 결정 + 대안 비교

### D1 — 모드 표기 줄을 없앤다

산출물 상단의 `> **모드**: Socratic ...` 줄을 제거합니다.

**대안 (가) 단일 문자열로 고정** — 표기를 남기되 한 가지로 통일하고, `tech-design` 감지자를 그 문자열에 맞춥니다. 실측에서 3종으로 갈렸던 문제는 해결됩니다. 다만 모드가 하나뿐인데 모드를 표기하는 셈이라 곧 아무도 안 읽는 줄이 됩니다.

**대안 (나) 제거 — 채택.** 갈래가 사라지므로 표기할 모드가 없습니다. 감지자도 함께 없어지니 문자열 불일치 문제가 원인째 사라집니다.

제거해도 되는 근거는 옛 문서와 새 문서가 `FR-N` 이라는 같은 앵커를 공유한다는 점입니다. `tech-design` 이 두 형식을 구분할 이유가 없어집니다.

### D2 — 요구 항목 섹션 하나만 필수로 한다

`## 요구 항목` 섹션과 항목마다 `FR-N` 을 강제하고, 나머지 섹션은 자유로 둡니다.

**대안 (가) 아무것도 강제하지 않음** — 지금 상태입니다. 실측에서 섹션 이름이 세 갈래로 갈라졌고 다운스트림 검증이 조용히 통과하는 결과를 낳았습니다.

**대안 (나) 최소 3섹션 강제 (배경 / 요구 항목 / 범위 밖)** — 형식이 더 잡히지만 축소판 PRD에 가까워집니다. 배경과 범위 밖은 절차(블록 1, 블록 3)로 유도하면 자연히 쓰이므로 형식으로 강제할 필요가 낮습니다.

**대안 (다) 요구 항목 하나만 — 채택.** 다운스트림이 실제로 필요한 것은 셀 수 있는 앵커 하나입니다. 나머지는 절차로 유도하고 형식으로 묶지 않습니다.

### D3 — 질문 종료 판정을 목록 충족으로 정의한다

개수 상한 대신 "무엇이 채워졌는가"로 판정합니다. 커버 목록은 다섯 가지입니다.

1. 무엇을 만드는가 (대상과 범위)
2. 왜 필요한가 (해결하려는 문제)
3. 성공을 어떻게 아는가 (판정 가능한 기준)
4. 무엇을 하지 않는가 (명시적 제외)
5. 무엇이 걸림돌인가 (제약과 의존)

다섯 가지가 다 채워지면 질문을 멈춥니다. 사용자가 먼저 "그만"이라고 하면 채워진 것까지만 쓰고, 빈 항목은 문서에 "미정 — 이유"로 남깁니다.

**대안 (가) 개수 상한** — `auto-brainstorm` 방식입니다. 단순하지만 사안의 무게와 무관하게 잘립니다. 사용자가 상한 없음을 선택했으므로 채택하지 않습니다.

**대안 (나) 목록 충족 — 채택.** 무거운 사안에서는 자연히 길어지고 가벼운 사안에서는 짧게 끝납니다. 판정 기준이 겉으로 드러나 사용자가 진행 상황을 압니다.

### D4 — 대안 비교축을 셋으로 고정한다

2~3안을 제시할 때 비교축을 매번 새로 정하지 않고 셋으로 고정합니다.

- 무엇이 달라지는가
- 무엇을 포기하는가
- 되돌리는 비용

그리고 추천을 먼저 말한 뒤 이유를 답니다. 추천안이 깨지는 조건 하나를 스스로 제시합니다.

**대안 (가) 자유 서술** — 지금 상태입니다. "2~3개 제시" 한 줄뿐이라 비교의 질이 매번 다릅니다.

**대안 (나) 고정 3축 — 채택.** 세 축은 저장소의 기존 문서들이 실제로 쓰던 축이라 새 개념이 아닙니다. 되돌리는 비용을 축에 넣은 이유는 스킬 본문 수정처럼 되돌리기 쉬운 작업과 데이터가 얽힌 작업을 같은 무게로 다루지 않기 위해서입니다.

### D5 — "모르겠다" 대처를 3단 사다리로 둔다

사용자가 모른다고 답하거나 질문 자체를 되물으면 순서대로 내려갑니다.

1. 질문을 더 쉬운 말로 바꿔 다시 묻습니다.
2. 그래도 막히면 선택지를 만들어 고르게 합니다.
3. 그래도 막히면 기본값을 제안하고 "이대로 갈지"만 확인합니다. 그 기본값이 무엇을 전제하는지 한 줄 덧붙입니다.

**대안 (가) 규정 없음** — 지금 상태입니다. 사용자가 막히면 대화가 그 자리에서 멈춥니다.

**대안 (나) 3단 사다리 — 채택.** 마지막 단계에서 진행이 보장되고, 전제를 밝혀두므로 나중에 되짚을 수 있습니다.

### D6 — PRD 자산은 절차 안으로 흡수한다

없애는 190줄 중 모드와 무관한 것 셋은 소크라테스 절차 안으로 옮깁니다.

| 자산 | 옮길 곳 | 이유 |
|---|---|---|
| 범위 밖 항목 취합 룰 | 블록 3 (문서 작성) | 제외 항목이 대화에서 증발하는 것을 막는 장치. 틀과 무관 |
| 기술 세부 누출 방지 점검 | 자체 점검 | 요구사항에 구현이 섞이는 것을 막는 장치. 틀과 무관 |
| 다음 단계 안내 배너 | 문서 형식 | 산출물 2개/3개 트랙 안내를 담고 있어 소크라테스 문서에도 필요 |

**대안 (가) 함께 폐기** — 가장 깔끔하지만 세 장치 모두 실제로 값을 하던 것들입니다. 특히 범위 밖 취합 룰이 없으면 대화 중 나온 제외가 문서에 안 남습니다.

**대안 (나) 흡수 — 채택.**

### D7 — 자체 점검을 한 목록으로 합친다

지금은 자체 점검이 두 곳에 나뉘어 있고 (소크라테스용 축약 4항목, 전체용 10항목) 모드에 따라 적용 범위가 갈립니다. 이를 단일 목록으로 합칩니다.

남길 항목은 여섯입니다 — 미완성 표현, 내부 모순, 범위 과다, 중의적 표현, 제외 항목 취합 여부, 기술 세부 누출. 앞의 넷은 기존 추상 점검이고 뒤의 둘은 PRD에서 가져옵니다.

버리는 항목은 사용자 스토리 3요소 점검과 비기능 요구 구체성 점검입니다. 둘 다 6섹션 틀에 묶인 항목이라 틀이 사라지면 가리킬 대상이 없습니다.

**대안 (가) 소크라테스용 축약 목록만 남기기** — 지금 소크라테스 경로가 쓰던 4항목을 그대로 두고 나머지를 지웁니다. 가장 손이 적게 갑니다. 다만 제외 항목 취합과 기술 세부 누출 점검이 함께 사라져 D6에서 흡수하기로 한 자산이 반쪽만 살아납니다.

**대안 (나) 10항목 전체를 남기고 틀 관련 항목만 무력화** — 문구를 최소로 건드립니다. 대신 가리킬 대상이 없는 항목이 목록에 남아 읽는 쪽이 헷갈립니다. 점검 목록에 죽은 항목이 섞이면 목록 전체의 신뢰가 떨어집니다.

**대안 (다) 6항목 단일 목록 — 채택.** 두 곳에 나뉜 중복이 없어지고, 흡수하기로 한 자산이 점검 단계에서도 실제로 작동합니다.
