# 요구사항: PRD 제거 + 소크라테스 고도화

> **다음 단계 안내**: 이 문서는 요구사항(무엇을 만들지)만 담습니다. 다음 단계로 `tech-design` skill (또는 `/tech-design` 슬래시) 을 호출해서 `<slug>-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요.

## 배경

`brainstorming` 스킬은 진입할 때마다 "PRD 방식으로 쓸까요, 소크라테스 방식으로 쓸까요"를 묻습니다. 이 게이트를 없애고 소크라테스 하나로 단일화하는 것이 이번 작업의 목적입니다.

조사 결과 두 가지가 이 방향을 지지합니다.

**게이트는 이미 한쪽으로 기울어 있습니다.** `docs/features/` 의 요구사항 문서 27개 중 PRD 형식은 6개, 소크라테스 형식이 19개입니다. 소수 경로를 위해 `skills/brainstorming/SKILL.md` 629줄 중 약 190줄과 `tech-design` 의 이중 분기를 계속 유지하고 있는 셈입니다.

**소크라테스 쪽은 정작 규정이 없습니다.** 본문 43줄 중 실질 절차는 5줄입니다. 질문 종료 판정도, 대안 비교 규격도, 산출물 형식도 없습니다. 같은 저장소의 `auto-brainstorming` 과 `/fast-tasks` 가 오히려 촘촘합니다. 정식 흐름만 무경계입니다.

그 결과 실제 산출물이 갈라졌습니다. 요구 항목 섹션 이름이 문서마다 `## 요구 항목` / `## 기능 요구` / 부재로 나뉘고, 모드 표기 줄도 3종 변종이 생겼습니다. 자유가 필요해서 생긴 편차가 아니라 계약이 없어서 생긴 드리프트입니다.

**이미 조용히 깨진 것도 둘 있습니다.**

`tech-design` 은 입력 형식을 감지할 때 영어 문자열 `> **Mode:** Socratic` 을 찾는데 실제 템플릿은 한국어 `> **모드**: Socratic` 입니다. 1차 감지는 항상 빗나가고 폴백으로만 살아 있습니다.

`verifying-spec` 은 "모든 FR 항목을 개발방향 문서에 매핑하라"를 검증 축으로 삼는데, 번호가 없는 19개 문서에서는 매핑 대상이 0건이라 검사가 조용히 통과합니다. 산출물 2개 트랙에서는 이것이 유일한 정합성 게이트여서 손실이 더 큽니다.

따라서 이번 작업은 "PRD를 걷어낸다"에서 끝나지 않습니다. 걷어내면서 소크라테스 쪽에 없던 계약을 채우고, 이미 깨져 있던 두 지점을 같이 고칩니다.

## 핵심 결정

작업 방향에 대해 다음을 확정했습니다.

**결정 1 — PRD는 탈출구 없이 완전히 제거합니다.** `--prd` 같은 플래그로 남기지 않습니다. 6섹션 템플릿, 적응형 질문 계획, 카테고리 루브릭, 모드 선택 게이트가 모두 사라집니다.

**결정 2 — 요구 항목에는 번호 앵커를 유지하고, 이름은 `FR-N` 을 그대로 씁니다.** 자유 산문은 유지하되 요구 항목 섹션 하나만 필수로 둡니다. 이름을 바꾸지 않는 이유는 두 가지입니다. 다운스트림 네 곳(`verifying-spec` / `writing-plans` / `change-propagation` / `tech-design`)의 참조를 건드리지 않아도 되고, 기존 문서 6개와 그대로 이어집니다. 후보였던 `R-N` 은 개발방향 문서에서 이미 위험 항목 번호로 쓰이고 있어 탈락했습니다.

**결정 3 — 질문 개수에 상한을 두지 않습니다.** 대신 종료 판정 기준을 명확히 합니다. "아이디어가 잡힐 때까지"라는 현행 한 문장을 판정 가능한 기준으로 교체합니다.

**결정 4 — 승인은 초안 전체를 한 번에 받습니다.** 섹션마다 승인받는 upstream 방식은 채택하지 않습니다. 승인 알람이 늘어나는 것이 게이트 절제 방향과 맞지 않습니다.

**결정 5 — 옛 PRD 형식 문서 6개의 하위호환은 앵커 공유로 해결합니다.** 결정 2에 따라 새 문서도 `FR-N` 을 갖게 되므로, 옛 문서와 새 문서가 같은 앵커를 공유합니다. 섹션 번호(`§3` 등)에 매달린 서술만 "요구 항목이 있는 곳"으로 느슨하게 풀면 형식 감지 분기 자체가 필요 없어집니다. 옛 문서를 새 형식으로 옮기는 작업도 하지 않습니다.

**결정 6 — 이미 낡은 테스트 예제 정리는 이번 범위에 넣지 않습니다.** H1과 H2는 og 스킬 삭제로, H5는 generating-html 강등으로 기대값이 무효인 상태입니다. PRD와 원인이 달라 섞으면 변경 범위가 흐려집니다.

## 요구 항목

### 제거

**FR-1**: `brainstorming` 스킬에서 모드 선택 게이트를 제거한다. 진입 시 사용자에게 방식을 묻지 않는다.

**FR-2**: PRD 전용 블록을 삭제한다. 대상은 6섹션 문서 스키마, 적응형 질문 계획(카테고리 미니질문 · 질문 계획 동의 · 루브릭 표), PRD 전용 자체 점검 6항목, 흐름도의 PRD 분기 노드와 엣지, PRD를 전제한 안티 패턴과 경고 표 행이다.

**FR-3**: 스킬 frontmatter 의 설명문에서 두 모드 선언을 제거한다. 이 문장은 매 세션 컨텍스트에 상주하며 자동 발동 판정 근거로 쓰인다.

### 이식

**FR-4**: PRD에만 있던 모드 중립 자산을 소크라테스 절차로 옮긴다. 대상은 범위 밖 항목 취합 룰(대화 중 나온 제외 항목을 모아 되돌려주고 추가분만 묻는 규정), 기술 세부사항이 요구사항 문서로 새는 것을 막는 자체 점검 항목, 문서 상단의 다음 단계 안내 배너(산출물 2개/3개 트랙 안내 포함)다.

### 계약 신설

**FR-5**: 소크라테스 산출물에 요구 항목 섹션을 필수로 규정하고 항목마다 `FR-N` 을 부여한다. 그 외 섹션 이름과 구성은 자유를 유지한다.

**FR-6**: 산출물 상단의 모드 표기 줄을 정리한다. PRD가 사라져 모드 개념이 없어지므로 표기 줄 자체를 없애거나 단일 문자열로 고정한다. 어느 쪽이든 실제 템플릿과 이를 읽는 쪽의 문자열이 일치해야 한다.

### 대화 고도화

**FR-7**: 질문 종료 판정 기준을 신설한다. 개수 상한은 두지 않는다. 무엇이 채워지면 질문을 멈추는지를 판정 가능한 형태로 적는다.

**FR-8**: 질문 커버 목록을 신설한다. 현행은 목적·제약·성공 기준 세 단어뿐이다. `auto-brainstorming` 의 질문 패턴 5종이 저장소 안 참고 원본이다.

**FR-9**: 대안 제시 규격을 신설한다. 고정 비교축과 추천을 먼저 제시하는 순서, 그리고 탈락한 안과 그 이유를 산출물에 남기는 의무를 포함한다.

**FR-10**: 사용자가 "모르겠다"고 답할 때의 대처를 규정한다. 현행 본문에는 이 경로가 없다.

### 다운스트림 정합

**FR-11**: `tech-design` 의 입력 형식 감지 분기를 정리한다. 결정 5에 따라 두 형식이 같은 앵커를 공유하므로 분기를 없애고 단일 경로로 만든다. 섹션 번호에 의존하는 서술은 "요구 항목이 있는 곳"으로 푼다.

**FR-12**: `tech-design` 에서 테스트 전략 토픽을 켜는 신호가 "FR 개수 3개 이상"인 부분이 계속 동작하는지 확인하고, 필요하면 신호를 바꾼다.

**FR-13**: `auto-brainstorming` 의 산출물 뼈대에 있는 모드 표기 줄을 FR-6의 결정과 맞춘다. auto 계열은 자동 동기되지 않는 별도 사본이므로 짝으로 수정해야 한다.

### 사용자 문서

**FR-14**: 사용자 시야에 노출되는 문구를 갱신한다. 대상은 `/brainstorm` 커맨드 설명, README의 슬래시 명령 표와 확인 게이트 표(게이트 개수 표기 포함), `/og-brainstorm` 커맨드의 정식 흐름 비교표다. 비교표는 정식이 소크라테스가 되면 대비 자체가 성립하지 않으므로 다시 써야 한다.

**FR-15**: `CLAUDE.md` 에 이번 변경의 결합 메모를 추가하고, 모드 게이트 존재를 전제한 기존 서술을 갱신한다.

**FR-18**: 산출물을 나열하는 공용 문구에서 첫 산출물을 "PRD" 라고 부르는 표현을 "요구사항" 으로 바꾼다. 같은 문장이 `brainstorming` · `tech-design` · `writing-plans` 세 스킬에 복제되어 있어 함께 처리한다. 모드를 가리키는 표현은 아니지만 이름이 남으면 수용 기준 2의 판정이 흐려진다.

### 회귀 검증

**FR-16**: 소크라테스 흐름을 검증하는 테스트 예제를 신규 작성한다. 현재 저장소 전체에 소크라테스 검증 예제가 0건이다.

**FR-17**: 착수 전에 보존 대상 문자열을 확정하고, 작업 후 그대로 남아 있는지 확인한다. 대상은 `--no-ask` 플래그 섹션 제목(네 개 파일이 문자열로 참조), 모호 응답 처리 규정, 진입 라우터의 안내 문구, auto 계열 체인 호출 문자열, `visual-companion.md` 경로다.

## 범위 밖

- 낡은 테스트 예제 H1 / H2 / H5 정리 — 원인이 달라 별도 배치로 진행
- 기존 PRD 형식 요구사항 문서 6개의 형식 이전 — 끝난 피처의 기록이라 손대지 않음
- `/og-brainstorm` 커맨드 자체의 존폐 판단 — 비교표 갱신(FR-14)까지만 하고 커맨드 정리는 별도 판단
- `auto-*` 4개 스킬의 대화 절차 변경 — 모드 표기 줄 동기(FR-13)만 하고 절차는 그대로
- `scripts/` 와 `hooks/` — PRD 의존이 0건이라 변경 없음
- 6개 manifest 버전 올리기 — 워크트리 세션에서는 하지 않음

## 수용 기준

1. `brainstorming` 진입 시 방식을 묻는 질문이 뜨지 않는다.
2. 현행 스킬과 커맨드 본문에 PRD 모드를 가리키는 문자열도, 첫 산출물을 PRD라고 부르는 표현도 남지 않는다. 두 가지는 제외한다 — 과거 사실을 적은 버전 이력, 그리고 이 저장소의 다른 스펙 문서를 가리키는 참조(`auto-flow-requirements.md` 를 PRD라고 부르는 `auto-brainstorming` 8행, `js-super-sub-driven` 181행의 결정 코드 인용).
3. 이 흐름으로 새로 만든 요구사항 문서에 요구 항목 섹션과 `FR-N` 이 있다.
4. `tech-design` 이 요구사항 문서를 읽을 때 형식 감지 없이 단일 경로로 동작한다.
5. 옛 PRD 형식 문서 6개를 `tech-design` 에 넣어도 요구 항목을 읽어낸다.
6. FR-17의 보존 문자열이 작업 전후로 동일하다.
7. 소크라테스 흐름 검증 예제가 저장소에 존재한다.
8. 소크라테스 절차 본문에 질문 종료 판정 기준, 질문 커버 목록, 대안 비교축, "모르겠다" 대처가 각각 명시되어 있다.
