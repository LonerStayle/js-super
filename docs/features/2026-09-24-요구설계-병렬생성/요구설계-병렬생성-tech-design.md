# 개발방향: 요구설계-병렬생성

> **다음 단계 안내**: 이 문서는 기술 설계서입니다. 다음 단계로 `writing-plans` skill (또는 `/write-plan` 슬래시) 을 호출해 `요구설계-병렬생성-implementation-plan.md` 를 만드세요.

## 1. 아키텍처 개요

새 흐름은 명령 하나와 그 명령이 부르는 스킬 하나로 이뤄진다. 스킬은 대화와 승인은 메인이 직접 하고, 두 문서의 작성만 보조 에이전트 둘에게 동시에 맡긴다. 문서 형식과 작성 규칙은 새로 적지 않고, 기존 요구사항 스킬과 기술설계 스킬의 본문을 작성 에이전트가 직접 읽게 한다.

```
┌──────────────────────── 메인 세션 ────────────────────────┐
│ ① 새 명령 → ② 새 스킬 진입                                   │
│   ③ 큰 작업 맥락 읽기 (있을 때만)                             │
│   ④ 통합 질문 대화 (요구사항 커버 목록 + 기술설계 토픽)       │
│   ⑤ 대화 요약 작성 ──────────────┐                          │
└─────────────────────────────────┼──────────────────────────┘
               ┌────────────────┴────────────────┐
               ▼                                 ▼
   ┌───────────────────────┐        ┌───────────────────────┐
   │ ⑥ 요구사항 작성 에이전트 │        │ ⑦ 기술설계 작성 에이전트 │
   │  기존 요구사항 스킬 규칙  │        │  기존 기술설계 스킬 규칙  │
   │  작성 + 자체 점검        │        │  작성 + 자체 점검 + 서술  │
   └───────────┬───────────┘        │  수준 점검              │
               │                    └───────────┬───────────┘
               └────────────────┬────────────────┘
┌───────────────────────────────┼───────────────────────────┐
│ ⑧ 사양 정합성 검증 (대상: 기술설계, 상위: 요구사항)            │
│ ⑨ 두 문서 + 검증 보고서 한 번에 승인                          │
│ ⑩ 두 문서 각각 첫 변경이력 → ⑪ 깊이 선택                      │
└───────────────────────────────────────────────────────────┘
```

| 번호 | 역할 | 동시 실행 |
|---|---|---|
| ①② | 명시 호출 진입. 명령은 스킬에 위임만 한다 | 아니오 |
| ③ | 진행 중인 큰 작업이 있으면 큰 그림과 이월 항목을 보여주고 소속 표식을 기억 | 아니오 |
| ④ | 한 번에 한 질문. 대안 비교와 추천 먼저. 두 문서의 빈칸이 다 차면 종료 | 아니오 |
| ⑤ | 대화에서 정한 것을 두 에이전트가 같은 입력으로 받도록 한 덩어리로 정리 | 아니오 |
| ⑥⑦ | 문서 작성과 각 문서의 자체 점검 | 예 — 한 메시지에서 동시 호출 |
| ⑧ | 기존 검증 스킬 그대로. 요구사항서가 있어야 대조가 가능하므로 ⑥⑦ 뒤에 돈다 | 검증 스킬 안에서 무맥락 검증자 둘이 동시에 돈다 |
| ⑨~⑪ | 승인 한 번, 변경이력 두 건, 기존 깊이 선택 | 아니오 |

검토의 동시 실행 범위는 이렇다. 두 문서의 자체 점검은 각 작성 에이전트 안에서 동시에 돈다. 사양 정합성 검증은 기술설계서를 요구사항서와 대조하는 일이라 요구사항서 완성을 기다려야 한다 — 요구 10 이 허용한 유일한 순서다. 기존 흐름에서 요구사항서는 자체 점검만 받으므로, 새 흐름도 요구사항서에 추가 검증을 붙이지 않는다.

## 4. 외부 인터페이스

사용자가 치는 명령은 `/brainstorm-design <주제>` 하나다.

| 플래그 | 동작 | 출처 |
|---|---|---|
| `--no-clean-verify` | 검증 단계의 무맥락 검증자 둘을 끈다 | 검증 스킬의 기존 플래그를 그대로 전달 |

`--no-ask` 는 지원하지 않는다. 그 플래그의 적용 범위는 여러 스킬에 걸친 결합 룰로 고정돼 있고, 새 흐름에 넣으면 그 룰의 검사 개수까지 함께 바뀐다. 필요해지면 별도 변경으로 넣는다.

산출물 경로는 기존과 같다 — `docs/features/<날짜>-<slug>/<slug>-requirements.md` 와 `<slug>-tech-design.md`.

## 5. 핵심 결정 + 대안 비교

### 명령과 스킬의 구성

| 안 | 달라지는 것 | 포기하는 것 | 되돌리는 비용 |
|---|---|---|---|
| **명령 + 숨긴 스킬 (채택)** | 스킬이 자기 폴더의 지시문 파일 두 개를 읽을 수 있다 | 스킬 설명이 세션마다 상주한다 | 파일 추가만이라 삭제로 끝 |
| 명령 하나에 전부 인라인 | 상주 비용 없음 | 슬래시 명령 환경에서는 플러그인 경로가 안 채워져 지시문 파일을 찾을 수 없다. 두 지시문과 절차가 한 파일에 몰려 길어진다 | 같음 |

스킬은 불릴 때 자기 폴더 경로를 받으므로 옆 파일을 확실히 읽을 수 있다. 검증 스킬이 무맥락 검증자 지시문을 같은 방식으로 읽는다. 스킬은 메뉴에서 숨겨 같은 기능이 두 번 보이지 않게 한다. 모델 호출 차단 표시는 명령에만 둔다 — 스킬에 두면 명령의 위임이 끊긴다.

명령 이름과 스킬 폴더 이름은 다르게 짓는다. 같으면 명령이 스킬을 가려 호출이 실패한다.

### 문서 형식 규칙의 출처

| 안 | 달라지는 것 | 포기하는 것 | 되돌리는 비용 |
|---|---|---|---|
| **기존 스킬 본문을 작성 에이전트가 직접 읽음 (채택)** | 형식 규칙의 원본이 하나로 유지된다. 기존 스킬을 고치면 새 흐름도 따라간다 | 작성 에이전트가 어느 섹션을 읽을지 지시문에 섹션 이름으로 적어야 한다 | 지시문 두 파일 수정 |
| 새 스킬에 형식 규칙 사본 | 에이전트가 파일 하나만 읽으면 된다 | 사본이 원본과 어긋나기 시작한다. 결합 메모와 회귀 검사가 네 곳으로 늘어난다 | 사본을 지우고 참조로 바꾸는 작업 |

메인은 새 스킬 폴더 경로에서 한 단계 위로 올라가 두 기존 스킬 본문의 절대 경로를 만들고, 그 경로를 지시문에 넣는다. 에이전트가 읽을 섹션은 아래 제목 문자열로 지정한다. 두 스킬의 이 제목이 바뀌면 지시문도 바꿔야 한다 — 결합 메모에 제목 목록과 존재 검사를 둔다.

| 작성 에이전트 | 읽을 파일 | 읽을 섹션 제목 (문자열 그대로) |
|---|---|---|
| 요구사항 | `skills/brainstorming/SKILL.md` | `## Document Schema` · `## 산출물 문서 스타일` · `## Self-Review` |
| 기술설계 | `skills/tech-design/SKILL.md` | `## Schema` · `## 산출물 문서 스타일` · `### 도면 형식` · `## 서술 수준 — 이름보다 역할` · `## Self-Review` |

제목은 앞부분 일치로 찾는다 (`## Document Schema` 뒤에 괄호 설명이 붙어 있다). 토픽 활성 판정 섹션 (`## Adaptive Topics`) 은 작성 에이전트가 읽지 않는다. 판정은 메인이 대화 전에 한 번 하고 결과만 요약에 싣는다 (아래 "통합 대화의 범위").

단점 하나가 남는다. 에이전트가 기존 스킬 본문 전체를 읽으면 대화 절차와 승인 게이트 문장도 함께 읽는다. 지시문 첫머리에 "그 스킬을 실행하지 말고 지정한 섹션만 규칙으로 쓴다, 사용자에게 묻지 않는다" 를 못박는다.

### 대화 요약의 전달 방식

| 안 | 달라지는 것 | 포기하는 것 | 되돌리는 비용 |
|---|---|---|---|
| **지시문 안에 텍스트로 붙임 (채택)** | 피처 폴더에 새 파일이 생기지 않는다 | 요약이 대화 기록에만 남는다 | 없음 |
| 피처 폴더에 요약 파일 저장 | 나중에 다시 볼 수 있다 | 변경이력 대상인지 판단이 새로 필요하고, 다음 단계 스킬이 이 파일을 모른다 | 파일 규약 추가 후 철회 |

두 에이전트는 **똑같은 요약 텍스트**를 받는다. 요구 8 (두 문서의 결정 일치) 의 1차 장치다. 2차 장치는 사양 정합성 검증의 대조다.

요약에는 커버 목록 다섯 항목의 답, 정한 결정과 버린 안과 이유, 제외 항목, 기술설계 토픽 활성 판정 결과와 토픽별 결정, 큰 작업 소속 표식 (있을 때) 을 넣는다. 소속 표식은 요구사항 에이전트만 요구사항서 머리에 쓴다 — 기존 요구사항 스킬과 같은 위치다. 기술설계서에는 넣지 않는다. 요구 항목 번호는 메인이 요약 단계에서 매긴다. 기술설계 에이전트가 요구사항서 없이도 영향 파일 표에 요구 번호를 적을 수 있어야 하기 때문이다. 요구사항 에이전트는 그 번호를 그대로 쓴다.

### 통합 대화의 범위

기존 요구사항 스킬의 질문 네 블록 (질문 · 대안 · 문서 · 승인) 을 따르되, 커버 목록을 두 문서 분량으로 넓힌다.

| 묶음 | 채울 것 |
|---|---|
| 요구사항 | 무엇을 · 왜 · 성공 기준 · 제외 · 제약 (기존 다섯 항목) |
| 기술설계 | 아키텍처 방향 · 영향 범위 · 핵심 결정 (대안 비교) · 위험 · 조건부 토픽 (데이터 모델 / 외부 인터페이스 / 테스트 전략) 중 활성인 것 |

피처 이름과 폴더는 대화 첫 질문으로 정한다. 기존 요구사항 스킬과 같이 이름에서 slug 를 만들고, 메인이 `docs/features/<날짜>-<slug>/` 폴더를 대화 시작 전에 만든다. 두 작성 에이전트는 각자 쓸 파일의 절대 경로를 지시문으로 받는다.

기술설계 토픽의 활성 판정은 대화 시작 전에 메인이 기존 기술설계 스킬의 `## Adaptive Topics` 섹션 규칙으로 한 번 하고 한 줄로 알린다. 질문은 기존 정식 흐름처럼 선택지 도구로 묻는다. 질문 개수 상한은 없다 (요구 4). 사용자가 먼저 그만하자고 하면 채워진 것까지만 요약하고 빈칸은 "미정 — 이유" 로 넘긴다.

### 작성 에이전트 호출 규칙

- 두 호출을 한 메시지에 묶는다. 나눠 부르면 대기 시간이 합쳐져 병렬의 의미가 없다.
- 모델 인자를 넘기지 않는다. 메인 모델을 상속한다. 문서 작성은 판단이 많은 일이라 낮은 등급을 쓰지 않는다.
- 에이전트는 파일을 쓰고 자체 점검까지 마친 뒤 "완료 / 점검에서 고친 것 / 남은 미정" 을 보고한다. 변경이력은 쓰지 않는다 — 승인 전이라 쓸 이력이 없다.
- 실패와 처리를 이렇게 나눈다. 실패 사실은 어느 경우든 승인 게이트 보고에 적는다.

| 상황 | 처리 |
|---|---|
| 에이전트가 오류로 끝남 / 파일을 쓰지 않음 / 보고 세 항목이 빠짐 | 그 한쪽만 한 번 다시 부른다. 두 번째도 같으면 메인이 기존 스킬 규칙대로 직접 쓴다 |
| 지정한 섹션 제목을 못 찾았다고 보고함 | 다시 불러도 같으므로 재시도하지 않는다. 에이전트는 이 경우 파일을 쓰지 않고 멈춘다. 메인이 직접 쓴다 |

### 승인과 수정

승인 게이트는 기존 기술설계의 결합 승인 게이트와 같은 모양이다. 두 문서 전체와 검증 보고서를 한 메시지에 싣고, 승인 / 수정 두 선택지를 묻는다. 수정 요청은 메인이 직접 고친다. 한 문서의 결정을 고치면 다른 문서의 같은 결정도 함께 고친 뒤 다시 전체를 보여준다. 어느 문서든 바뀌면 사양 정합성 검증을 다시 돌린다. 요구사항만 고쳐도 두 문서의 대조 결과가 달라질 수 있기 때문이다.

승인 뒤에는 요구사항서에 요구사항 수정 이력을, 기술설계서에 개발방향 수정 이력을 각각 한 건씩 남긴다. 그다음 기존 깊이 선택과 같은 세 선택지를 묻고, 각 선택의 동작도 기존과 같다 (구현계획서 스킬 호출 / 두 문서 확정 표식 기록 / 표식 없이 종료).

## 6. 위험/사이드이펙트

| 위험 | 영향 | 대응 |
|---|---|---|
| 기존 스킬 섹션 이름이 바뀜 | 작성 에이전트가 규칙을 못 찾고 추측으로 쓴다 | 지시문에 "섹션을 못 찾으면 보고에 적는다" 를 넣고, 결합 메모에 섹션 이름 목록과 회귀 검사를 둔다 |
| 작성 에이전트가 기존 스킬의 대화 절차를 따라 함 | 사용자에게 질문하거나 다음 스킬을 부른다 | 지시문 첫머리 금지 문장. 에이전트에게는 사용자 질문 도구가 없다는 점도 명시 |
| 두 문서의 결정 불일치 | 기술설계가 요구사항과 어긋난다 | 같은 요약 입력 + 사양 정합성 검증의 대조 |
| 명령과 스킬 이름 충돌 | 스킬 호출 불가 | 이름을 다르게 짓고 충돌 검사 명령을 결합 메모에 둔다 |
| 스킬이 메뉴에 노출 | 같은 기능이 메뉴에 두 번 | 스킬 머리에 메뉴 숨김 표시. 숨김 목록 검사 개수를 13 에서 14 로 올린다 |
| 대화 요약이 커서 지시문이 길어짐 | 에이전트가 앞머리 규칙을 놓친다 | 금지 문장을 지시문 맨 앞에 두고 요약은 맨 뒤에 붙인다 |
