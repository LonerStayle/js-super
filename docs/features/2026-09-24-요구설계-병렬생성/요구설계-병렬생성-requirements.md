# 요구사항: 요구설계-병렬생성

> **다음 단계 안내**: 이 문서는 요구사항 (기획 단계) 입니다. 다음 단계로 `tech-design` skill (또는 `/design-tech` 슬래시) 을 호출해서 `요구설계-병렬생성-tech-design.md` (기술 설계서) 를 만드세요. 기술 결정이나 구현 세부사항은 여기 박지 마세요.

## 배경

지금의 정식 흐름은 문서마다 대화를 따로 한다. 요구사항 대화로 요구사항서를 만들고, 그 문서를 읽고 기술설계 대화를 다시 시작해 기술설계서를 만든다. 문서 하나가 끝나야 다음 문서의 대화가 시작되므로 전체가 오래 걸린다.

사용자는 처음부터 두 문서를 함께 만든다고 보고, 질문을 한 번의 대화로 몰아서 끝내기를 원한다. 질문이 길어지는 것은 괜찮다. 대화가 끝나면 두 문서를 동시에 작성하고, 문서별 검토도 동시에 돌려 기다리는 시간을 줄인다.

## 핵심 결정

| 결정 지점 | 고른 안 | 버린 안 | 고른 이유 |
|---|---|---|---|
| 새 흐름의 위치 | 기존 흐름 옆에 새 진입 명령을 하나 추가 | 기존 요구사항 명령이 두 문서를 만들도록 교체 | 되돌리기 쉽고 두 방식을 비교할 수 있다. 품질을 확인한 뒤 교체를 다시 판단한다 (사용자 결정) |
| 승인 방식 | 두 문서와 검증 보고서를 한 번에 보여주고 한 번 승인 | 문서별로 따로 승인 | 요구사항을 고치면 기술설계도 다시 봐야 해서 따로 승인해도 결국 두 번 확인한다 (사용자 결정) |
| 승인 뒤 진행 | 기존 기술설계의 깊이 선택을 그대로 묻는다 | 두 문서로 무조건 종료 | 구현계획서가 필요한 피처와 아닌 피처가 섞여 있다. 기존 선택지를 재사용하면 새 규칙이 생기지 않는다 (사용자 결정) |
| 자동 흐름 적용 | 이번 범위에서 제외 | 자동 흐름에도 같은 병렬 작성 추가 | 사용자가 요구한 것은 질문이 긴 정식 흐름이다. 자동 흐름은 질문이 1~5개라 대화 통합의 이득이 작다 (AI 판단) |

## 흐름

```
└─────────────┬──────────────┘
              │ 대화 요약
      ┌───────┴────────┐
      ▼                ▼
┌───────────┐    ┌───────────┐
│ ② 요구사항 │    │ ③ 기술설계 │   동시에 작성 + 각자 검토
│  작성·검토 │    │  작성·검토 │
└─────┬─────┘    └─────┬─────┘
      └───────┬────────┘
              ▼
┌────────────────────────────┐
│ ④ 두 문서 + 검증 보고서 한 번에 승인 │
└─────────────┬──────────────┘
              ▼
┌────────────────────────────┐
│ ⑤ 변경이력 기록 → 깊이 선택   │  구현계획서까지 / 두 문서로 종료 / 나중에
└────────────────────────────┘
```

## 요구 항목

### 진입

**요구 1**: 기존 요구사항 명령과 기술설계 명령 옆에 두 문서를 함께 만드는 새 진입 명령이 있어야 한다. 기존 두 명령의 동작은 바뀌지 않는다.

**요구 2**: 새 진입 명령은 명시 호출로만 시작되어야 한다. 대화 중 자동으로 시작되지 않는다.

### 통합 질문 대화

**요구 3**: 질문 대화는 한 번만 진행되며, 요구사항서와 기술설계서 두 문서를 쓰는 데 필요한 내용을 모두 다뤄야 한다. 대화가 끝난 뒤 문서 작성 단계에서 사용자에게 추가 질문을 하지 않는다.

**요구 4**: 질문 개수에 상한이 없어야 한다. 두 문서에 필요한 항목이 다 채워졌을 때 대화를 끝낸다.

**요구 5**: 방향을 정해야 하는 지점마다 대안을 비교해 보여주고 추천을 먼저 말하는 기존 정식 흐름의 대화 방식을 따른다. 기술적 결정 지점도 이 방식으로 대화 안에서 정한다.

### 동시 작성

**요구 6**: 대화가 끝나면 요구사항서와 기술설계서를 두 개의 보조 에이전트가 동시에 작성해야 한다.

**요구 7**: 두 문서는 기존 정식 흐름이 만드는 문서와 같은 형식이어야 한다. 이후 단계 (구현계획서 작성, 검증, 변경 전파) 가 기존 문서와 구분 없이 읽을 수 있어야 한다.

**요구 8**: 두 문서가 같은 대화에서 나온 결정을 서로 어긋나지 않게 담아야 한다.

### 문서별 검토

**요구 9**: 기존 정식 흐름이 문서마다 하던 검토 (자체 점검, 사양 정합성 검증) 를 새 흐름에서도 빠짐없이 수행해야 한다.

**요구 10**: 검토는 문서별로 동시에 진행되어야 한다. 한 문서의 검토가 다른 문서의 완성을 반드시 기다려야 하는 경우에만 순서를 둔다.

### 승인과 이후 진행

**요구 11**: 두 문서와 검증 보고서를 한 번에 보여주고 한 번 승인받아야 한다. 수정 요청이 오면 고친 뒤 다시 한 번에 보여준다.

**요구 12**: 승인 뒤 두 문서 각각에 첫 변경이력을 기록해야 한다.

**요구 13**: 변경이력 기록 뒤 기존 기술설계의 깊이 선택 (구현계획서까지 진행 / 두 문서로 종료 / 나중에 결정) 을 같은 의미로 물어야 한다.

## 범위 밖

| 항목 | 이유 |
|---|---|
| 기존 요구사항 명령과 기술설계 명령의 교체·수정 | 옆에 두기로 결정. 품질 확인 후 별도로 판단 |
| 자동 흐름 (auto 계열) 에 병렬 작성 추가 | 이번 요구는 질문이 긴 정식 흐름 대상 |
| 구현계획서의 동시 작성 | 구현계획서는 두 문서가 승인된 뒤 기존 방식으로 만든다 |
| 기존 피처 문서의 소급 변경 | 새로 만드는 피처부터 적용 |

## 우려와 해결

| 우려 | 해결 방향 |
|---|---|
| 기술설계 검증은 요구사항서와 대조하는데, 동시에 쓰면 대조할 문서가 아직 없다 | 요구 10 의 예외에 해당한다. 대조가 필요한 검증만 두 문서가 끝난 뒤 돈다. 구체 순서는 기술설계에서 정한다 |
| 두 작성 에이전트가 같은 결정을 다르게 옮겨 적을 수 있다 | 요구 8. 두 에이전트가 같은 대화 요약을 입력으로 받고, 검증 단계에서 두 문서의 결정이 일치하는지 본다 |
| 대화가 길어져 사용자가 지칠 수 있다 | 사용자가 먼저 그만하자고 하면 채워진 것까지만 쓰고 빈 항목은 미정으로 남긴다 (기존 정식 흐름 규칙 답습) |
