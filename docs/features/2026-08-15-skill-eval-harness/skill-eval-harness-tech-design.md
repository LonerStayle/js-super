## 1. 아키텍처 개요

### 1-1. 한 줄 요약

파이썬 러너가 뼈대입니다. 결합 룰은 복제하지 않고 `CLAUDE.md` 를 실행 시점에 직접 파싱해서 씁니다. 케이스는 마크다운 파일 앞머리에 메타데이터를 얹고 본문은 원문 그대로 둡니다.

세 후보를 실현 가능성·유지 비용·안전성 세 렌즈로 채점했고, 렌즈마다 이긴 안을 그 지점에서 채택했습니다.

| 갈린 지점 | 채택 | 이유 |
|---|---|---|
| 격리를 무엇이 강제하는가 | 러너 코드 | 격리가 문서 문장이나 케이스 데이터면 케이스 하나의 오기로 뚫립니다. 러너가 위험 등급에서 격리 수준을 도출하면 케이스가 격리를 낮출 수 없습니다 |
| 자산이 썩는 속도 | 원문 보존 형식 | [실측] 이 저장소의 스킬 커밋 154건 대 fixture 커밋 30건입니다. 안 읽히는 자산은 안 고쳐집니다. 순수 데이터 형식으로 재작성하면 사람이 읽는 문서 성격이 사라집니다 |
| 정답 원천 | `CLAUDE.md` 단일 | 결합 룰을 복제하면 정답이 둘이 됩니다. [실측] `CLAUDE.md` 는 3.5개월에 54회 갱신됐습니다. 복제본은 매 릴리즈마다 어긋날 기회를 갖습니다 |

### 1-5. 승인 게이트를 관측할 수 없다는 한계

[실측] `claude -p` 가 알려주는 도구 목록 125개에 `AskUserQuestion` 이 **없습니다** (플래그 조합 6가지를 모두 확인). 즉 "승인 게이트를 실제로 띄웠는가" 를 도구 호출 기록으로 확인할 수 없습니다.

대체 신호 셋으로 근사합니다.

1. 게이트 지점 이후 다음 단계 도구 호출이 0건인가 — 기계 판정
2. 게이트를 건너뛴 흔적(파일 생성, git 조작)이 없는가 — 기계 판정
3. 최종 응답이 선택지를 제시하는가 — 모델 판정 (앞 둘이 통과했을 때만)

이 구멍은 어떤 설계로도 메워지지 않습니다. `CLAUDE.md` 의 결합 섹션 최소 3개가 정확히 이 지점을 주장하고 있어서, 그 주장들은 근사로만 검증됩니다. 요구사항 §8 범위 밖에 명시했습니다.

## 3. 데이터 모델/스키마 변경

### 3-1. 케이스 파일

마크다운 파일 앞머리에 YAML 메타데이터를 얹고, `---` 아래는 기존 fixture 본문을 그대로 둡니다. [실측] `pyyaml` 이 이미 `requirements-dev.txt` 에 선언되어 있어 파서를 자작하지 않습니다.

```markdown
---
id: js-super-sub-driven/H11-user-edit-reorder   # 소유 스킬/지역 id — 번호 충돌 해소
title: 사용자 중간 수정 후 재정렬 호출
status: active            # active | stale | wip | blocked
layer: [B, C]
covers:
  - skills/js-super-sub-driven/SKILL.md
  - skills/js-super-sub-driven/reorder-prompt.md
danger: '-'               # - | C | B | A  → 러너가 격리 수준을 도출
est: {s: 120, usd: 0.3}   # 실행 기록이 덮어씀
reply:                    # 무인 실행 시 사용자 응답 대신 넣을 값 (없으면 생략)
  - {at: '모드 선택', value: 'PRD'}
expect:
  - {kind: tool, op: eq, name: Task, value: 2}
  - {kind: file, op: exists, path: 'docs/features/*/plan.md'}
---

(기존 README 본문을 그대로 복사. 사람이 읽는 시나리오 설명)
```

필수 6개는 `id`, `title`, `status`, `layer`, `covers`, `expect` 입니다. 선택 항목은 `run`, `danger`, `seed`, `est`, `repeat`, `priority`, `couples`, `schema_version`, `traceability` 입니다. `run` 이 없으면 Claude 를 안 띄우는 비용 0 케이스입니다.

단언은 다섯 종류입니다. `shell`, `file`, `tool`, `text`, `judge`. 비교 연산은 `eq`, `gte`, `lte`, `zero`, `lines_eq`, `exists`, `capture` 입니다. 자연어 기대값 9건이 `capture` 로 증거를 잡고 그 안에 `judge` 를 중첩하는 자리입니다.

`shell` 단언은 **인자 배열로만 쓰고 셸을 거치지 않습니다.** 자유 문자열을 허용하지 않습니다. 이유는 §5 D5 에 있습니다.

`reply` 는 무인 실행을 위한 항목입니다. 커맨드 여러 개가 사용자 응답을 기다리며 멈추는데, 사람이 붙어 있지 않으므로 미리 답을 넣어둡니다. `--no-ask` 플래그를 받는 커맨드 8개는 그 플래그로 대신할 수 있고, 나머지는 이 항목으로 처리합니다.

### 3-2. baseline.json

관측값과 사람의 판단을 분리하는 게 핵심입니다. 요구사항 결정 8 이 여기 대응합니다.

```json
{"schema_version": 1,
 "cases": {
   "<id>": {"verdict": "fail", "label": "regression-open", "reason": "...", "commit": "6c3191d"}}}
```

`verdict` 는 그때 실제로 관측된 값이고 `label` 은 사람이 붙인 판단입니다. 라벨은 `confirmed`, `regression-open`, `stale`, `blocked`, 그리고 라벨 없음(신규·미분류)입니다. **라벨 없는 항목은 통과로 집계되지 않습니다.**

소요 시간·비용·토큰은 담지 않습니다. [실측] 같은 종류 호출이 1,703밀리초와 30,058밀리초로 갈릴 만큼 편차가 커서 회귀 판정에 못 씁니다. 그 값들은 실행 기록과 케이스의 `est` 에만 씁니다.

### 3-3. 모델 판정 캐시

`verdicts/<id>.json` 에 `{verdict, reason, evidence_quote, evidence_sha256, judged_at, mode}` 를 담습니다. 증거 해시가 달라지면 캐시를 버리고 다시 판정합니다. 판정 캐시를 커밋하므로 사람이 리뷰할 수 있습니다.

### 3-4. 실행 상태 10종

`PASS` / `FAIL` / `REGRESSION` / `KNOWN` / `FIXED` / `NEW` / `NOT-SELECTED` / `DEFERRED` / `BLOCKED` / `PENDING`.

뒤 넷은 통과로 집계되지 않습니다. 이걸 문서 규칙이 아니라 pytest 커스텀 판정 상태로 만들어 코드가 강제합니다. 요구사항 수용 기준 5가 여기 대응합니다.

### 4-2. 관측하는 신호

이벤트 스트림에서 다음을 읽습니다. 전부 [실측] 확인했습니다.

- `tool_use{name, input}` — 어떤 도구를 어떤 인자로 불렀는가
- `result{is_error, duration_ms, total_cost_usd, stop_reason, terminal_reason, permission_denials, usage}`
- `init{slash_commands, skills, plugins, tools}` — 무엇이 로드됐는가
- `system{hook_started, hook_response}` — 훅 발화

세션 기록 파일(`~/.claude/projects/<경로>/<uuid>.jsonl`)에서 추가로 `attributionSkill`, `attributionPlugin`, `toolUseResult`, `isSidechain`, `parentUuid` 를 읽습니다. 전부 [실측] 확인했습니다.

**미검증**: 보조 에이전트(`Task`)를 쓸 때의 `parent_tool_use_id` 구조와 비용 귀속. 1차의 사전 실측 항목입니다.

### 4-4. 모델 판정도 같은 인터페이스를 씁니다

요구사항 결정 2 에 따라 모델 판정에 외부 LLM API 를 붙이지 않습니다. 판정이 필요한 항목은 **같은 `claude` 명령줄 도구를 한 번 더 띄워서** 처리합니다. 새 의존성도, 새 인증도, 새 청구 경로도 생기지 않습니다.

판정 세션은 검증 대상과 반대로 띄웁니다. 플러그인 경로를 주지 않고 사용자 설정도 차단합니다. 이유는 두 가지입니다. 검증 중인 스킬이 판정자에게 영향을 주는 경로를 끊고, 판정 세션의 컨텍스트 비용을 줄이기 위해서입니다.

판정 결과는 근거 인용과 함께 캐시에 저장합니다 (§3-3). 같은 증거면 다시 부르지 않습니다.

### 4-3. 파일시스템 계약

격리 사본은 임시 디렉토리 안에 만듭니다. **원본 저장소는 읽기만 합니다.** 실행 전후로 `git rev-parse HEAD` 와 `git status --porcelain` 을 비교해 다르면 실행 전체를 무효로 처리합니다.

**격리 준비가 안 되면 실행하지 않습니다.** 위험 등급이 붙은 케이스는 하위 프로세스를 띄우기 직전에 다음을 확인하고, 하나라도 어긋나면 프로세스를 아예 안 띄우고 차단 상태로 보고합니다.

- 현재 작업 디렉토리가 임시 루트 아래인가
- 임시 경로가 실제 저장소 경로를 포함하지 않는가 (심링크·상대경로 우회 차단)
- 사본이 실제로 만들어졌고 원본 지문이 기록됐는가

임시 디렉토리 삭제는 종료 시 반드시 실행합니다. 중간에 끊겨도 남지 않도록 걸어둡니다. [실측] 같은 패턴이 `tests/opencode/setup.sh:76-79` 에 이미 있습니다.

홈 디렉토리는 격리하지 않습니다. 요구사항 결정 4 를 따릅니다.

## 8. 확정된 충돌 처리

`H17` fixture 와 `CLAUDE.md` 가 같은 명령에 다른 기대값을 갖고 있었습니다. 한쪽은 0건, 다른 쪽은 3건을 기대합니다.

**`CLAUDE.md` 의 3건을 정본으로 확정했습니다** (사용자 결정). `H17` fixture 는 이관 시 `status: stale` 로 표시하고 실패 집계에서 제외합니다.

근거는 [실측] `CLAUDE.md` 가 54회 갱신되며 유지된 반면 fixture 는 30회에 그쳤다는 빈도입니다. 강한 근거는 아니므로, 나중에 `H17` 쪽이 맞았다는 게 드러나면 fixture 의 `status` 를 되돌리고 `CLAUDE.md` 룰을 고치면 됩니다. 어느 쪽도 지우지 않습니다.

같은 종류의 충돌이 또 생기면 검사 단계(S3)가 로드 시점에 잡아 실행을 거부합니다. 러너가 임의로 한쪽을 고르는 일은 없습니다.
