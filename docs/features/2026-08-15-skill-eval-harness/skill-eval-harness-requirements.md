# 요구사항: 스킬 검증 환경 (skill-eval-harness)

> **모드**: Socratic (자유 형식). 다음 단계의 `tech-design` 가 본 문서를 자유 형식 산문으로 읽습니다 (PRD 6 섹션 ID 강제 X).

> **다음 단계 안내**: 이 문서는 기획 레벨 요구사항입니다. 기술 결정과 구현 세부사항은 다음 산출물 (`skill-eval-harness-tech-design.md`) 에 들어갑니다.

---

## 1. 배경

js-super 는 스킬 29개와 커맨드 24개로 에이전트 행동을 바꾸는 플러그인입니다. 스킬 본문 한 줄이 곧 실행 코드라서, 문장 하나를 고치면 다른 흐름이 조용히 깨질 수 있습니다.

그런데 지금 그걸 잡아낼 방법이 없습니다. 저장소에 자동으로 도는 테스트는 `scripts/tests/` 의 pytest 6개 모듈 54개 함수뿐이고, 그 대상은 순수 파이썬 헬퍼 함수입니다. 스킬 자체의 행동은 하나도 검증하지 않습니다.

`skills/*/tests/` 아래 fixture 43개가 있지만 전부 사람이 읽는 문서입니다. 실행 코드가 읽는 것은 그중 한 개(`F1-basic-batch`)뿐입니다. 나머지 42개는 눈으로 비교합니다.

`tests/` 아래에 실제로 Claude 를 띄워서 스킬 발동을 확인하는 bash 하네스가 있긴 합니다. 다만 upstream 에서 상속한 것이라 대상이 6개 스킬이고, js-super 고유 스킬은 하나도 들어 있지 않습니다. 2026-05-02 이후 손대지 않았고 CI 도 없어서, 지금 통과하는지조차 근거가 없습니다.

`CLAUDE.md` 는 결합 회귀를 잡으라고 grep 룰 116개를 문서에 박아뒀습니다. 하지만 그걸 돌리는 건 사람 손입니다.

### 이 환경을 만들면서 이미 확인된 사실

요구사항을 쓰기 위해 결합 룰 116개를 전수로 실제 실행해봤습니다. 101개가 통과하고 **9개가 실패**했으며 6개는 명령 자체가 돌지 않았습니다. 실패 9건 중 최소 1건은 진짜 회귀입니다 (`generating-html` 의 "적극 시각화 v2.2.3" 마커가 사라짐). 나머지는 룰이 낡았거나 기대값이 자연어라 숫자 비교로 판정되지 않는 경우입니다.

즉 검증 환경이 없어서 못 잡고 있던 회귀가 실제로 존재했습니다.

## 2. 해결하려는 문제

세 가지입니다.

**첫째, 고친 뒤 회귀를 모릅니다.** 스킬 본문을 수정하면 결합된 다른 스킬이나 커맨드가 깨질 수 있는데, 확인하려면 `CLAUDE.md` 의 grep 룰 116개를 손으로 돌려야 합니다.

**둘째, 발동 여부를 모릅니다.** 새 스킬이 의도한 상황에서 실제로 불리는지, 반대로 안 불려야 할 때 조용히 있는지 확인할 방법이 없습니다. 후자가 특히 취약합니다. auto 계열 4개와 워크트리 계열 2개는 frontmatter 플래그가 아니라 **description 안 자연어 문구로만** 자동 발동을 막고 있습니다. 자연어 차단은 확률적이라 한 번 돌려서는 판정이 안 됩니다.

**셋째, 흐름 완주를 모릅니다.** 브레인스토밍부터 실행까지 4단계가 끝까지 도는지 매번 손으로 돌려봐야 합니다.

## 3. 검증 대상 범위

전수로 잡습니다. 실측 규모는 다음과 같습니다.

| 대상 | 수 | 비고 |
|---|---|---|
| 스킬 (`SKILL.md`) | 29 | |
| 스킬이 런타임에 읽는 자산 | 36 | 프롬프트 파일 6개 + 스크립트(`server.cjs`, `setup-memory-symlinks.sh` 등) |
| 커맨드 | 24 | `commands/*.md` 25개 중 `audit-report-prompt.md` 는 프롬프트 자산 |
| 서브에이전트 정의 | 1 | `agents/code-reviewer.md` |
| 훅 | 2 | `session-start`, `worktree-memory-symlink` |
| 결합 회귀 룰 | 116 | `CLAUDE.md` 90 + fixture README 26 |
| 기존 fixture 문서 | 44 | 스킬 아래 43 + `commands/audit-risk-tests/H23-e2e` 1 |

**커버리지 전수와 실행 전수는 다릅니다.** 커버리지 전수는 위 목록의 모든 대상에 케이스가 등록되어 있다는 뜻입니다. 실행 전수는 매번 전부 돌린다는 뜻입니다. 이 환경은 커버리지는 전수로 가되, 매 실행은 영향 범위만 골라 돌립니다. 이유는 6절에 있습니다.

## 4. 네 가지 검증 층위

**발동했는가.** 자연어 프롬프트를 줬을 때 올바른 스킬이 불리는가. 안 불려야 할 때 안 불리는가. 케이스 59건 (스킬 35 + 커맨드 24) 으로 잡힙니다. 실제로 Claude 를 띄워야 판정됩니다.

**절차를 지켰는가.** 불린 뒤에 승인 게이트를 제대로 띄우는가, 단계 순서를 지키는가, 금지된 행동을 하지 않는가. 판정점 92개 (게이트 21 + Checklist 항목 71) 가 13개 스킬에 걸쳐 있습니다. 실제 실행이 필요합니다.

**산출물이 맞는가.** 약속된 경로에 약속된 구조로 파일이 나오는가. 변경이력 footer, 위험 주석, 파일명 규칙까지 봅니다. 스킬 20개와 커맨드 23개가 대상입니다. 절차 검사를 돌릴 때 같이 확인하면 되므로 추가 실행 비용이 없습니다.

**결합이 깨졌는가.** `CLAUDE.md` 의 회귀 룰 116건. 파일 텍스트만 보면 되므로 실제 실행이 필요 없고 수 분에 끝납니다.

## 5. 핵심 결정

**결정 1. eval 자산은 사용자 컨텍스트에 노출되지 않는다.**
이 환경은 저장소를 개발하는 쪽만 씁니다. 플러그인 사용자는 쓸 일이 없습니다. Claude Code 가 자동으로 읽어들이는 곳은 `skills/`, `commands/`, `agents/`, `hooks/hooks.json` 네 곳이므로, eval 자산을 여기 두면 사용자 세션에 스킬 설명이 상주하거나 슬래시 목록에 뜹니다.

이미 사고가 하나 나 있습니다. `commands/audit-risk-tests/H23-e2e/` 아래 테스트 문서가 실제로 슬래시 커맨드로 등록되는 것이 실측됐습니다. 이 환경을 만들면서 같이 정리합니다.

`marketplace.json` 의 `source` 가 `./` 라서 저장소 파일은 어차피 전부 사용자 PC 에 복사됩니다. 노출을 막는 기준은 "파일이 안 가는가" 가 아니라 "로드되지 않는가" 입니다.

**결정 2. 판정은 기계와 모델을 섞되, 모델 판정은 Claude Code 가 한다.**
파일 존재, 호출 기록, 문서 구조처럼 눈에 보이는 건 기계가 판정합니다. 절차를 지켰는지, 자연어 기대값을 만족했는지처럼 판단이 필요한 건 모델이 판정합니다. 다만 그 모델 판정을 외부 LLM API 로 붙이지 않고 Claude Code 가 직접 수행합니다. js-super 가 의존성 없는 플러그인이라는 성격을 유지하기 위해서입니다.

**결정 3. 실행은 영향 범위 기반으로 고른다.**
결합 검사와 산출물 검사는 항상 전수로 돌립니다. 무거운 발동 검사와 절차 검사는 이번에 고친 대상이 영향을 주는 범위만 골라 돌립니다. 영향 범위는 `CLAUDE.md` 의 결합 섹션 23개가 이미 문서화해둔 매핑을 그대로 씁니다.

이 결정의 대가는 명확합니다. 결합 메모에 안 적힌 간접 영향은 못 잡습니다. 즉 이 환경의 정확도는 결합 메모의 정확도에 묶입니다.

**결정 4. 위험 대상도 격리해서 실제로 돌린다. 단 홈 디렉토리는 격리하지 않는다.**
파일을 지우거나 git 을 건드리는 커맨드가 15개 있습니다. 그중 4개는 회복 불가 등급입니다. `/remove-worktree --force` 는 머지 안 된 브랜치를 강제 삭제하고, `/andrej-init` 은 프로젝트 루트의 `CLAUDE.md` 를 덮어씁니다. 이것들을 문면 검사로만 넘기면 실제 동작 버그를 못 잡으므로, 임시 저장소를 만들어 그 안에서 진짜로 실행합니다.

홈 디렉토리(`~/.claude/`)는 격리하지 않습니다. 홈을 임시 디렉토리로 바꾸면 그 안에 로그인 정보가 없어서 `claude` 가 실행되지 않고, 되살리려면 별도 API 키가 필요합니다(실측). 대신 홈을 건드리는 커맨드를 다음과 같이 처리합니다.

- `/new-skill` — `--project` 플래그로 임시 프로젝트 폴더에 쓰게 해서 검증합니다. 홈에 쓰는 갈래는 `--dry-run` 으로 안내문만 확인합니다.
- `/remove-skill` — 실행 검증에서 제외합니다(사용자 결정). 문면 검사만 합니다.

이 결정의 대가는 명확합니다. 홈에 실제로 쓰거나 지우는 동작은 검증되지 않은 채 남습니다.

**결정 5. 기존 자산은 데이터만 흡수하고 실행 코드는 버린다.**
기존 fixture 43개의 시나리오 지식, `tests/` 의 프롬프트 15개, `CLAUDE.md` 의 룰 116건은 새 공통 형식으로 옮깁니다. 반면 기존 bash 판정 로직은 버립니다. 세션 경로를 역산하는 방식, 네임스페이스가 `superpowers:` 로 굳어 있는 점, 독립 grep 두 개로 판정하는 방식 모두 지금 구조에 안 맞습니다.

실제 작업량은 "기존 것 고치기" 가 아니라 **43개 문서의 기대값을 실행 가능한 케이스로 번역하기** 입니다.

`scripts/tests/` 의 pytest 54개 함수는 예외입니다. 무료로 항상 돌릴 수 있으므로 그대로 흡수해 항상 전수로 실행합니다.

**결정 6. 케이스는 하나의 공통 형식으로 통일한다.**
지금 fixture 는 세대별로 형식이 제각각입니다. 섹션 이름도 다르고, 기대값이 산문·체크박스·bash 명령·코드펜스로 흩어져 있습니다. 게다가 번호가 충돌합니다 (`H14`, `H15`, `H17` 이 각각 두 스킬에서 중복). 새 형식은 네 층위를 모두 표현할 수 있어야 하고, 식별자는 소유 스킬을 포함해 전역에서 유일해야 합니다.

**결정 7. 낡은 케이스는 지우지 않고 표시한다.**
기존 fixture 중 최소 5건은 지금 구조와 안 맞습니다 (삭제된 og 스킬 참조 등). 이걸 그대로 옮기면 항상 실패하는 케이스가 5건 생깁니다. 지우는 대신 "낡음" 상태로 표시해서, 실패 집계에서 빼되 존재는 남깁니다.

**결정 8. 정답 라벨은 현재 실행 결과를 그대로 굳히지 않는다.**
결합 룰 실패 9건을 "원래 그런 것" 으로 라벨링하면 진짜 회귀 1건이 정답으로 박제됩니다. 라벨을 정하기 전에 9건을 회귀와 낡음으로 분류하는 작업을 반드시 거칩니다.

## 6. 제약

**시간.** 한 바퀴에 30분에서 1시간. 이걸 지키려면 실행 전수를 포기해야 합니다.

실측 근거는 이렇습니다. 발동 검사 59건에 케이스당 상한 300초, 흐름 검사 13건에 케이스당 600초에서 1800초입니다 (`docs/testing.md:32` 가 통합 테스트를 10분에서 30분으로 기록). 합치면 순차 실행 기준 2시간 10분에서 11시간 25분입니다. 비용은 하한이 $43.6 이고, 멀티턴과 보조 에이전트 비용이 얹히면 그 몇 배가 됩니다.

병렬로 줄이는 것도 지금은 안 됩니다. `--plugin-dir` 이 기존 플러그인에 더해지는 방식이라 격리 없이는 서로를 오염시킵니다.

**노출.** eval 자산은 `skills/`, `commands/`, `agents/`, `hooks/` 에 두지 않습니다 (결정 1).

**의존성.** 외부 LLM API 클라이언트를 새로 붙이지 않습니다 (결정 2). pytest 는 이미 `requirements-dev.txt` 에 선언되어 있으므로 개발 환경 설치를 전제로 합니다. 현재 이 워크트리에는 설치되어 있지 않습니다.

**격리와 기존 문서의 충돌.** `docs/testing.md:36` 은 테스트를 플러그인 디렉토리 안에서 돌리라고 못박고, `:38` 은 `~/.claude/settings.json` 의 개발용 마켓플레이스 설정에 의존합니다. 그런데 위험 커맨드를 안전하게 돌리려면 임시 디렉토리와 임시 홈으로 격리해야 합니다. 이 충돌은 지금 풀리지 않았고 기술 설계에서 해결해야 합니다.

**비결정성.** 산출물 경로에 날짜와 슬러그가 들어가고, 일부 산출물은 백그라운드로 생성되며, `.html` 은 gitignore 대상이라 git 으로 복원되지 않습니다. 스냅샷은 git 이 아니라 파일시스템 복사로 떠야 합니다.

**무인 실행.** 커맨드 여러 개가 `AskUserQuestion` 으로 사용자 응답을 기다립니다. 자동 실행하려면 응답을 케이스 입력으로 미리 넣을 수 있어야 합니다.

## 7. 수용 기준

1. 3절 표의 모든 대상에 케이스가 최소 1건 등록되어 있고, 등록되지 않은 대상이 있으면 실행 결과에 목록으로 표시된다.
2. 한 번의 기본 실행이 30분 안에 끝난다. 영향 범위가 넓어 늘어나더라도 1시간을 넘지 않는다.
3. 기본 실행에서 결합 룰 116건과 pytest 54개 함수가 항상 전수로 돌아간다.
4. 이번에 고친 대상을 지정하면 영향 범위에 해당하는 발동·절차 케이스가 자동으로 선택된다.
5. 실행할 때마다 어떤 케이스가 돌았고 어떤 케이스가 건너뛰어졌는지 명시적으로 보고한다. 건너뛴 것이 조용히 통과로 집계되지 않는다.
6. 이전 실행 결과와 비교해 새로 실패한 항목을 회귀로 구분해 보고한다.
7. 위험 등급이 붙은 케이스는 격리 환경 밖에서 실행되지 않는다. 격리 준비가 안 되면 실행을 거부한다.
8. eval 자산 중 어느 것도 Claude Code 의 자동 로드 경로에 존재하지 않는다. 이를 확인하는 검사가 스스로의 케이스로 등록되어 있다.
9. 기존 fixture 44건이 새 형식으로 옮겨져 있고, 낡은 것은 낡음으로 표시되어 실패 집계에서 제외된다.
10. 현재 실패 중인 결합 룰 9건이 회귀와 낡음으로 분류되어 있고, 진짜 회귀는 수정되었거나 별도 항목으로 남아 있다.
11. `commands/audit-risk-tests/` 가 슬래시 커맨드로 등록되지 않는 위치로 옮겨져 있다.

## 8. 범위 밖

- **커밋이나 PR 에서 자동으로 도는 게이트.** CI 를 이번에 만들지 않습니다. 로컬 수동 실행만 다룹니다.
- **두 버전을 비교하는 실험.** `docs/matt-pocock-강한단어-eval-plan.md` 에 있는 방식(두 버전을 각각 5회 돌려 비율 비교)은 이번 범위 밖입니다. 다만 케이스 형식에 나중에 표현할 자리는 남겨둡니다.
- **정기적인 전수 실행 스케줄.** 야간 배치나 릴리즈 게이트로 전수를 도는 운영은 이번에 정하지 않습니다.
- **플러그인 사용자에게 노출되는 기능.** 이 환경은 내부 전용입니다.
- **upstream superpowers 기여.** 이 저장소 안에서만 씁니다.
- **다른 하네스(Cursor, Codex, OpenCode, Gemini)에서의 검증.** 이번에는 Claude Code 기준만 다룹니다. 기존 `tests/opencode/` 와 `tests/codex-plugin-sync/` 를 흡수 대상에 넣을지는 기술 설계에서 정합니다.
- **성능이나 토큰 사용량 최적화 자체.** 실행 시간을 제약으로 다루긴 하지만, 스킬의 토큰 효율을 측정하는 것은 목적이 아닙니다.
- **`/remove-skill` 의 실행 검증.** 이 커맨드는 홈 디렉토리에서 `rm -rf` 를 실행하므로 안전하게 돌리려면 홈 격리가 필요한데, 홈 격리는 별도 API 키를 요구합니다. 실행 검증을 하지 않기로 했습니다(사용자 결정). 문면 검사만 남깁니다.
- **홈 디렉토리(`~/.claude/`)에 실제로 쓰거나 지우는 동작의 검증.** 위와 같은 이유입니다. 홈을 건드리는 커맨드는 프로젝트 범위로 우회하거나 미리보기만 확인합니다.
- **승인 게이트가 실제로 떴는지의 직접 확인.** 헤드리스 실행에서는 `AskUserQuestion` 이 발화하지 않는 것으로 실측됐습니다. 대체 신호로 근사할 뿐, 게이트 발화 자체를 직접 관측하지는 않습니다.

## 9. 기술 설계에서 정해야 할 것

요구사항 단계에서 답이 안 나온 항목입니다. 다음 문서에서 선택지를 비교해 정합니다.

1. **진입점을 어디에 둘 것인가.** 판정을 Claude Code 가 하려면 진입점이 필요한데, 가장 자연스러운 슬래시 커맨드가 결정 1의 금지 구역입니다. 저장소 로컬 `.claude/commands/` 는 사용자에게 안 가지만 `.gitignore` 에 걸려 커밋이 안 됩니다. gitignore 예외, 별도 디렉토리에 프롬프트를 두고 읽어서 실행, 설치 스크립트로 심링크 중 어느 쪽인지 정해야 합니다.
2. **격리를 어떻게 구성할 것인가.** `docs/testing.md` 가 요구하는 "플러그인 디렉토리 안에서 실행" 과 위험 커맨드 격리가 충돌합니다. 왜 플러그인 디렉토리 밖에서 못 도는지부터 다시 확인해야 합니다.
3. **결합 룰 116건에 층위를 붙일 것인가.** 지금은 룰 문면만으로 절차·산출물·결합을 기계 분류할 수 없습니다. 사람이 하나씩 태깅할지, 전부 결합으로 뭉뚱그릴지 정해야 합니다.
4. **`H17` fixture 와 `CLAUDE.md` 의 기대값 충돌에서 어느 쪽이 정본인가.** 같은 명령에 한쪽은 0건, 다른 쪽은 3건을 기대하고 있습니다.
5. **케이스 형식의 최종 스펙.** 네 층위, 격리 축, 사용자 응답 주입, 확률적 판정을 모두 표현해야 합니다. 초안은 조사 단계에서 나왔고 실제 fixture 6종으로 역검증했습니다.
6. **실제 소요 시간 실측.** 300초와 1800초는 기존 하네스가 잡아둔 상한일 뿐입니다. 대표 케이스 3~5건을 먼저 돌려 실제 소요와 비용을 재야 계획이 섭니다.
7. **승인 게이트 개수 재확인.** 조사에서 9개 스킬 21지점과 11개 스킬이라는 두 값이 나왔습니다.
