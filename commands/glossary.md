# /glossary — 문서 용어집 만들기

지정한 문서를 읽고, 거기 나오는 이름들 중 그 프로젝트를 처음 보는 사람이 멈출 만한 것을
실제 코드에서 확인해 `<slug>-glossary.md` 로 정리합니다.

대상 문서가 정본이고 용어집은 읽기를 돕는 파생 문서입니다. 용어집을 만드는 동안 대상 문서는
한 글자도 고치지 않습니다.

**시작할 때 사용자에게 알릴 말**: "문서에 나오는 이름들을 정리한 용어집을 만들고 있습니다."

## 1. 대상 정하기

`/glossary` 뒤에 붙은 인자를 다음 순서로 해석합니다.

| 인자 | 해석 |
|---|---|
| 파일 경로 (`docs/features/2026-08-29-잔액-출금/잔액-출금-tech-design.md`) | 그 파일 하나가 대상 |
| 피처 폴더 경로 또는 slug (`잔액-출금`) | 그 폴더 안 MD 전부가 대상 (용어집 자신은 제외) |
| 없음 | 아래 "인자 없이 부른 경우" 로 |

문서 종류에 제한이 없습니다. 요구사항 문서, 기술설계서, 구현계획서 어느 것이든 대상이 됩니다.
피처 폴더 밖의 일반 마크다운 문서도 됩니다.

대상 문서 옆에 `plan/` 폴더가 있으면 그 안의 문서들도 함께 읽습니다. 구현계획서는 task 가
10개를 넘으면 본문이 인덱스가 되고 task 상세와 코드가 그 폴더로 나뉘기 때문에, 인덱스만
읽으면 정작 이름이 등장하는 곳을 놓칩니다.

시점에도 제한이 없습니다. 문서에 `## 변경이력` 이 이미 쌓여 있어도 그대로 만듭니다.
용어집은 언제든 다시 만들 수 있는 파생 문서입니다.

### 인자 없이 부른 경우

`docs/features/` 아래에서 가장 최근에 수정된 폴더 세 개를 찾아 `AskUserQuestion` 으로
어느 것을 대상으로 할지 묻습니다. `docs/features/` 가 없는 프로젝트면 사용자가 문서 경로를
직접 알려주도록 묻습니다.

## 2. 저장 위치 정하기

`<slug>-glossary.md` 로 저장하며, 대상 문서와 같은 폴더에 둡니다.

slug 는 이렇게 정합니다.

- 피처 폴더가 대상이면 폴더 이름에서 날짜를 뗀 부분 (`2026-08-29-잔액-출금` → `잔액-출금`)
- 파일 하나가 대상이면 파일 이름에서 `-requirements` / `-tech-design` / `-implementation-plan`
  꼬리를 뗀 부분
- 어느 쪽도 아니면 파일 이름 그대로

같은 이름의 용어집이 이미 있으면 덮어씁니다. 덮어쓰기 전에 "기존 용어집을 새로 만듭니다"
한 줄을 알립니다. 별도 승인은 받지 않습니다 — 재생성이 이 문서의 성격입니다.

## 3. 보조 에이전트 호출

용어집 작성은 **반드시 보조 에이전트에게 맡깁니다.** 이름을 코드베이스에서 찾는 일은
Grep 과 Read 를 수십 번 부르는 작업이라 메인 대화에 그대로 쏟으면 컨텍스트가 넘칩니다.
결과물도 독립된 파일이라 돌아올 것은 짧은 요약뿐입니다.

`Agent` 도구를 다음 값으로 호출합니다.

- `subagent_type`: `general-purpose`
- `model`: `sonnet`
- `description`: `Glossary for <파일 이름>`
- `prompt`: 아래 템플릿에 경로를 채운 것

모델은 sonnet 으로 고정합니다. 처음 보는 사람이 어디서 막힐지 고르는 데 판단이 필요하지만
깊은 추론까지는 필요 없습니다. 더 낮은 등급은 열어보지도 않은 심볼의 설명을 지어냅니다.

### 보조 에이전트 프롬프트 템플릿

```
당신은 이 문서를 처음 읽는 개발자를 위한 용어집을 씁니다.

읽을 파일: <TARGET_ABSOLUTE_PATHS>
           (이 파일 옆 `plan/` 폴더에 상세 문서들이 있으면 그것도 함께 읽으세요. 코드 블록이 거기 있습니다.)
쓸 파일:   <GLOSSARY_ABSOLUTE_PATH>
프로젝트 루트: <REPO_ROOT>

# 독자 설정 (이게 전부입니다)

오늘 이 프로젝트에 처음 합류한 개발자가, 인수인계 문서 한 장만 받고 위 문서를
읽으려 합니다. 그 사람이 읽다가 "이게 뭐지" 하고 멈출 이름들을 미리 풀어주는 게
당신의 일입니다.

# 1단계 — 문서에서 이름 뽑기

대상 문서 전체를 읽고, 본문·표·코드 블록에 등장하는 다음을 모읍니다:

- 클래스 / 타입 / 인터페이스 이름
- 함수 / 메서드 이름
- 중요한 변수 / 상수 / 설정 키 이름
- 파일 / 모듈 이름 중 역할이 이름만으로 안 드러나는 것

문서 작성 규약이나 필드 형식 같은 것은 모으지 않습니다. 코드에 실제로 존재하는
이름만 다룹니다.

# 2단계 — 실제 코드에서 확인하기 (건너뛰지 말 것)

모은 이름 각각을 프로젝트 루트에서 Grep / Glob 으로 찾습니다.

- **찾았으면**: 해당 파일을 열어 실제로 무엇을 하는지 확인하고, 그 근거로 설명을 씁니다.
  경로는 `path/to/file.ts:42` 형태로 적습니다.
- **못 찾았고 문서가 새로 만든다고 한 것이면**: "이번에 새로 만듦" 으로 분류합니다.
- **못 찾았고 새로 만드는 것도 아니면**: 추측해서 쓰지 말고 "확인 못 함" 으로 적습니다.
  외부 라이브러리 심볼이면 그렇게 적습니다.

추측으로 채운 설명은 이 문서를 쓸모없게 만듭니다. 모르면 모른다고 적으세요.

# 3단계 — 걸러내기

모은 것을 전부 싣지 않습니다. 다음만 남깁니다:

- 이름만 봐서는 무슨 일을 하는지 알기 어려운 것
- 문서가 쓰긴 하는데 배경 설명 없이 지나가는 것
- 비슷한 이름이 둘 이상이라 헷갈릴 수 있는 것

빼는 것: `id`, `name`, `useState`, `map`, `console.log` 처럼 어느 프로젝트에나 있고
설명이 필요 없는 것. 프레임워크 표준 API 도 그 프로젝트에서 특이하게 쓰는 게 아니면 뺍니다.

전체 항목이 30개를 넘어가면, 문서를 읽는 데 실제로 필요한 순서로 잘라냅니다.
길어서 안 읽히는 용어집은 없는 것과 같습니다.

# 4단계 — 쓰기

아래 구조로 <GLOSSARY_ABSOLUTE_PATH> 에 Write 합니다. 내용이 없는 섹션은 통째로 뺍니다
(빈 표를 남기지 않습니다).

# 쓰는 방식

설명 칸은 옆자리 동료에게 말해주듯 이어지는 문장으로 씁니다. 항목을 나열하고 기호로
잇는 메모가 아니라, 읽으면 그대로 이해되는 말이어야 합니다.

- **백틱은 "이름" 칸과 "위치" 칸에만** 씁니다. 설명 문장 안에서는 되도록 쓰지 않습니다.
  파일 확장자나 필드 이름을 언급할 때도 코드 표기 없이 풀어서 적습니다.
- 가운뎃점(·) 이나 슬래시로 항목을 늘어놓지 않습니다. 문장으로 잇습니다.
- "하는 일" 은 한 문장. 한 줄에 담기면 두 문장으로 늘리지 않습니다.
- 비유를 쓰지 않습니다. 그 이름이 실제로 무엇을 하는지 그대로 씁니다.
- 대상 문서의 문장을 그대로 옮기지 않습니다. 처음 보는 사람이 이해할 말로 다시 씁니다.
- 영어 식별자는 이름 칸에 그대로 두고, 설명은 한국어로 씁니다.
- 마케팅 표현("강력한", "효율적인") 을 쓰지 않습니다.

이렇게 쓰지 마세요:

> `sessionId`/`userToken` 을 받아 `TTL` 만료 여부·서명 유효성·`revoked` 플래그를
> 확인하는 게이트. `AuthMiddleware` 의 요청 전처리 단계에서 호출됨

이렇게 쓰세요:

> 세션 아이디와 토큰을 받아 유효시간이 지났는지, 서명이 맞는지, 강제 만료된 세션은
> 아닌지를 차례로 확인한다. 셋 중 하나라도 걸리면 요청을 거절한다.

# 절대 하지 않는 것

- 대상 문서를 Write / Edit 하지 않습니다. 읽기만 합니다.
- 용어집에 `## 변경이력` 을 넣지 않습니다.
- 코드를 고치지 않습니다. 어떤 소스 파일도 수정하지 않습니다.
- 열어보지 않은 심볼을 설명하지 않습니다. 안 열어봤으면 "확인 못 함" 입니다.
- 대상 문서의 결정을 평가하거나 대안을 제안하지 않습니다. "이 설계는 별로다",
  "이렇게 하는 게 낫다" 는 당신 몫이 아닙니다.

단, **사실 관찰은 적습니다.** 문서가 쓰는 이름인데 선언하는 곳이 어디에도 없거나,
검증 문구가 가리키는 대상이 본문에 없으면 해당 항목의 설명 칸에 그대로 적습니다.
설계 비평이 아니라 "처음 읽는 사람이 여기서 막힌다" 는 사실 보고이고, 이게 이 문서의
값어치입니다. 판단이 섞이면 "(추정)" 을 붙여 추측임을 드러냅니다.

# 마지막에 보고할 것

Write 를 마친 뒤 아래 형식으로 한 문단만 돌려줍니다:

용어집 작성 완료 — <경로>
- 새로 만드는 것 N개 / 이미 있는 것 N개 / 헷갈리는 짝 N개
- 확인 못 한 이름: <목록, 없으면 "없음">
- 대상 문서 수정: 없음
```

## 4. 결과 확인하고 알리기

보조 에이전트가 끝나면 다음을 확인합니다.

1. `<slug>-glossary.md` 가 예상한 경로에 있는지
2. 용어집 안에 `## 변경이력` 제목이 없는지
3. 보조 에이전트의 보고가 `대상 문서 수정: 없음` 으로 끝나는지

그다음 보조 에이전트의 요약(항목 수와 확인 못 한 이름)을 사용자에게 그대로 보여주고,
용어집 경로를 알립니다.

용어집 파일이 없으면 실패를 알리고 다시 만들지 물어봅니다. 다른 작업을 대신 진행하지 않습니다.

## 5. 변경이력

용어집에는 `## 변경이력` 꼬리말을 붙이지 않습니다. 대상 문서가 바뀔 때마다 통째로 다시
만들어지는 파생 문서라 이력을 쌓는 것이 의미가 없습니다. js-super 피처 폴더의 마크다운 중
이 문서만 변경이력 규칙에서 빠집니다.

용어집을 만들었다고 해서 대상 문서의 변경이력에 항목을 추가하지도 않습니다. 대상 문서는
읽기만 했으므로 바뀐 것이 없습니다.

## 금지 사항

| 하면 안 되는 것 | 대신 이렇게 |
|---|---|
| 보조 에이전트가 대상 문서를 고침 | 읽기만 합니다. 용어집은 별개 파일입니다. |
| 문서에 나온 이름을 전부 싣기 | 처음 보는 사람이 멈출 이름만. 많으면 아무도 안 읽습니다. |
| 파일을 열어보지 않고 심볼 설명하기 | Grep 으로 찾고 열어본 뒤 씁니다. 못 찾으면 "확인 못 함". |
| 용어집에 변경이력 붙이기 | 재생성되는 파생 문서라 이력을 쌓지 않습니다. |
| 메인 대화에서 직접 용어집 쓰기 | 보조 에이전트 필수. 코드 탐색이 컨텍스트를 넘칩니다. |
| 이름으로 보아 캐시 같으니 그렇게 적기 | 뻔해 보이는 이름이 거짓말을 합니다. 열어보거나 "확인 못 함". |
| 비유로 설명하기 | 그 코드가 실제로 하는 일을 그대로 씁니다. |

## 관련

- `/write-plan` — 구현계획서를 만듭니다. 용어집은 더 이상 여기서 자동으로 만들어지지 않으며,
  필요할 때 `/glossary` 로 직접 부릅니다.
- `code-pretty` — 구현계획서의 수정 후 코드 블록을 다듬는 스킬. `/write-plan` 흐름 안에서
  자동으로 돕니다.
