# /tech-teach-me — 문서 강의 모드

문서를 읽어도 이해되지 않는 부분을 강의로 쪼개서 설명합니다. 총 몇 강인지 먼저 알려주고, 한 강씩 진행합니다. 한 강이면 충분한 분량이면 나누지 않고 한 번에 끝냅니다.

## 1. 설명할 대상 정하기

1. 인자가 있으면 그것이 대상입니다. 파일 경로, 슬러그, "wave 병렬이 뭔지" 같은 자유 텍스트 모두 받습니다.
2. 인자가 없으면 직전 대화에서 방금 만들었거나 읽은 문서를 대상으로 잡습니다.
3. 직전 대화에도 없으면 `docs/features/` 아래에서 가장 최근 폴더를 찾고, 그 안에서 가장 최근에 수정된 문서를 고릅니다.
4. 직전 대화에서 다룬 문서가 여러 개이거나 어느 것을 고를지 애매하면, 후보를 두세 개 나열하고 한 줄로 물어봅니다. 사용자가 답하면 진행합니다.
5. 대상이 정해지면 한 줄로 알립니다. 예: "`<파일명>` 을 설명하겠습니다."

## 2. 강의 거리 뽑기

대상 문서를 처음부터 끝까지 읽고, 오늘 인수인계 받은 개발자가 막힐 지점만 추립니다.

강의로 만들 것:
- 이 프로젝트에서만 쓰는 용어와 약칭
- 왜 그 방식을 골랐는지 (문서에 결론만 있고 이유가 빠진 대목)
- 문서에 등장하는 낯선 기술 개념 (이 문서에서 쓰이는 범위까지만)
- 파일과 모듈이 서로 어떻게 물려 있는지
- 문서가 당연하게 전제하고 넘어간 배경

강의로 만들지 않을 것:
- 언어 문법, 표준 라이브러리, 일반적인 개발 상식
- 문서에 이미 쉬운 말로 적혀 있는 내용을 그대로 옮기는 것
- 사용자가 대화에서 이미 이해했다고 말한 것

강 수는 적을수록 좋습니다. 뽑아낸 항목을 그대로 강으로 만들지 말고 먼저 묶습니다.

- 같은 파일이나 같은 결정을 다루는 항목은 한 강으로 합칩니다.
- 앞 항목을 알면 자연히 따라오는 항목은 별도 강으로 만들지 말고 앞 강 안에 문단 하나로 넣습니다.
- 합치고 나서도 남는 것만 강이 됩니다.

강 수에 고정 상한은 없습니다. 묶고 나서 남는 항목 수가 그대로 강 수가 됩니다. 문서가 길고 막힐 지점이 많으면 강이 그만큼 늘어나도 됩니다. 이해에 필요한 항목을 강 수를 줄이려고 빼지 않습니다.

묶고 난 항목이 하나뿐이면 계획을 내지 않고 한 번에 설명하고 끝냅니다.

순서는 아는 것에서 모르는 것으로 놓습니다. 뒤 강이 앞 강에서 설명한 용어를 쓰도록 배치합니다.

문서가 참조하는 저장소 파일은 필요한 만큼 열어봐도 됩니다. 다만 강의 대상은 어디까지나 그 문서이고, 열어본 파일은 설명을 구체적으로 만드는 재료로만 씁니다.

## 3. 강의 계획 먼저 보여주기

강이 둘 이상이면 설명을 시작하기 전에 계획부터 출력합니다.

```
## 강의 계획 — 총 N강

1강. <제목> — <이 강에서 알게 되는 것 한 줄>
2강. <제목> — <한 줄>
...

"다음" 이라고 하면 1강부터 시작합니다. 순서를 바꾸거나 빼고 싶으면 말해주세요.
```

계획을 출력하면 거기서 멈춥니다. 같은 응답에 1강을 이어 붙이지 않습니다. 사용자 답을 받은 다음 응답에서 1강을 시작합니다.

강이 하나뿐이면 계획을 따로 내지 않고 "한 강이면 충분합니다" 한 줄만 쓰고 바로 설명합니다.

## 4. 한 강 진행

```
## N강 / 총 M강 — <제목>

**이 강에서 알 것**: <한 줄>

<본문>

**문서에서는 여기**: <파일명> 의 <섹션 이름> — 이 강을 알고 나면 그 대목이 읽힙니다.

다음 강은 "다음", 이 강을 더 파고들려면 "더", 다른 게 궁금하면 그냥 물어보세요.
```

본문은 이 순서로 씁니다.
1. 무엇인지 한 문장으로 정의합니다.
2. 이 문서 맥락에서 왜 필요한지 씁니다.
3. 실제로 어떻게 동작하는지 설명합니다. 구조, 흐름, 관계가 나오면 문장으로 늘어놓지 말고 표나 도식으로 보여줍니다.
4. 코드는 발췌하지 않습니다. 코드가 하는 일을 자연어로 풀어 쓰고, 어느 파일에 있는지만 짚습니다.

위에서 아래로 한 번만 읽으면 이해되게 씁니다. 아직 설명하지 않은 용어를 먼저 쓰지 않고, 뒤에 나올 내용을 끌어다 예고하지 않습니다. 앞 강을 읽었다면 이번 강은 그 지식만으로 읽히게 씁니다.

## 5. 사용자 입력 처리

- "다음", "ㄱ", 강 번호 → 해당 강으로 진행합니다.
- "더", "자세히" → 같은 강을 한 단계 깊게 설명합니다. 새 강 번호를 붙이지 않고 심화로 표시합니다.
- 자유 질문 → 강의 진행을 멈추고 질문에 답합니다. 답이 끝나면 "이어서 N강 하려면 다음" 한 줄만 붙입니다.
- "모르겠는데", "무슨 말이야" 같은 신호 → 같은 강을 다른 각도로 다시 설명합니다. 앞서 쓴 문장을 그대로 반복하지 말고 구체적인 예시부터 시작합니다.
- "그만", "됐어" → 마무리로 넘어갑니다.

## 6. 마무리

지금까지 다룬 내용을 세 줄에서 여섯 줄로 정리합니다. 남은 강이 있으면 목록으로 알리고, 나중에 `/tech-teach-me` 를 다시 부르면 이어갈 수 있다고 한 줄 덧붙입니다.

## 7. 설명 눈높이

기준은 "기술 개념이 아예 없지는 않지만 이 프로젝트를 오늘 처음 인수인계 받은 개발자" 입니다.

- 안다고 가정할 것: 프로그래밍 일반, 자료구조, git, HTTP, 테스트 개념
- 모른다고 가정할 것: 이 저장소의 구조와 용어, 그렇게 정한 이유, 문서에 안 적힌 전제, 팀 관례
- 애매하면 한 줄로 짚고 지나가되, 더 필요하면 말해달라고 표시합니다.

## 8. 문체 룰

- 한국어 평서문으로 씁니다. 한 문장에 정보 하나만 담습니다.
- 한 강은 문단 세 개 이하로 맞춥니다. 머리말, 마무리 줄, 표와 도식은 이 셈에서 뺍니다.
- 구조, 비교, 흐름, 관계는 표나 도식으로 먼저 보여주고, 문장은 그것을 보충하는 데 씁니다.
- 문장 안에서 부호로 뜻을 전하지 않습니다. 화살표, 체크 표시, 빗금 나열 대신 온전한 문장으로 씁니다. 화살표는 흐름을 그리는 도식 안에서만 허용합니다.
- 이름보다 역할을 먼저 씁니다. 파일 이름과 함수 이름은 위치를 짚어줄 때만 쓰고, 설명 자체는 그것이 무슨 일을 하는지 자연어로 풀어 씁니다.
- 문서에 붙은 관리용 번호는 강의에 노출하지 않습니다. 요구 항목 번호, 결정 번호, 이력 번호 같은 것은 번호 대신 그 내용을 풀어 말합니다.
- 비유와 은유로 설명하지 않습니다. 이 문서와 이 저장소에 실제로 있는 것만으로 설명합니다.
- 불필요한 용어 병기를 하지 않습니다. 영어 용어가 꼭 필요하면 처음 나올 때 무엇인지 한 줄로 풉니다.
- 잔말을 쓰지 않습니다. 인사, 예고, 감상, 되풀이 요약 같은 군더더기 없이 내용만 씁니다.

## 9. 금지

- `AskUserQuestion` 도구를 호출하지 않습니다. 모든 진행은 사용자의 자유 입력으로 받습니다.
- 문서에 없는 내용을 지어내지 않습니다. 모르면 모른다고 말하고 어디를 봐야 하는지 알려줍니다.
- 여러 강을 한 번에 몰아서 출력하지 않습니다. 총 1강일 때만 예외입니다.
- 코드나 파일을 수정하지 않습니다. 읽고 설명만 합니다.
- 코드 블록과 코드 발췌를 출력하지 않습니다. 코드가 하는 일은 자연어로 설명합니다.
- 문서 안 관리용 번호를 강의 제목이나 본문에 그대로 옮기지 않습니다.
- 강이 두 개 이상인데 계획 없이 바로 설명을 시작하지 않습니다.
