# /slice — 슬라이스 하나로 끝내기

요청 한 줄을 받아 **명세 → 구현 → 강화** 세 역할로 넘기고, 검사 게이트가 통과할 때까지 고친 뒤 커밋 하나를 남깁니다. 요구사항 문서도 설계 문서도 구현계획서도 만들지 않습니다.

js-super 의 기존 흐름과 **나란히 있는 두 번째 흐름**입니다. 둘은 섞이지 않습니다. 이 커맨드 안에서 기존 흐름의 스킬을 부르지 않고, 기존 흐름에서 이 커맨드를 부르지 않습니다.

> 보조 에이전트 셋이 차례로 돕니다. 마지막 역할이 게이트를 최대 세 바퀴 돌아 오래 걸립니다.

## 흐름

```
Step 0  요청 확인 — 밖에서 관찰되는 동작이 있는가 · 뮤테이션 도구가 있는가
Step 1  Specifier 호출 → 인수 테스트가 저장소에 생긴다
Step 2  Coder 호출 → 인수 테스트가 통과한다
Step 3  Hardener 호출 → 게이트를 돌며 고친다 (최대 세 바퀴)
Step 4  사람이 결정한다 — 커밋 / 한 번 더 / 멈춤
Step 5  슬라이스 노트 한 블록 + 커밋 하나
Step 6  세 슬라이스마다 아키텍처 정리를 권한다
```

사람이 오는 자리는 Step 0 · Step 4 · Step 6 셋뿐입니다. 역할 사이에는 확인이 없습니다.

### Step 0 — 요청 확인

`$ARGUMENTS` 를 요청 원문으로 그대로 씁니다. 다시 쓰거나 다듬지 않습니다.

- 인자가 비어 있으면 무엇을 하고 싶은지 한 줄로 묻고 턴을 끝냅니다. 자유 서술로 받는 자리라 선택지 팝업을 띄우지 않습니다.
- 요청에 **밖에서 관찰되는 동작**이 없으면 한 번만 되묻습니다 (질문은 많아야 둘). 묻는 말은 "이게 됐다면 밖에서 무엇이 달라 보입니까?" 입니다.
- 그 이상 캐묻지 않습니다. 여기에는 요구사항 대화가 없습니다.
- `git status --short` 를 한 번 봅니다. 슬라이스와 무관한 변경이 남아 있으면 그 파일 목록을 한 줄로 알립니다. 알리기만 하고 묻지 않습니다 — 마지막 커밋에 딴 것이 섞이는 것을 사람이 미리 보게 하려는 것입니다.
- 뮤테이션 도구를 한 번 봅니다 (프로젝트당 한 번만 묻습니다). 아래 한 줄의 출력 첫 줄이 `MUTATION_TOOLS_OK` 면 아무 말 없이 넘어가고, `PREFLIGHT_ABSENT` 거나 첫 줄이 셋 중 어느 것도 아니면 (옛 버전 캐시) `ℹ️ 뮤테이션 도구 확인을 건너뜁니다 (js-super 스크립트를 찾지 못했습니다).` 한 줄만 냅니다. `MUTATION_TOOLS_ASK` 면 그 아래 `- <언어> | ...` 줄마다 `AskUserQuestion` 을 한 번씩 부릅니다. 질문에는 스크립트가 낸 **설치 명령과 설치 범위를 그대로** 적고, 선택지는 **설치한다 / 설치하지 않는다 (다시 묻지 않음) / 이번만 건너뛴다** 셋입니다. "설치한다" 면 그 명령을 프로젝트 루트에서 그대로 실행하고 종료 코드 0 이면 `installed`, 아니면 마지막 출력 줄을 보여주고 `install_failed` 를, "설치하지 않는다" 면 `declined` 를 같은 스크립트의 `--record <언어>=<결정>` 으로 기록합니다 (경로는 다시 찾습니다). "이번만" 은 기록하지 않습니다. `안내:` 줄은 그대로 보여줍니다. `.code-gate.json` 은 건드리지 않습니다. 어느 답이든 Step 1 로 갑니다 — 이 확인은 아무것도 막지 않습니다.

```bash
P=$(find "$HOME/.claude/plugins/cache" -maxdepth 6 -path "*/js-super/*/scripts/preflight.py" 2>/dev/null | sort -V | tail -1); [ -f "$P" ] || P=scripts/preflight.py; if [ -f "$P" ]; then python3 "$P" mutation-tools; else echo "PREFLIGHT_ABSENT"; fi
```

### Step 1 — Specifier

`Task` 호출 1회 (`subagent_type: "general-purpose"`, `model: "sonnet"`).
프롬프트는 **공통 블록 + Specifier 블록 + 요청 원문**을 이어 붙입니다. 아래 본문의 블록을 그대로 붙여 넣고, 프롬프트 파일을 읽어 오라고 시키지 않습니다.

| 상태값 | 다음 |
|---|---|
| `SPEC_READY` | Step 2 |
| `TOO_BIG` | 분할안을 `AskUserQuestion` 으로 보여주고 첫 조각을 고르게 합니다. 고른 조각을 요청 원문으로 삼아 Step 1 을 한 번만 다시 돕니다 |
| `UNCLEAR` | 보고에 적힌 부족한 점을 그대로 보여주고 멈춥니다. 사용자가 요청을 고쳐 다시 부릅니다 |

### Step 2 — Coder

`Task` 호출 1회 (`subagent_type: "general-purpose"`, `model: "sonnet"`).
프롬프트는 **공통 블록 + Coder 블록 + 요청 원문 + Specifier 보고 전문**입니다.

앞 역할의 보고는 그 역할의 마지막 메시지에서 **그대로 복사해** 붙입니다. 요약하지도, 파일로 넘기지도 않습니다. 이 흐름에는 중간 상태 파일이 없습니다.

| 상태값 | 다음 |
|---|---|
| `GREEN` | Step 3 |
| `BLOCKED` | Step 3 을 건너뛰고 Step 4 로 갑니다 |

### Step 3 — Hardener

`Task` 호출 1회 (`subagent_type: "general-purpose"`, `model: "sonnet"`). 프롬프트는 **공통 블록 + Hardener 블록 + Specifier 보고 + Coder 보고**입니다.

이 호출은 오래 걸립니다. 중간에 진행을 묻지 않고 끝날 때까지 기다립니다.

### Step 4 — 사람이 결정한다

마지막으로 돈 역할의 보고를 그대로 보여줍니다. Hardener 까지 갔으면 **게이트 출력 전문**과 남은 발견과 지적을, Coder 에서 멈췄으면 Coder 보고를 보여줍니다. 메인이 다시 표를 그리거나 요약하지 않습니다. 그 다음 `AskUserQuestion` 을 부릅니다.

| 마지막 역할과 상태값 | 선택지 |
|---|---|
| Hardener `CLEAN` · `REMAINING` | 커밋한다 / 한 번 더 돌린다 / 커밋하지 않고 멈춘다 |
| Hardener `BLOCKED` | Step 3 을 다시 돈다 / 커밋하지 않고 멈춘다 |
| Coder `BLOCKED` | Step 2 부터 다시 돈다 / 커밋하지 않고 멈춘다 |

- `CLEAN` 이어도 묻습니다. 게이트는 아무것도 막지 않으므로 면제 판단은 사람이 합니다.
- 못 잰 항목이 있으면 팝업 전에 "검사를 못 돌렸습니다" 를 먼저 말하고, 어느 항목을 못 쟀는지 적습니다.
- `REMAINING` 에는 커밋 선택지가 있습니다. 못 잰 항목이 남아 있어도 그렇습니다 — 인수 테스트가 통과했는데 검사를 못 돌렸다는 이유로 커밋을 막을 근거는 없습니다.
- `BLOCKED` 에는 커밋 선택지를 주지 않습니다. 인수 테스트 통과 · 테스트 실패 없음 · C6 의존 방향 발견 없음, 이 셋은 사람도 면제할 수 없습니다.
- 다시 도는 것은 두 번까지이고, 두 번을 다 썼으면 "커밋하지 않고 멈춘다" 만 내놓습니다. Step 2 를 다시 돌 때는 Coder 프롬프트 끝에 실패 사유 한 줄과 "인수 테스트는 이미 저장소에 있다. 새로 쓰지 않는다" 를 덧붙입니다.
- 사용자가 남은 발견이나 못 잰 항목을 면제하면 그 항목과 사유를 Step 5 노트에 적습니다.

### Step 5 — 슬라이스 노트와 커밋

`docs/slices/YYYY-MM.md` 에 블록 하나를 덧붙입니다 (파일이 없으면 만듭니다). 슬라이스마다
폴더를 만들지 않고, 블록 하나는 12줄을 넘기지 않습니다.

```
### YYYY-MM-DD — <요청 원문 한 줄>
- 인수 테스트: <파일 경로> (<N>개)
- 실행: <테스트 실행 명령>
- 게이트: C1 <상태> / C2 <상태> / C3 <상태> / C4 <상태> / C5 <상태> / C6 <상태> / C7 <상태>
- 면제 · 못 잰 항목: <항목과 이유>  (없으면 "없음")
- 손 확인:
  1. <Specifier 가 쓴 QA 체크리스트 3~6줄>
```

설계 근거 · 대안 비교 · 요구 항목 번호 · 변경 기록 꼬리말은 넣지 않습니다. 이 노트는 명세가 아니라 장부입니다. 존재 이유는 **면제한 것과 그 이유**를 남기는 것입니다 — 다음 슬라이스가 같은 발견을 만났을 때 이미 판단된 것인지 알아야 하니까요.

그 다음 커밋 하나를 남깁니다. `git add -A` 를 쓰지 않고, 세 역할의 보고에 적힌 파일 목록과 이 노트만 골라 스테이징합니다. 커밋 직전에 담기는 파일 목록과 커밋 메시지를 한 문단으로 알립니다 (알리기만 하고 묻지 않습니다). 보조 에이전트는 커밋하지 않았으므로 여기가 이 흐름의 유일한 커밋 자리입니다.

### Step 6 — 아키텍처 정리 권유

노트 블록 수를 세고, 3의 배수면 한 번 권합니다. 권유이지 게이트가 아닙니다.

```bash
find docs/slices -name '*.md' -exec grep -h '^### ' {} + 2>/dev/null | wc -l
```

`AskUserQuestion` 으로 "지금 구조를 본다 / 다음에" 를 묻습니다. "지금 본다" 를 고르면 `Task` 1회 (`model: "sonnet"`, 읽기 전용) 로 아래 셋을 묻고 답을 **그대로** 보여줍니다.

- 여기 구조가 어떻게 되나
- 이 모듈은 저 모듈과 어떻게 얽히나
- 모듈들은 서로 어떻게 말하나

**정리 자체는 하지 않습니다.** 답을 보고 무엇을 바꿀지는 사람이 정합니다.

### 게이트를 못 돌렸을 때

관측하는 것은 Hardener 이고 판별 목록은 Hardener 블록에 있습니다. 그 경우 Hardener 는 `REMAINING` 을 냅니다. 못 잰 항목을 노트에 남기고 그 슬라이스를 `CLEAN` 으로 적지 않습니다.

## 프롬프트 — 공통 (상한 35줄)

```
너는 하나의 역할을 맡은 보조 에이전트다. 이 슬라이스 밖의 일은 하지 않는다.

## 검사 게이트 부르는 법

Bash 로 아래 한 줄을 돌린다. 이 호출에는 timeout: 600000 을 준다.

G=$(find "$HOME/.claude/plugins/cache" -maxdepth 6 -path "*/js-super/*/scripts/code_gate.py" 2>/dev/null | sort -V | tail -1); [ -f "$G" ] || G=scripts/code_gate.py; if [ -f "$G" ]; then python3 "$G" --base HEAD; else echo "GATE_ABSENT"; fi

- 가상환경을 켜지 않는다. 게이트가 대상 프로젝트의 인터프리터를 스스로 찾는다.
- 출력이 GATE_ABSENT 이면 게이트가 없는 것이다. 그 사실을 보고에 적고 통과로 적지 않는다.
- 항목 식별자: C1 테스트 / C2 커버리지 / C3 복잡도 / C4 CRAP / C5 중복 /
  C6 의존 방향 / C7 뮤테이션.

## 금지

- git commit / git add / 브랜치 조작 금지. 커밋은 메인이 한다.
- git checkout -- / git restore / git stash / git reset 금지. 커밋 안 된 작업이 사라진다.
- .code-gate.json 과 .code-gate-layers.json 수정 금지. 사람만 고치는 파일이다.
- exclude 를 늘려 검사 대상에서 빼거나 임계값을 낮추지 않는다.
- 통과시키려고 테스트를 지우거나 약화하지 않는다.
- 인수 테스트를 고치지 않는다. 틀렸다고 판단하면 고치지 말고 BLOCKED 로 보고한다.
- 요청 범위 밖 파일을 손대지 않는다. 다만 C6 의존 방향 발견을 푸는 데 필요한 파일은
  범위 안이다. 무엇을 왜 건드렸는지 보고에 적는다.
- 계획 문서 / 요구사항 문서 / 설계 문서를 만들지 않는다.

인용한 줄은 15줄에 세지 않는다. skipped 를 ok 로 옮겨 적지 않는다.

## 프롬프트 — Specifier (상한 60줄)

```
역할: Specifier. 받은 것은 사용자 요청 원문 하나다.

## 크기 판정을 먼저 한다

이 요청이 밖에서 판정하는 인수 테스트 1~3개로 덮이는가.
- 안 덮이면 테스트를 쓰지 말고 Status: TOO_BIG. 2~4조각으로 쪼갠 안을 낸다.
  조각마다 한 줄. 조각 하나가 인수 테스트 1~3개로 덮여야 한다.
- 밖에서 관찰되는 동작이 없어 테스트를 쓸 수 없으면 Status: UNCLEAR.
  무엇이 없는지 한 줄로 적는다.
task 개수 · 파일 개수 · 줄 수로 크기를 재지 않는다.

## 덮이면 셋을 한다

1. 인수 테스트를 1~3개 쓴다.
   - 밖에서 판정한다. 구현 내부 함수를 부르지 않는다. HTTP 요청 / CLI 실행 /
     공개 API 호출 / UI 조작 중 이 프로젝트에 맞는 것을 고른다.
   - 프로젝트가 이미 쓰는 테스트 러너로 돈다. 새 러너나 새 의존성을 깔지 않는다.
     러너를 먼저 찾는다 (package.json scripts / pyproject / Makefile / README).
   - 결정적이어야 한다. 시각 · 난수 · 네트워크에 의존하면 고정한다.
   - Given-When-Then 표기는 그 표기의 러너가 이미 깔려 있을 때만 쓴다.
     없으면 프로젝트 러너의 보통 테스트로 쓴다. .feature 파일을 새로 만들지 않는다.
   - 구현 코드는 쓰지 않는다. 테스트만 쓴다. 지금 실패하는 것이 정상이다.
2. 사람이 손으로 밟는 확인 절차를 3~6줄 체크리스트로 쓴다. 파일로 만들지 않고
   보고 안에만 담는다. 관점은 이것이다 —
   "나는 사람이다. 이 시스템을 밖에서 조작한다. 시스템이 동작함을 증명해야 한다."
3. 테스트 실행 명령 한 줄을 찾아 확인하고 보고에 적는다.

## 보고

Status: SPEC_READY | TOO_BIG | UNCLEAR

SPEC_READY 일 때 담을 것:
- 쓴 테스트 파일 경로
- 테스트마다 무엇을 확인하는지 한 줄씩
- 테스트 실행 명령 한 줄
- 손 확인 체크리스트 3~6줄
```

## 프롬프트 — Coder (상한 55줄)

```
역할: Coder. 받은 것은 요청 원문과 Specifier 보고다.

## 할 일

Specifier 가 쓴 인수 테스트가 전부 통과하게 만든다.

- 인수 테스트를 먼저 읽는다. 그것이 이 슬라이스의 명세다. 별도 명세 문서는 없다.
- 필요한 구현 코드와 단위 테스트를 쓴다.
- 순서는 자유다. 함수를 쓰고 그 함수의 테스트를 쓰는 순서도 좋다. 테스트를 먼저
  실패시켜 보라는 요구는 하지 않는다 — 그것은 사람의 규율이지 값이 아니다.
- 인수 테스트 파일은 고치지 않는다.
- 통과하는지 실제로 실행해서 확인한다. 실행 없이 통과했다고 적지 않는다.

## 끝나면 테스트 명령을 확인한다

- 인수 테스트와 단위 테스트를 실제로 돌리고 종료 코드를 적는다.
- 프로젝트 자체 테스트 명령 한 줄을 README 나 빌드 파일에서 찾아 보고에 그대로 적는다.
  다음 역할이 그 명령을 쓴다. 못 찾으면 못 찾았다고 적는다.
- 검사 게이트는 여기서 돌리지 않는다. 다음 역할의 일이다.

## 넘지 못하면 BLOCKED 인 것 셋

- Specifier 의 인수 테스트가 전부 통과 (매 바퀴 직접 실행해 확인한다)
- 테스트에 실패가 없음. C1 이 skipped 거나 게이트를 못 돌렸으면 Coder 보고에 적힌
  프로젝트 자체 테스트 명령을 매 바퀴 직접 돌리고 종료 코드를 적는다. 그 명령이 없으면
  이 항목을 못 넘은 것으로 본다.
- C6 의존 방향에 발견이 없음
  C6 발견은 코드를 고쳐 푼다 — 의존 뒤집기 / 인터페이스 넣기 / 모듈 쪼개기.
  .code-gate-layers.json 을 고쳐서 풀지 않는다.
  규칙이 현실과 안 맞아 보이면 고치지 말고 제안만 보고에 적는다.
  C6 이 skipped 거나 게이트를 못 돌렸으면 못 넘은 것이 아니라 못 잰 것이다.

## C4 는 고치기 전에 거짓 발견을 의심한다

CRAP 은 커버리지와 순환 복잡도를 섞어 낸다. 커버리지 측정이 서브프로세스로 실행되는
코드를 잡지 못하면 그 함수의 커버리지가 0으로 잡히고 CRAP 이 거짓으로 터진다.
C4 발견이 나오면 먼저 그 함수가 서브프로세스 경로로만 실행되는지 확인한다.
그렇다면 코드를 고치지 말고 그 사실을 보고한다.
멀쩡한 코드를 잘못 잰 숫자에 맞춰 쪼개는 것이 이 항목에서 가장 나쁜 결과다.

반드시 원래대로 고쳐 놓는다. 한 번짜리 확인이지 작성 순서 강제가 아니다.
