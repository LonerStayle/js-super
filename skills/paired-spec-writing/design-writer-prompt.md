# 기술설계 작성 에이전트 지시문

`paired-spec-writing` 이 작성 기준을 대화에 남긴 뒤, 요구사항 작성 에이전트와 **같은 메시지에서** 이 지시문으로 fork 를 부른다. fork 는 대화 전체를 물려받으므로 요약을 붙이지 않는다.

**치환 규칙:** `<TECH_DESIGN_SKILL_PATH>` / `<TECH_DESIGN_PATH>` / `<FEATURE_NAME>` / `<SLUG>` / `<REPO_ROOT>` 자리만 채운다. `<REPO_ROOT>` 는 저장소 최상위 절대 경로다. 대화 원문이나 요약은 넣지 않는다 — fork 가 이미 보고 있다.

```
Agent tool:
  subagent_type: "fork"   # 대화와 메인 모델을 그대로 물려받는다
  description: "Write tech design <SLUG>"
  prompt: |
    너는 기술설계 문서 하나를 쓰는 작성자다. 사용자와의 대화는 이미 끝났다. 너는 그
    대화를 물려받은 fork 이고, 대화 마지막의 "작성 기준" 메시지가 입력이다.

    ## 먼저 지킬 것

    - 사용자에게 질문하지 않는다. 너에게는 사용자에게 묻는 도구가 없다
    - 어떤 스킬도 부르지 않는다. 아래 규칙 파일은 스킬로 실행하지 말고,
      지정한 섹션만 문서 작성 규칙으로 읽는다. 그 파일의 대화 절차 · 검증
      호출 · 승인 게이트 · 다음 단계 호출 문장은 너에게 해당하지 않는다
    - 대화와 작성 기준에 없는 결정을 새로 만들지 않는다. 비어 있는 것은
      "미정 — <이유>" 로 쓴다
    - 코드베이스는 읽어도 된다 (읽기 전용): <REPO_ROOT>
      대화에서 확인되지 않은 코드 사실 (파일 존재 · 개수 · 호출처 · 함수 반환) 을
      새로 적을 때만 코드를 직접 확인한다. 대화의 사실과 코드가 다르면 코드
      기준으로 쓰고 보고의 Mismatch 에 적는다
    - 아래 출력 경로의 파일 하나만 쓴다. 같은 폴더의 요구사항서
      (<SLUG>-requirements.md) 는 다른 작성자가 지금 쓰고 있다. 읽지 않는다.
      요구 항목과 그 번호는 작성 기준에 있다
    - 프론트매터를 쓰지 않는다. 산출물 깊이는 사용자 승인 뒤에 정해진다
    - `## 변경이력` footer 는 제목과 주석 한 줄만 두고 비운다

    ## 규칙 파일

    <TECH_DESIGN_SKILL_PATH>

    읽을 섹션 (제목 앞부분 일치):
    - `## Schema`
    - `## 산출물 문서 스타일`
    - `### 도면 형식`
    - `## 서술 수준 — 이름보다 역할`
    - `## Self-Review`

    다섯 중 하나라도 못 찾으면 파일을 쓰지 말고 멈춘다. 보고의 Status 를
    SECTION_MISSING 으로 하고 못 찾은 제목을 적는다.

    ## 출력

    경로: <TECH_DESIGN_PATH>
    제목: `# 개발방향: <FEATURE_NAME>`

    - 일곱 섹션 중 작성 기준의 "토픽 활성 판정" 에서 비활성인 것은 그 섹션 제목 줄에
      "— N/A: <이유>" 한 줄로만 쓴다. 활성 판정을 네가 다시 하지 않는다
    - §2 영향 파일 표의 요구 항목 칸에는 작성 기준의 요구 번호를 그대로 쓴다.
      작성 기준의 모든 요구 번호가 §2 또는 §4 에 한 번 이상 나와야 한다
    - §5 에는 작성 기준의 두 결정 목록 (사용자가 보는 동작 결정 · 구현 방식 결정) 를
      모두 옮긴다. 결정마다 고른 안 · 버린 안 · 비교축 셋 · 깨지는 조건을 남긴다
    - 작성 기준의 "제외 항목" 을 다시 범위 안으로 들이지 않는다
    - 요구사항서가 다룰 내용 (사용자가 보는 동작 결정의 비교 표, 범위 밖 표, 수용
      기준) 을 그대로 다시 싣지 않는다. 요구 번호로 가리키고, 기술설계에는 그 결정을
      구현하는 방식만 쓴다
    - 요구 항목의 서술을 새 문장으로 바꿔 쓰지 않는다. 요구의 의미는 요구사항서가
      정한다

    ## 자체 점검

    다 쓴 뒤 `## Self-Review` 의 항목으로 한 번 훑고 그 자리에서 고친다.
    첫 항목의 "<slug>-requirements.md 의 요구 N" 은 작성 기준의 요구 항목 번호로
    읽는다.

    ## 보고 형식 (이것만)

    Status: DONE | SECTION_MISSING
    Fixed: <점검에서 고친 것, 없으면 없음>
    Undecided: <미정으로 남긴 항목, 없으면 없음>
    Mismatch: <대화의 사실과 코드가 달랐던 사실과 코드 기준 값, 없으면 없음>
```
