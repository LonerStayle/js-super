# 요구사항 작성 에이전트 지시문

`paired-spec-writing` 이 작성 기준을 대화에 남긴 뒤, 기술설계 작성 에이전트와 **같은 메시지에서** 이 지시문으로 fork 를 부른다. fork 는 대화 전체를 물려받으므로 요약을 붙이지 않는다.

**치환 규칙:** `<BRAINSTORMING_SKILL_PATH>` / `<REQUIREMENTS_PATH>` / `<FEATURE_NAME>` / `<SLUG>` 자리만 채운다. 대화 원문이나 요약은 넣지 않는다 — fork 가 이미 보고 있다.

```
Agent tool:
  subagent_type: "fork"   # 대화와 메인 모델을 그대로 물려받는다
  description: "Write requirements <SLUG>"
  prompt: |
    너는 요구사항 문서 하나를 쓰는 작성자다. 사용자와의 대화는 이미 끝났다. 너는 그
    대화를 물려받은 fork 이고, 대화 마지막의 "작성 기준" 메시지가 입력이다.

    ## 먼저 지킬 것

    - 사용자에게 질문하지 않는다. 너에게는 사용자에게 묻는 도구가 없다
    - 어떤 스킬도 부르지 않는다. 아래 규칙 파일은 스킬로 실행하지 말고,
      지정한 섹션만 문서 작성 규칙으로 읽는다. 그 파일의 대화 절차 · 승인
      게이트 · 다음 단계 호출 문장은 너에게 해당하지 않는다
    - 대화와 작성 기준에 없는 결정을 새로 만들지 않는다. 비어 있는 것은
      "미정 — <이유>" 로 쓴다
    - 아래 출력 경로의 파일 하나만 쓴다. 같은 폴더에 다른 작성자가 기술설계서를
      동시에 쓰고 있다. 그 파일은 열지도 고치지도 않는다
    - `## 변경이력` footer 는 제목과 주석 한 줄만 두고 비운다. 이력은 사용자
      승인 뒤에 메인이 쓴다

    ## 규칙 파일

    <BRAINSTORMING_SKILL_PATH>

    읽을 섹션 (제목 앞부분 일치):
    - `## Document Schema`
    - `## 산출물 문서 스타일`
    - `## Self-Review`

    셋 중 하나라도 못 찾으면 파일을 쓰지 말고 멈춘다. 보고의 Status 를
    SECTION_MISSING 으로 하고 못 찾은 제목을 적는다.

    ## 출력

    경로: <REQUIREMENTS_PATH>
    제목: `# 요구사항: <FEATURE_NAME>`

    - 작성 기준의 "요구 항목" 번호를 그대로 쓴다. 번호를 바꾸거나 합치거나 새로
      붙이지 않는다. 기술설계서가 같은 번호로 이 항목들을 가리킨다
    - 작성 기준에 큰 작업 소속 표식이 있으면 제목 바로 아래, 다음 단계 안내 줄보다
      위에 그 한 줄을 그대로 넣는다. 없으면 넣지 않는다
    - 작성 기준의 "사용자가 보는 동작 결정" 만 문서에 옮긴다. 고른 안 · 버린 안 ·
      비교축 셋 · 깨지는 조건을 남긴다
    - 작성 기준의 "구현 방식 결정 "과 "기술설계 토픽" 은 문서에 옮기지 않는다.
      그 내용은 기술설계 작성자의 몫이다
    - 작성 기준의 "제외 항목" 은 전부 문서에 넣는다
    - 머리의 다음 단계 안내는 "기술설계서는 같은 대화에서 함께 작성됐다. 다음은
      /write-plan" 으로 쓴다. 규칙 파일 템플릿의 "다음은 기술설계" 문구를 쓰지 않는다
    - 기술 세부 (라이브러리 · 파일 구성 · 함수 · 호출 방식) 는 넣지 않는다.
      구현 방식 결정은 기술설계 작성자의 몫이다

    ## 자체 점검

    다 쓴 뒤 `## Self-Review` 의 항목으로 한 번 훑고 그 자리에서 고친다.
    "제외 항목 취합" 항목은 작성 기준의 제외 항목 목록과 대조한다.

    ## 보고 형식 (이것만)

    Status: DONE | SECTION_MISSING
    Fixed: <점검에서 고친 것, 없으면 없음>
    Undecided: <미정으로 남긴 항목, 없으면 없음>
```
