# H20 — 산출물 문서 스타일 시나리오 fixture

요구사항서와 기술설계서의 작성 스타일 룰의 기대 동작 검증. spec: `docs/features/2026-08-29-문서가독성개선/`.

문체 룰이라 기계 판정이 어렵다. 아래는 같은 내용을 두 가지로 쓴 대조 사례다 — 판단 기준을 맞춰보는 용도.

## 시나리오 A — 위에서 아래로 읽히는가

### 위반

> 판정은 표식이 있을 때만 적용한다. 표식이 없으면 기존 동작을 따른다.
>
> (세 섹션 뒤)
>
> 여기서 말하는 표식이란 문서 맨 위에 적는 깊이 값이다.

- 위반 이유: 앞 문단을 이해하려면 세 섹션 뒤를 먼저 읽어야 한다

### 통과

> 판정은 문서 맨 위에 적힌 깊이 값이 있을 때만 적용한다. 이 값이 없으면 기존 동작을 따른다.

- 통과 이유: 용어가 처음 등장하는 자리에서 뜻이 밝혀진다

## 시나리오 B — 비유와 잔말

### 위반

> 이 스킬은 문서의 파수꾼 역할을 한다. 마치 공항의 검색대처럼, 통과하지 못한 것은 아래로 내려가지 못한다. 우리는 이 부분을 특히 신경 써서 설계했고, 앞으로도 계속 다듬어 나갈 것이다.

- 위반 이유: 두 개의 비유가 실제 동작을 대신하고 있다. 마지막 문장은 정보가 없다

### 통과

> 이 스킬은 상위 문서와 대조해 누락과 모순을 찾는다. 발견된 항목은 보고서에 실리고, 사용자가 진행 여부를 정한다.

- 통과 이유: 무엇을 하는지, 결과가 어떻게 되는지가 그대로 적혀 있다

## 시나리오 C — 나열을 산문으로 늘어놓기

### 위반

> 스캔 대상은 현재 프로젝트와 글로벌과 다른 프로젝트 세 곳인데, 현재 프로젝트는 현재 위치에서 위로 올라가며 찾고, 글로벌은 홈 아래 고정 경로이며, 다른 프로젝트는 홈 전체를 훑되 숨김 폴더와 무거운 폴더는 건너뛴다.

- 위반 이유: 세 항목의 비교인데 한 문장에 뭉쳐 있어 대조가 안 된다

### 통과

| 대상 | 찾는 방법 |
|---|---|
| 현재 프로젝트 | 현재 위치에서 위로 올라가며 탐색 |
| 글로벌 | 홈 아래 고정 경로 |
| 다른 프로젝트 | 홈 전체 탐색 (숨김·무거운 폴더 제외) |

- 통과 이유: 항목이 셋이라 표가 맞다. 각 행을 나란히 비교할 수 있다

## 시나리오 D — 항목 코드

### 위반

> D-3 에 따라 스캔 범위를 정하고, R-7 의 완화책을 적용한다. 자세한 것은 D-T12 참조.

- 위반 이유: 독자가 코드표를 따로 들고 읽어야 한다

### 통과

> 스캔 범위 결정에 따라 홈 전체를 훑고, 접근 권한 오류는 무시한다. 자동 흐름에는 적용하지 않는다.

- 통과 이유: 각 항목이 무엇인지 그 자리에서 알 수 있다

### 금지 대상이 아닌 것 (통과)

> **요구 3**: 나열·비교·구조 설명은 산문 대신 표나 다이어그램으로 표현한다.

> 도면의 ① 은 스캔을 수행하는 부분이고, ② 는 결과를 출력하는 부분이다.

- 통과 이유: 요구 항목 번호는 다음 단계 문서가 항목을 찾는 데 쓰는 유일한 예외다. 도면 안 번호는 표에서 설명하기 위한 표기법이라 항목 코드가 아니다

## 시나리오 E — 도면 형식

### 위반 (기술설계서 §1 을 절차 나열로 채움)

```
사용자 입력 → 판정 → 분기 A → 처리 → 저장 → 보고
                  ↓
              분기 B → 처리
```

- 위반 이유: 절차 단계의 나열이라 구성 요소가 어떻게 배치돼 있는지가 안 보인다

### 통과 (구역과 배치를 보이는 도면)

```
┌──────────────────────────────────┐
│  입력 처리                        │
│  ┌────────┐      ┌────────┐      │
│  │ 판정 ① │ ───▶ │ 분기 ② │      │
│  └────────┘      └────────┘      │
└──────────────┬───────────────────┘
               ▼
┌──────────────────────────────────┐
│  저장 ③        보고 ④             │
└──────────────────────────────────┘
```

- 통과 이유: 어떤 구성 요소가 어느 구역에 속하는지 보인다. 번호는 아래 표에서 설명한다

### 형식 선택 (판단 기준)

| 상황 | 형식 |
|---|---|
| 구역·레이어·배치 (기본) | 아스키 박스 도면 |
| 구성 요소 여섯 개 초과 또는 요소별 설명 필요 | 아스키 도면 + 번호 + 설명 표 |
| 관계·조건 분기가 본질 + 렌더링 환경 전제 가능 | mermaid |

- 기대: 세 형식 중 상황에 맞는 것을 고른다. 항상 한 형식만 쓰면 기준이 없는 것

## 시나리오 F — 요구 항목 번호 하위 호환

세 세대의 문서를 읽는 쪽이 모두 인식하는지 본다.

| 세대 | 형식 | 위치 |
|---|---|---|
| 최신 | `**요구 N**:` | `## 요구 항목` |
| 직전 | `**FR-N**:` | `## 요구 항목` |
| 초기 | `**FR-N**:` | `## 3. 기능 요구사항 (FR)` |

- 기대: 옛 문서를 열었을 때 그 번호를 그대로 읽는다. 새 형식으로 고쳐 쓰지 않는다
- 위반: 옛 문서를 읽으면서 번호를 못 찾겠다고 하거나, 읽는 김에 새 형식으로 바꿔 저장하는 것

## 시나리오 G — 두 경로 일치

- 같은 요청을 수동 경로 (`/brainstorm`, `/design-tech`) 와 자동 흐름 (`/auto-brainstorm`, `/auto-design-tech`) 으로 각각 진행
- 기대: 두 산출물의 문체가 같다. 한쪽에만 비유나 항목 코드가 남으면 룰이 한 스킬에만 박힌 것

## 보조 검증

- 점검 장치 동작: 문서를 다 쓴 뒤 수동 경로는 자체 점검 목록에서, 자동 경로는 문서 작성 단계 안에서 스타일을 훑는지
- 범위 보존: 스킬 본문 자체의 영어 식별자와 내부 흐름도는 이번 룰의 대상이 아니다. 구현계획서의 문체도 대상이 아니다
- 이미 작성된 문서는 소급 수정하지 않는다
